### 四件套

```
① 元数据（有什么表/字段/含义）
② 血缘（这张表从哪来、被谁用）
③ 质量（数据对不对、全不全、及时不及时）
④ 权限（谁能看、谁能改）
```

**"没有元数据的数据平台"等于一个巨大的黑洞**。

### 元数据的三个层次

```
技术元数据：表结构、存储、分区、字段类型
业务元数据：字段含义、口径、责任人、更新频率
操作元数据：任务运行记录、数据量、耗时
```

**"业务元数据"是最缺的**（技术元数据往往能自动采集）。

**最小可用要求**：

```
每张核心表有：owner、口径说明、更新频率、上游依赖
```

### 血缘的价值

```
① 改一张表，能知道影响哪些下游
② 出问题，能快速定位"哪一环坏了"
③ 下线表，能确认"没人用了"
```

**采集方式**：

```
SQL 解析（静态）：覆盖 SQL 任务
运行时采集：覆盖存储过程/脚本（更真实）
```

**"静态解析 SQL"覆盖不全（动态拼接的 SQL 解析不出来）**，要结合运行时。

### 质量校验的三种落地

**① 调度内嵌校验（最常见）**

```sql
-- 在 ETL 任务末尾加校验节点
SELECT COUNT(*) FROM dwd.orders WHERE dt = '${bizdate}' AND id IS NULL;
-- 结果 > 0 → 任务失败并告警
```

**② 独立质量平台**

```
配置规则（非空/唯一/枚举/范围/波动）
→ 定时跑 → 出报告 → 告警
```

**③ 数据契约（Data Contract）**

```
上游承诺：字段、类型、时效、非空约束
下游订阅：变更必须提前通知
```

**"数据契约"是治理上游最有效的手段**（但需要组织推动）。

### 五类必做的质量规则

```
① 完整性：主键非空、必填字段非空、行数不低于昨日 80%
② 唯一性：主键/业务键唯一
③ 有效性：枚举值在范围内、金额非负
④ 一致性：父子表数量匹配、汇总=明细之和
⑤ 时效性：分区按时产出（如 8 点前）
```

**"行数波动"规则最实用**：

```
今日行数 / 近 7 日均值 在 [0.8, 1.2] 之外 → 告警
```

**它能发现"上游少推了数据"这类静默故障**。

### 五个"治理做成了报表工程"的误区

**① 只做"看板"，不做"拦截"**

```
质量报告很好看，但坏数据照样进下游
→ 校验要能"阻断任务"
```

**② 规则太多，告警疲劳**

```
2000 条规则每天告警 → 全部忽略
→ 只保留高价值规则（20–50 条）
```

**③ 没有 owner**

```
出问题找不到人 → 谁都不认
→ 每张核心表必须有 owner
```

**④ 只治理"新表"，存量不动**

```
存量问题永远存在
→ 按"使用频率 × 重要性"分批治理
```

**⑤ 血缘靠人工维护**

```
人工写的血缘三个月就过期
→ 能自动采集就别手工
```

### 一个"半年能见效"的路线

```
第 1 月：核心表打 owner + 口径（20 张）
第 2 月：上血缘采集（SQL 解析 + 运行时）
第 3 月：20 条质量规则（完整性/唯一/波动）+ 阻断
第 4 月：权限梳理（按角色，最小权限）
第 5 月：数据契约试点（1–2 个关键上游）
第 6 月：复盘，扩展到下一批核心表
```

**"先 20 张核心表"** 比"全平台一起上"现实得多。

### 检查清单

```
□ 核心表有 owner + 口径说明
□ 有血缘（自动采集优先）
□ 有 20–50 条高价值质量规则
□ 质量校验能阻断任务
□ 有"行数波动"规则
□ 权限按角色最小化
□ 有数据契约试点（上游变更提前通知）
□ 告警有分级（不是全量推送）
□ 下线表有流程（先确认无下游）
□ 有治理看板（问题数是否在降）
```
