三个词听起来像同一个问题，实际对应三种完全不同的失效模式。用错解法，问题会以另一种形式回来。

## 一、先分清三个场景

| 现象 | 数据是否存在 | 特征 | 后果 |
| --- | --- | --- | --- |
| **穿透** | 不存在 | 查不存在的数据，缓存无法命中，每次都打到 DB | 恶意请求可打垮 DB |
| **击穿** | 存在 | 某一个热点 key 过期瞬间，大量并发同时回源 | 单点压力尖峰 |
| **雪崩** | 存在 | 大批 key 同时过期，或缓存整体不可用 | DB 瞬时被打满 |

判断依据：**看请求打的 key 是不是同一个、是不是不存在的 key**。

## 二、穿透的两套解法

### 方案 1：缓存空值

查询无结果时，把 `null` 也写进缓存，TTL 设短（如 60s）。

```
SET product:999 "NULL" EX 60
```

优点简单；缺点是有大量随机 key 时内存会被垃圾占满（攻击者每次换一个 id）。

### 方案 2：布隆过滤器前置

把所有存在的 key 放进布隆过滤器（内存极小），请求先过 BF，明确不存在的直接拒绝。

```text
请求 → BloomFilter（不存在则直接返回）→ Redis → DB
```

注意两个特性：**只会误判"存在"（假阳性），不会误判"不存在"**；删除 key 需要计数型布隆过滤器或定期重建。

### 方案 3（业务层）

- 接口层做参数合法性校验（id 必须符合格式与范围）。
- 限流/黑名单：同一 IP 高频查不同 id 直接拒绝。
- 数据库层兜底：查询未命中时不要 `SELECT ... WHERE id=?` 走全表，索引必须存在。

## 三、击穿的解法：只让一个请求回源

### 互斥锁（mutex）

```text
if (cache miss) {
  if (SETNX lock:key 1 EX 10) {          // 抢到锁的才回源
    value = loadFromDB(key)
    SET cache:key value EX 300
    DEL lock:key
  } else {
    sleep(50ms); retry
  }
}
```

要点：**锁的过期时间必须小于业务超时**，否则死锁；失败要重试而不是直接返回空。

### 逻辑过期

不设置 Redis TTL，而是把过期时间存在 value 里。读到"逻辑过期"时异步重建，旧值继续服务。这保证读请求永不阻塞，代价是短时间内可能读到旧数据。

```json
{ "data": {...}, "expireAt": 1764000000 }
```

选择：**强一致优先用互斥锁，可用性优先用逻辑过期**。

## 四、雪崩的解法：打散 + 兜底

1. **TTL 加随机抖动**：`EX 300 + random(0,60)`，避免同一时刻集体失效。
2. **热点永不过期 + 后台刷新**：核心数据用逻辑过期 + 定时预热。
3. **多级缓存**：本地缓存（Caffeine/进程内）→ Redis → DB，一级失效不直接穿透到底。
4. **DB 侧限流**：连接池上限 + 队列长度，宁可拒绝也不要雪崩式超时（雪崩时 DB 的连接耗尽会让整个站点不可用，而不是只慢一点）。
5. **熔断**：DB 错误率超阈值时，直接返回降级内容（如静态兜底页），保住系统存活。

## 五、缓存与数据库的一致性

先更新 DB 再删缓存（Cache-Aside），不要"更新 DB 再更新缓存"——两个写操作的并发交错会导致缓存里长期是旧值。

```
写：UPDATE db; DELETE cache
读：cache miss → 读 db → SET cache
```

延迟双删解决"删除后又被脏读回填"的问题：删除 → 更新 DB → sleep(百毫秒级) → 再删一次。宽泛地说，只要允许最终一致，这套是最实用的方案。

强一致场景（如库存扣减）不要依赖缓存，直接把 Redis 当主存储用原子操作（Lua 脚本或 `DECR`），并配合持久化与补偿。

## 六、排障时的观察点

```bash
# 命中率（Redis）
redis-cli info stats | grep -E 'keyspace_hits|keyspace_misses'

# 过期与淘汰
redis-cli info stats | grep expired
redis-cli info memory | grep -E 'used_memory_human|maxmemory'

# 找出大 key（可能是热点）
redis-cli --bigkeys
```

命中率突然下降通常对应三种情况：key 批量过期、缓存被清空/重启、大量不存在的 key（穿透）。

> 一句话：**穿透解决"不存在的 key"，击穿解决"同一个 key 的并发"，雪崩解决"同时失效"。名字相似，药方完全不同。**
