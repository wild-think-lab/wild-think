### 先确认"是不是真的需要拆"

**四个不必要拆的信号**：

```
① 单表 < 5000 万行且查询都能走索引 → 加索引/优化查询
② 慢在"某些大查询" → 归档历史数据、加缓存
③ 慢在"写" → 升级硬件 / 读写分离
④ 慢在"备份/DDL" → 用在线 DDL、增量备份
```

**真需要拆的信号**：

```
① 单表 > 1 亿行，且索引已经优化到位仍慢
② 写入 QPS 单机撑不住（> 3000 写/秒）
③ 单机存储 > 2TB（备份/恢复时间不可接受）
④ 有明确的"按用户/租户隔离"的业务边界
```

**"先优化再拆分"是硬顺序**：拆分会带来一串新问题（见下文）。

### 三种拆分维度

| 维度 | 做法 | 适合 |
| --- | --- | --- |
| 垂直拆（按业务） | 订单库、用户库、商品库分开 | 业务边界清晰 |
| 水平拆（按数据） | 同一张表按 shard key 拆成 N 张 | 数据量大 |
| 分区表（单机内） | MySQL 的 PARTITION | 按时间归档 |

**建议顺序**：

```
① 垂直拆（最简单、风险最低）
② 分区表（按时间，主要用于归档）
③ 水平拆（最后手段）
```

### 分片键怎么选

**三条硬要求**：

```
① 高基数（避免热点）—— 用用户 ID 而不是"地区"
② 查询命中率高 —— 80% 的查询都带这个字段
③ 分布均匀 —— 不要用自增（会全打到最后一个分片）
```

**常见选择**：

```
用户相关 → user_id
订单相关 → 用 user_id（不是 order_id，否则按用户查要扫全部分片）
多租户 → tenant_id
```

**"订单表用 user_id 分片"的理由**：

```
用户看自己的订单 → 命中所属分片（1 次查询）
运营看全量订单 → 扫全部分片（可接受，频率低）
```

**如果订单用 order_id 分片**，那"用户查订单"就要扫全部片（高频操作）。

### 分片算法

```python
# 取模（简单，但扩容要重洗数据）
shard = hash(user_id) % 8

# 范围（便于扩容，但可能热点）
shard = 0 if user_id < 100000 else 1

# 一致性哈希（扩容影响小）
shard = consistent_hash(user_id)

# 预分片（一次分足够多，未来只扩物理机）
shard = hash(user_id) % 1024     # 1024 个逻辑分片，映射到 N 台机器
```

**推荐"预分片"**：一开始就分成 1024 个逻辑分片，路由到当前 N 台机器；扩容时只迁移逻辑分片（不重算 hash）。

### 跨分片查询的四种解法

**① 冗余（最实用）**

```
订单表按 user_id 分片
运营需要按"订单号"查 → 建一张"订单号 → user_id"的映射表（小表，可全量）
```

**② 广播（小表适用）**

```
商品表数据量小 → 每个分片都存一份完整副本（读本地）
```

**③ 异构索引（ES）**

```
把需要多维查询的数据同步到 ES
→ 复杂查询走 ES，拿到 ID 再回 MySQL 取详情
```

**④ 中间件拼装（最后手段）**

```
ShardingSphere 之类的中间件会把查询发到所有分片再合并
→ 延迟高、深度分页几乎不可用
```

**"深度分页"是分库分表最大的痛点**：

```
limit 100000, 20 在单表里就慢，跨分片更是灾难
→ 限制最大页数（如只允许前 100 页），或改用游标（where id > last_id）
```

### 双写迁移的完整流程

**目标**：从单库迁到分片，业务不中断。

```
① 建新分片集群（空表，表结构与旧一致）
② 双写：应用同时写旧库与新库（以旧库为准）
③ 全量迁移：把旧库数据按分片键导入新库
④ 增量追平：用 binlog（Canal/DTS）把期间的新数据同步过去
⑤ 校验：对比新旧数据（行数 + 抽样字段）
⑥ 切读：读流量切到新库（灰度 10% → 50% → 100%）
⑦ 切写：写流量切到新库，旧库改为只读/停写
⑧ 观察一周后下线旧库
```

**每一步都可回滚**：这是这个流程的核心价值。

**第⑤步"校验"必须做**：

```sql
-- 每个分片对比总行数
SELECT COUNT(*) FROM orders WHERE user_id % 8 = 0;

-- 抽样对比关键字段（如金额总和）
SELECT SUM(amount), COUNT(*) FROM orders WHERE user_id % 8 = 0;
```

**校验脚本示例思路**：

```python
# 按分片键范围，逐段对比
for start in range(0, MAX_UID, 10000):
    old = query_old(f"user_id >= {start} and user_id < {start+10000}")
    new = query_new_same_range()
    assert old.count == new.count
    assert old.sum_amount == new.sum_amount
```

### 五个必踩的坑

**① 自增 ID 冲突**

```
两个分片各自自增 → ID 重复
→ 用雪花 ID / 号段模式（Leaf）/ UUID（不推荐，无序）
```

**② 全局唯一约束失效**

```
唯一索引只在单个分片内有效
→ 需要"全局唯一"的字段（如手机号）要单独一张全局表，或用 Redis 去重
```

**③ 事务跨分片**

```
同一事务写两个分片 → 本地事务无法保证
→ 尽量避免（按分片键设计业务）；必须跨时用最终一致（消息 + 补偿）
```

**④ 排序与聚合**

```
ORDER BY create_time 跨分片 → 每个分片排一遍再合并（慢）
→ 用 ES 或预聚合表
```

**⑤ 统计类查询**

```
SELECT COUNT(*) 全表 → 扫所有分片
→ 用离线数仓（Hive/ClickHouse）出报表，不在线上库算
```

### 中间件 vs 应用层分片

| | 中间件（ShardingSphere） | 应用层（自己路由） |
| --- | --- | --- |
| 侵入性 | 低（改连接） | 高（改代码） |
| 灵活性 | 中 | 高 |
| 运维 | 多一个组件 | 少一个组件 |
| 排查 | 多一层，问题定位难 | 直接 |

**建议**：

```
已有系统改造 → 中间件（快）
新建系统 → 应用层分片（简单可控，不必引入中间件）
```

**"新建系统直接上中间件"往往是过度设计**。

### 检查清单

```
□ 先确认优化到位（索引、归档、缓存、读写分离）
□ 有明确的拆分信号（数据量/QPS/存储）
□ 先垂直拆，再考虑水平拆
□ 分片键高基数 + 命中 80% 查询
□ 用预分片（1024 逻辑分片）
□ 跨分片查询有冗余表/ES 方案
□ 限制深度分页
□ ID 用雪花/号段
□ 全局唯一约束有单独方案
□ 尽量不跨分片事务
□ 迁移走"双写 → 全量 → 增量 → 校验 → 切读 → 切写"
□ 每步可回滚
```
