### 一句话说清四层

```
ODS（贴源层）  ：原样存放业务库/日志的原始数据，不做清洗
DWD（明细层）  ：清洗后的事实明细（去重、标准化、关联）
DWS（汇总层）  ：按主题/维度做轻度聚合（如按天按用户）
ADS（应用层）  ：面向具体报表/看板的最终数据集
```

**"为什么要分四层"**：

```
不分层的代价：
① 每个报表都从原始表算 → 计算重复、口径不一
② 业务表结构一变，所有报表全挂
③ 找问题要从原始数据开始，无法快速复用中间结果
```

**分层就是把"计算复杂度"固化成"可复用的中间表"**。

### ODS：不要做任何加工

```
内容：同步过来的原始表（可能带增量标记、时间戳）
原则：与源系统一一对应，不做过滤、不做类型转换
```

**常见做法**：

```
① 每天全量快照（小表）或增量（大表）
② 保留原始字段名（便于和源系统对照）
③ 带 etl_time（加载时间）与 src_db（来源标记）
```

**分区**：通常 `dt`（数据日期）或 `pt`（加载批次）。

**ODS 不是"永远不清理"**：

```
保留期：7–30 天（够回滚/重跑即可）
长期归档到冷存储
```

### DWD：明细事实，加维度

```
特征：一行一个业务事件（一次订单、一次访问、一次支付）
原则：清洗、去重、标准化、退化维度与维度关联
```

**典型加工**：

```
① 脏数据过滤（金额为空、状态非法）
② 类型标准化（时间统一成 timestamp、金额统一成 decimal）
③ 去重（幂等加载、主键去重）
④ 关联维度（把 user_id 补成 user_name / 城市 / 渠道）
```

**表命名**：`dwd_<业务域>_<事实>_df`（df = day fact）/ `di`（增量）。

**一个 DWD 例子**：

```sql
INSERT OVERWRITE TABLE dwd_trade_order_di PARTITION(dt='2026-11-27')
SELECT
    o.order_id,
    o.user_id,
    u.city,
    u.channel,
    CAST(o.amount AS DECIMAL(18,2)) AS amount,
    o.status,
    FROM_UNIXTIME(o.create_ts) AS create_time
FROM ods_order o
LEFT JOIN dim_user u ON o.user_id = u.user_id
WHERE o.dt = '2026-11-27'
  AND o.amount IS NOT NULL
  AND o.status IN ('paid','shipped','done');
```

### DWS：轻度汇总

```
特征：按"主题 + 维度"聚合，粒度比 DWD 粗
目的：让 80% 的报表能直接从 DWS 出，而不是回 DWD 算
```

**典型粒度**：

```
① 用户 × 天（dws_user_1d）
② 商品 × 天（dws_item_1d）
③ 渠道 × 天（dws_channel_1d）
```

**注意"轻度"二字**：

```
DWS 不做"复杂派生指标"（如 LTV、留存率）
那是 ADS 的活
```

**聚合函数的选择**：

```
count / sum / max / min → 直接聚合
distinct 计数 → 用 bitmap 或 HyperLogLog（保精度 vs 省空间）
```

**推荐可累加设计**：

```
把"可累加"的度量放 DWS（sum、count）
把"不可累加"（如去重人数、比率）放 ADS 或按天存明细
```

**"比率不能跨天相加"是数仓最常见的错误**：

```
错误：每天转化率 5%，直接平均 7 天 → 得到 5%（可能错）
正确：存 sum(下单数) 与 sum(访问数)，在 ADS 才算比率
```

### ADS：面向应用

```
特征：一张表对应一个报表/看板
原则：字段名可直接用于展示，指标已算好
```

**典型**：

```
ads_sales_daily      ：每日销售额、订单数、客单价
ads_user_growth      ：新增、活跃、留存
ads_channel_compare  ：渠道对比
```

**ADS 可以冗余、可以宽**（宽表换查询速度）：

```
宽表：把常用维度全部拍平到一张表
代价：存储变大、更新成本高
收益：查询快、报表简单
```

### 维度表（DIM）

```
dim_user   ：用户属性（城市、渠道、注册时间）
dim_item   ：商品属性（类目、品牌、价格带）
dim_date   ：日期维表（年/季/月/周/是否节假日）
```

**拉链表的场景**：

```
需要"历史上某天的用户城市是什么"
→ 用拉链表（start_date / end_date）
否则用"每日快照"（存储代价高但简单）
```

**SCD（缓慢变化维）三种处理**：

```
Type 1：直接覆盖（不保留历史）
Type 2：加版本行（保留历史，最常用）
Type 3：加"上一版本"字段（只留一层）
```

### 五个常见错误

**① ODS 里就做清洗**

```
后果：原始数据不可追溯，口径出问题无法回溯
原则：ODS 保持原样，清洗放 DWD
```

**② 跳过 DWD 直接 ODS → ADS**

```
后果：每张报表都在算同样的逻辑，口径打架
原则：公共逻辑沉淀到 DWD/DWS
```

**③ 指标定义没有唯一来源**

```
现象："销售额"在三个报表里三个数
根因：指标定义散落在各 SQL 里
原则：建"指标字典"（一个指标一个口径，集中维护）
```

**④ 分区不剪枝**

```sql
-- 错：全表扫
SELECT * FROM dwd_order WHERE create_time > '2026-01-01';
-- 对：带分区条件
SELECT * FROM dwd_order WHERE dt BETWEEN '2026-01-01' AND '2026-11-27';
```

**⑤ 小文件爆炸**

```
现象：一个分区几千个小文件 → 查询极慢
原因：频繁小批写入
处理：定时合并（compact）、控制写入批次、用支持 compaction 的格式
```

### 一个最小的分层目录

```
warehouse/
├── ods/            # 贴源
│   ├── ods_order/
│   └── ods_user/
├── dwd/            # 明细
│   ├── dwd_trade_order_di/
│   └── dwd_user_login_di/
├── dws/            # 汇总
│   ├── dws_user_1d/
│   └── dws_item_1d/
├── ads/            # 应用
│   ├── ads_sales_daily/
│   └── ads_user_growth/
└── dim/            # 维度
    ├── dim_user/
    └── dim_date/
```

**命名规范**（建议）：

```
<层>_<业务域>_<主题>_<粒度>
粒度后缀：di（增量日）、df（全量日）、1d（按天汇总）、td（累计）
```

### 数据质量校验（必须做）

```sql
-- 每层都要有基础校验
-- ① 主键唯一
SELECT COUNT(*) - COUNT(DISTINCT order_id) AS dup FROM dwd_trade_order_di WHERE dt='...';
-- ② 关键字段非空
SELECT COUNT(*) FROM dwd_trade_order_di WHERE dt='...' AND amount IS NULL;
-- ③ 环比波动（防上游断流）
-- ④ 行数不为 0
-- ⑤ 分区存在
```

**"上游断流但任务成功"是最隐蔽的故障**：任务跑完 0 行，下游全空，看板一片零。

**必须加"行数环比"校验**（如与昨天比波动 > 50% 就报警）。

### 检查清单

```
□ 四层职责清晰（ODS 不清洗）
□ 命名有规范（层_域_主题_粒度）
□ 公共逻辑沉淀在 DWD/DWS
□ 指标有唯一口径（指标字典）
□ 可累加度量放 DWS，比率在 ADS 算
□ 维度表有 SCD 策略
□ 查询带分区条件
□ 控制小文件（定时合并）
□ 每层有数据质量校验（含行数环比）
□ 有保留期与归档策略
```
