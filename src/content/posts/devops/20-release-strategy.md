### 四种方式

| 方式 | 资源 | 回滚 | 适用 |
| --- | --- | --- | --- |
| 全量替换（停机） | 1 套 | 慢 | 内部系统/可停机 |
| 滚动 | 1 套 | 中（等滚动完） | 无状态服务（最常见） |
| 蓝绿 | 2 套 | 秒级（切流量） | 关键服务、需瞬时回滚 |
| 金丝雀 | 1 套 + 少量新版本 | 秒级（摘掉新版本） | 有风险变更、需要真实流量验证 |

**"蓝绿"解决的是"回滚速度"，"金丝雀"解决的是"验证充分性"**。

### 金丝雀的核心：流量怎么分

```
① 按用户（按 ID 哈希/白名单）—— 最常用
② 按请求比例（1% → 5% → 20% → 100%）
③ 按地域/机房
④ 按设备/入口（内部员工先）
```

**"按用户哈希"的好处**：

```
同一个用户始终落在同一版本 → 体验一致，问题可复现
```

**"按请求比例随机"** 会导致"用户刷新一次换一个版本"（体验割裂）。

### 金丝雀的判定标准（必须有）

```
① 错误率（新版本 vs 老版本）
② 延迟 P99
③ 业务指标（下单成功率/转化率）
④ 日志异常量
```

**"没有判定标准就是发了灰度没看"**。

**自动化判定**：

```promql
# 新版本错误率显著高于老版本 → 自动回滚
sum(rate(http_requests_total{version="canary",code=~"5.."}[5m))
/ sum(rate(http_requests_total{version="canary"}[5m))
> 0.02
```

**"自动回滚"** 才能把金丝雀的价值兑现。

### 蓝绿的关键：切流量

```
① 新环境（green）部署完、自检通过
② 在 LB/网关切换 upstream
③ 观察 15 分钟
④ 老环境（blue）保留 24 小时（可立即切回）
```

**"保留老环境"是蓝绿的灵魂**（否则和滚动没区别）。

**成本**：

```
两套环境 = 双倍资源（数据库通常共享，需兼容）
```

### 五个"灰度发了但没效果"的原因

**① 灰度比例太小/时间太短**

```
1% 流量 + 10 分钟 → 采样不足，异常没暴露
```

**② 用户没真正落到新版本**

```
LB 会话保持/缓存 → 实际还是老版本在服务
→ 用"响应头带版本号"验证
```

**③ 新旧版本不兼容**

```
新版本改了下游接口语义 → 老版本消费不了
→ 必须"向前/向后兼容"（双写、兼容读）
```

**④ 判定指标没区分版本**

```
监控指标没有 version 标签 → 无法对比
```

**"给所有指标打 version label"** 是灰度的前提。

**⑤ 回滚了但缓存/配置没回滚**

```
代码回滚了，但配置中心/Redis 里的"新格式数据"还在
→ 老代码读不了
```

### 数据库变更的兼容三原则

```
① 先加（新字段可空）→ 双写 → 切读 → 再删旧字段
② 不重命名（重命名 = 破坏兼容）
③ 变更分多次发布（不一次到位）
```

**"发布和迁移解耦"** 是零停机的前提。

### 一个"安全发布"的流程

```
1) 变更分级（低/中/高风险）
2) 低风险：滚动 + 自动回滚（错误率/延迟阈值）
3) 中风险：金丝雀 1% → 20% → 100%，每步观察 15 分钟
4) 高风险：金丝雀 + 人工确认 + 蓝绿兜底
5) 每次发布打 annotation（看板可见）
6) 发布后 30 分钟值班关注
```

**"变更分级"** 比"全都走最重流程"可持续。

### 检查清单

```
□ 有变更分级
□ 无状态服务用滚动（配好探针与优雅退出）
□ 关键服务用蓝绿（保留老环境）
□ 高风险用金丝雀（按用户哈希）
□ 指标带 version label
□ 有自动化判定与回滚
□ 数据库变更遵循兼容三原则
□ 发布打 annotation
□ 有"发布后观察期"
□ 回滚演练过（真跑过一次）
```
