### 三类配置，别混在一起

```
① 启动配置（端口/日志级别/数据源）—— 改完要重启
② 运行时配置（开关/阈值/限流）—— 要热生效
③ 机密（密码/密钥/证书）—— 要加密 + 权限
```

**"把机密和业务开关放同一个中心"** 是最常见的安全隐患。

### 为什么需要配置中心

```
① 改配置不用发版（降低变更风险）
② 变更可审计（谁改了什么）
③ 可以灰度（先 10% 实例生效）
④ 可以回滚（一键切回旧值）
```

**"直接改文件 + 重启"** 的问题：

```
不知道改了什么、谁改的、什么时候改的
```

### 变更流程（关键）

```
① 提交（带"变更单/原因"）
② 校验（类型/范围/依赖）
③ 灰度（按实例/用户比例）
④ 观察（指标是否异常）
⑤ 全量 or 回滚
```

**"直接全量推送"** 是最危险的做法。

### 灰度怎么做

```
① 按实例灰度：标签 selector（如 env=canary）
② 按用户灰度：ID 哈希分桶
③ 按比例：10% → 50% → 100%
```

**"配置灰度要能'立刻回滚'"** —— 保留旧版本，一键切换。

### 敏感项处理

```
① 加密存储（KMS/Vault）
② 访问控制（谁能读哪些）
③ 不落日志（读取时不打印明文）
④ 定期轮换（尤其密钥）
```

**"配置中心里明文存数据库密码"** 一旦中心被读，全部失守。

**推荐**：

```
配置中心只存"引用"（secret://db/password）
运行时从 Vault 取真实值
```

### 五个"上了配置中心反而更常出事"

**① 全量推送 + 无观察**

```
一个错误的阈值推送全集群 → 全站异常
```

**② 没有类型/范围校验**

```
刚改成"1000 秒超时"（实际单位是毫秒）→ 全站挂
```

**③ 配置项太多、没人知道含义**

```
2000 个 key，无注释无归属 → 谁都不敢动
```

**④ 客户端缓存不一致**

```
部分实例读到旧值，部分读到新值 → 行为不一致
→ 需要"版本号 + 主动通知"或"短轮询"
```

**⑤ 没有"配置变更"与"指标"的关联**

```
改完出问题，无法判断"是不是这次配置引起的"
→ 变更打 annotation 到看板
```

### 一个"最小可用"的设计

```
① 存储：配置中心（带版本历史）
② 校验：schema（JSON Schema/自定义）
③ 分发：长轮询或推送（带版本号）
④ 灰度：按标签/比例
⑤ 回滚：一键切上一版
⑥ 审计：谁/何时/改了什么/为什么
⑦ 机密：走 Vault，中心只存引用
```

### 三个"落地时会争论的点"

**① 配置放代码还是中心**

```
"基础设施配置"放代码（GitOps）
"业务开关"放中心（运营可改）
```

**② 热更新的边界**

```
能热更的：开关/阈值/白名单
不能热更的：连接池大小/线程数（改了会抖动）
```

**③ 谁有权改生产配置**

```
必须有审批（至少两人确认）
```

### 检查清单

```
□ 区分启动/运行时/机密三类
□ 变更走"提交-校验-灰度-观察"
□ 灰度可回滚
□ 有类型与范围校验
□ 机密走 Vault/加密，不落日志
□ 分发带版本号（避免不一致）
□ 有审计（谁/何时/为什么）
□ 配置项有注释与 owner
□ 变更打 annotation 到监控
□ 关键配置变更需审批
```
