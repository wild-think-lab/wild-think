### 它解决的三件事

```
① 加速（代理公网仓库，内网缓存）
② 隔离（公网不可用时仍能构建）
③ 管控（只允许审核过的依赖进入）
```

**"只为了加速"是初级用法，"管控供应链"才是核心价值**。

### 三类仓库

```
proxy（代理）：指向公网仓库，缓存下载
hosted（私有）：存放自己发布的包/镜像
group（聚合）：把多个仓库合成一个入口
```

**最佳实践**：

```
应用只配置 group 地址
→ 内部包与公网包都能解析，切换后端不用改应用配置
```

### 常见仓库类型

| 生态 | 格式 | 说明 |
| --- | --- | --- |
| Maven | maven2 | Java 依赖 |
| npm | npm | JS |
| PyPI | pypi | Python |
| Docker | docker | 镜像 |
| apt/yum | apt/yum | 系统包 |
| 通用 | raw | 任意文件（安装包/配置） |

**"镜像也放制品仓库"** 是现代做法（统一管控 + 扫描）。

### 清理策略（最重要的运维项）

```
① 快照类：保留最近 N 个（如 10 个）
② 发布类：永久保留（release 不应该被删）
③ 代理缓存：按"最后访问时间"清理（如 90 天未用）
④ Docker：按 tag 规则清理（保留 latest + 最近 20 个 sha）
```

**"磁盘满"是制品仓库最常见的故障**：

```
现象：构建全部失败（无法拉依赖）
原因：磁盘满 → blob store 写入失败
```

**必须有"磁盘水位告警 + 定期清理任务"**。

### 依赖投毒防护

```
① 私有仓库优先，且"内部命名空间不允许 fallback 到公网"
② 只允许白名单中的上游（不要"代理一切"）
③ 新包进仓库要人工/自动审核
④ 定期扫描仓库里的包（漏洞/恶意）
```

**"内部包名被公网抢注"（依赖混淆）的防线就在这里**。

### 五个让仓库"越用越慢"的原因

**① 没有清理（元数据膨胀）**

```
百万级 artifact → 浏览与搜索变慢 → 数据库压力大
```

**② 数据库没调优**

```
Nexus 用 H2/OrientDB/PostgreSQL
默认配置在大规模下会明显吃力
→ 用外部 PostgreSQL + 调 JVM 内存
```

**③ 存储用了 NAS/NFS**

```
blob store 在 NFS 上性能差且有锁问题
→ 用本地盘或对象存储（S3 blob store）
```

**④ 代理了太多上游**

```
代理 20 个仓库 → 每次请求要"逐个尝试"
→ 只代理真正需要的
```

**⑤ 单实例扛所有流量**

```
构建高峰 → 所有节点同时拉依赖 → 打满
→ 前置缓存（CDN/nginx）+ 多实例
```

### 镜像仓库的额外注意

```
① 镜像层去重（同一 layer 不重复存）
② 清理"未被任何 tag 引用的 layer"（GC）
③ 代理 Docker Hub 时要限流（避免被上游封）
④ 签名与扫描（cosign + trivy）
```

**Docker 仓库的 GC 不能随便跑**：

```
GC 期间仓库应只读（否则可能删掉正在被引用的层）
```

### 一个"最小可用"的配置清单

```
① 建 group（应用只配这一个地址）
② 每个生态一个 proxy + 一个 hosted
③ 内部命名空间禁止 fallback
④ 清理任务（代理 90 天、快照保留 10 个）
⑤ 磁盘水位告警（80%/90%）
⑥ 外部数据库（大规模）
⑦ blob store 用本地盘或 S3
⑧ 定期漏洞扫描
⑨ 备份元数据（配置 + 数据库）
```

**"备份元数据"很容易被忽略**：

```
blob 数据还在，但元数据丢了 → 仓库等于废了
```

### 检查清单

```
□ 应用只配 group 地址
□ 内部包禁止 fallback 到公网
□ 有清理任务（按类型分别设）
□ 磁盘水位告警
□ 大规模用外部数据库
□ blob store 不用 NFS
□ 只代理必要上游
□ 构建高峰有前置缓存
□ 镜像 GC 在只读窗口做
□ 有漏洞扫描
□ 元数据有备份
```
