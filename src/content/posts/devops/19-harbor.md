### 装完默认能用，但不等于可用

```
默认配置：单机、本地存储、无扫描、无配额
→ 生产必须补：项目权限、GC、配额、扫描、备份
```

### 项目和权限模型

```
项目（project）：镜像的顶层命名空间
成员（member）：用户或组，角色分 4 级
```

| 角色 | 权限 |
| --- | --- |
| 访客 | 只读 |
| 开发者 | 推送/拉取 |
| 维护者 | + 扫描/复制/删除 |
| 项目管理员 | + 成员管理 |

**"给所有开发都开发者权限"是常见问题**：

```
→ 谁能删镜像？谁改复制规则？
→ 需要维护者/管理员角色收窄
```

**项目规划建议**：

```
① 按"团队"建项目（一个团队一个）
② 按"环境"建项目（prod/staging）
③ 公共镜像放 library
```

### 垃圾回收（最重要）

```
删除镜像 tag ≠ 删除层数据
→ 必须跑 GC 才真正释放空间
```

```bash
# 在 harbor-core 容器内
harbor-core: registry-gc
```

**GC 的约束**：

```
① 期间仓库应为只读（否则可能删掉正在被推送的层）
② 大仓库 GC 耗时长（小时级）
③ 定期跑（每周/每月），不要等到磁盘满
```

**"删除镜像后磁盘没降"** → 90% 是没跑 GC。

### 配额

```
项目级配额：限制单个项目能用多少存储
系统级：限制总量
```

**没有配额的后果**：

```
某个团队 CI 每天推 100 个镜像 → 半年后磁盘满 → 全体构建失败
```

### 漏洞扫描

```
内置 Trivy：每次推送自动扫描
阻止策略：项目设置里勾"阻止潜在漏洞镜像被拉取"
```

**建议**：

```
① 扫描必开
② 只对"高危且可修复"做阻止（否则挡得没法用）
③ 定期看"未修复的高危"清单
```

**"CVSS ≥ 9 且可修复才阻断"** 是相对可接受的阈值。

### 复制与高可用

```
复制（replication）：A 仓库 → B 仓库（跨机房/跨云）
```

**用途**：

```
① 灾备（主仓库挂了从仓库能拉）
② 混合云分发（生产集群就近拉）
```

**高可用方案**：

```
① 共享对象存储（S3/MinIO）+ 多 Harbor 实例
② 或"主备 + 复制"
```

**"单机 Harbor"不可用于生产**。

### 签名

```bash
cosign sign --key cosign.key registry.example.com/app:v1
cosign verify --key cosign.pub registry.example.com/app:v1
```

**配合准入策略**：

```
Kyverno 校验签名 → 只允许已签名镜像运行
```

### 五个"装完就用"的坑

**① 用默认密码 Harbor12345 上生产**

```
必须改，且不要把 admin 账户给开发用
```

**② 存储用 NFS**

```
registry 对 NFS 的锁支持不佳 → 推送偶发失败
→ 用本地盘或 S3
```

**③ 没配 HTTPS**

```
Docker 需要 insecure-registry 配置（每个节点都要改）
→ 长期看必须上证书
```

**④ 时区/证书过期**

```
容器内时区不对 → 日志时间错乱
自签证书过期 → 全部拉取失败
```

**⑤ 备份只备了数据库**

```
元数据在 DB，镜像在存储 → 两者都要备
或"用复制做冗余"更简单
```

### 一个"上线检查"清单

```
□ HTTPS 证书（有效期内 + 自动续期提醒）
□ admin 密码已改
□ 项目按团队/环境划分
□ 角色最小化（不是全员开发者）
□ 配额已设置
□ 扫描已开启 + 阻断策略合理
□ GC 定时任务
□ 复制规则（如需灾备）
□ 存储不用 NFS
□ 日志接入统一平台
□ 备份（DB + 存储）或复制冗余
□ 磁盘水位告警
```

### 检查清单

```
□ 不用默认密码
□ 有 HTTPS
□ 项目与角色规划清楚
□ 有配额
□ 开了扫描
□ 有 GC 定时
□ 存储非 NFS
□ 有灾备/复制（视要求）
□ 有磁盘告警
□ 有备份或冗余
□ 签名与准入（高安全要求场景）
```
