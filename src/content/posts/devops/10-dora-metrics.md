### 四个指标

| 指标 | 定义 | 好的水平（参考） |
| --- | --- | --- |
| 交付周期 Lead Time | 代码提交 → 上线的时间 | < 1 天 |
| 部署频率 Deploy Frequency | 多久上线一次 | 每天多次 |
| 变更失败率 CFR | 上线后需要回滚/热修的比例 | < 15% |
| 恢复时长 MTTR | 故障发生 → 恢复的时间 | < 1 小时 |

**这四个是一组，单看一个会骗人**：部署很频繁但失败率高，说明在"快速制造故障"；周期很短但 MTTR 很长，说明修复能力跟不上。

### 怎么算（别拍脑袋）

**交付周期**：

```
起点：代码合入主干（merge commit 时间）
终点：该提交在生产环境生效（发布记录时间）
按 P50 / P75 统计，别用平均值（少数超长会拉偏）
```

**部署频率**：

```
= 生产发布次数 / 统计周期
按周统计，区分"计划发布"与"紧急热修"
```

**变更失败率**：

```
= 需要回滚或 24 小时内热修的发布数 / 总发布数
"热修"的定义要写清楚（否则各人算法不同）
```

**恢复时长**：

```
= 故障开始（告警触发或用户可感知）→ 服务恢复
只算 P1/P2，不算轻微问题
```

### 数据从哪来

| 指标 | 数据源 |
| --- | --- |
| 交付周期 | Git 提交时间 + 发布系统记录 |
| 部署频率 | CI/CD 的 deploy 事件 |
| 变更失败率 | 发布记录 + 回滚记录 |
| 恢复时长 | 告警系统 + 工单系统 |

**没有自动采集就不要开始度量**：手工填表的数据一定会失真。

```yaml
# 发布事件上报示例（ArgoCD/流水线里加一步）
curl -X POST https://metrics.example.com/api/deploy \
  -d '{"service":"api","env":"prod","sha":"abc123","at":"2026-11-27T10:00:00Z"}'
```

### 指标为什么会变坏

| 现象 | 常见根因 |
| --- | --- |
| 周期变长 | 审批环节多、测试环境排队、跨团队依赖 |
| 频率下降 | 发布风险高（不敢发）、批量发（一次发很多） |
| 失败率上升 | 测试覆盖不足、配置漂移、缺少灰度 |
| MTTR 变长 | 缺监控、缺回滚手段、值班响应慢 |

**先看瓶颈在哪一段**：把"提交 → 构建 → 测试 → 部署 → 验证"拆开，找耗时最长的那段。

### 别把 DORA 当 KPI

一旦用于考核，必然出现：

- 拆小提交刷"部署频率"。
- 把回滚叫"计划内变更"来降 CFR。
- 故障早报晚修来刷 MTTR。

**正确用法**：作为"团队自评与改进方向"的输入，而不是排名。

### 一个改进例子

某团队初始数据：

```
周期 P75：9 天
部署频率：每周 1 次
CFR：30%
MTTR：4 小时
```

做了三件事（3 个月后）：

```
① 拆掉"发布审批会"，改为"自动化门禁 + 值班人一键发布"
② 引入灰度（10% → 50% → 100%），失败率降到 12%
③ 加了一键回滚脚本 + 关键接口监控
周期 P75：2 天 / 频率：每天 1–2 次 / CFR 12% / MTTR 40 分钟
```

**没有大量"加班"，只是把等待和返工去掉了**。

### 采集与展示

简单做法：一个周报，四个数 + 一张趋势图 + 一句"本周瓶颈在哪"。

```
DORA 周报（11/24–11/30）
- 交付周期 P75：2.1 天（上周 2.6）
- 部署次数：9（其中热修 1）
- CFR：11%（1/9）
- MTTR：35 分钟
- 本周瓶颈：预发环境排队（平均等 4 小时）
```

### 检查清单

```
□ 四个指标都有自动数据源（不是手工填）
□ 用 P50/P75，不用平均
□ 定义写清楚（尤其"热修""故障开始"）
□ 拆段看瓶颈（哪一段最慢）
□ 不用于个人考核
□ 每周/每月有趋势与一句结论
```
