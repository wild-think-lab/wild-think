### 一个共同规律

```
所有 Web 漏洞的本质：把"用户输入"当成了"代码/指令/信任边界"
```

**"过滤关键字"之所以没用**，是因为攻击者的输入空间无限，而你的黑名单有限。

### SQL 注入

**成因**：

```php
// 错：字符串拼接
$sql = "SELECT * FROM user WHERE name='" . $_GET['name'] . "'";
// 输入 admin' OR '1'='1 → 逻辑被改写
```

**正确防御（唯一可靠）**：

```php
// 参数化查询
$stmt = $pdo->prepare("SELECT * FROM user WHERE name = ?");
$stmt->execute([$_GET['name']]);
```

**要点**：

```
① 参数化/预编译是治本
② 不要"手工转义"（不同上下文规则不同）
③ ORM 的"拼接字符串"仍然会注入（要检查用法）
```

**为什么"过滤单引号"没用**：

```
数值型注入不需要引号：id=1 OR 1=1
不同数据库/字符集有各自的绕过方式
```

**二次注入**：

```
第一次存入的数据"经过转义"→ 安全
后来某处"直接拼接"这个存下来的值 → 依然注入
```

**"所有 SQL 拼接"都要查，包括"看起来安全的内部变量"**。

### XSS

**三种类型**：

```
反射型：输入直接回显（钓鱼链接）
存储型：存进数据库，别人访问就触发（最危险）
DOM 型：前端 JS 把不可信数据写进 DOM
```

**成因示例**：

```html
<!-- 错 -->
<div>{{ user_input }}</div>
<script>document.body.innerHTML = location.hash</script>
```

**防御（按优先级）**：

```
① 输出编码（按上下文：HTML/属性/JS/URL 各不同）
② 用框架的自动转义（不要手写 innerHTML）
③ CSP（兜底，即使有注入也难执行）
④ HttpOnly Cookie（防被脚本读走会话）
```

**"输入过滤"是辅助手段**：

```
有些场景必须拒绝危险字符（如富文本）
但"输出编码"才是根本
```

**富文本的黑名单永远不够**：

```
用成熟的白名单库（如 DOMPurify）而不是自己写正则
```

### CSRF

**成因**：

```
浏览器会自动带 Cookie
→ 攻击页面向你的站点发请求，浏览器自动带上你的会话
```

**防御**：

```
① SameSite Cookie（Lax/Strict）—— 最有效且成本最低
② CSRF Token（服务端校验）
③ 校验 Origin/Referer
④ 敏感操作二次确认
```

**`SameSite=Lax`** 能挡住大部分跨站 POST。

**"用 Token 但放在 Cookie 里"** 是无效的（攻击者也能带）。

**Token 的正确用法**：

```
服务端生成 → 放进表单/请求头 → 服务端比对
（攻击者拿不到 token，因为跨域读不到页面内容）
```

### SSRF

**成因**：

```
服务端根据"用户提供的 URL"去发请求
→ 可以打内网（云元数据、内部管理接口）
```

**典型**：

```
图片抓取、URL 预览、Webhook 回调、文件导入
```

**防御**：

```
① 白名单（只允许指定域名/协议）
② 禁止内网地址（但要注意"绕过"：DNS 重绑定、302 跳转）
③ 出网走代理（统一管控）
④ 元数据服务访问禁用（如 AWS 169.254.169.254）
```

**"只校验一次 URL"会被绕过**：

```
先解析成内网地址 → 校验 → 再解析时 DNS 被重绑定
→ 校验与实际连接的目标不同
```

**正确做法**：

```
解析出 IP 后"用这个 IP 连接"（不要二次解析）
或"出网代理做统一白名单"
```

### "能防到什么程度"的现实评估

| 漏洞 | 防御强度 | 残余风险 |
| --- | --- | --- |
| SQL 注入 | 参数化 = 基本免疫 | ORM 误用、二次注入 |
| XSS | 输出编码 + CSP = 高 | DOM 型、第三方脚本 |
| CSRF | SameSite + Token = 高 | 老浏览器、子域攻击 |
| SSRF | 白名单 + 代理 = 高 | 0day 绕过、配置错误 |

**"分层防御"是唯一正确的姿势**：

```
输入校验（辅助）+ 输出编码（核心）+ CSP（兜底）
```

### 五个"以为是防御其实不是"的做法

**① 用黑名单过滤 `<script>`**

```
大小写/编码/嵌套标签都能绕过
```

**② 只在前端校验**

```
绕过前端直接调接口
```

**③ 用 `strip_tags` 当 XSS 防御**

```
它不能处理属性里的注入（<img onerror>）
```

**④ 把 WAF 当唯一防线**

```
WAF 能挡"已知模式"，挡不住"逻辑漏洞"
```

**⑤ 认为"内网就安全"**

```
SSRF、横向移动、内网未授权接口 —— 内网并不安全
```

### 一个"检查清单式"的自查

```
□ 所有 SQL 用参数化（包括 ORM 的自定义查询）
□ 所有输出按上下文编码（框架自动转义是否真开了）
□ 富文本用白名单库
□ Cookie 加 HttpOnly + Secure + SameSite
□ 有 CSP（至少 default-src 'self'）
□ 敏感操作有 CSRF Token 或 SameSite
□ 所有"服务端发请求"的功能有白名单
□ 禁止访问云元数据地址
□ 出网有代理/统一管控
□ 有 WAF（但不作为唯一防线）
□ 有安全测试（SAST/DAST/渗透）
```

### 一句话总结

**"把不可信输入永远当数据，而不是当代码"** —— 所有防御都从这句话推出来。
