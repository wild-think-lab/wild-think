### 先说最重要的判断

```
应急响应第一原则：先止损，再取证，最后追因
第一错误：为了"保留现场"而不止损（攻击者还在动）
第二错误：为了"快速止损"而破坏证据（事后无法追责/无法防再发）
```

**两者不冲突**：**快照 + 隔离可以同时做**，关键是顺序与方式。

### 七步框架

```
① 确认与分级（是不是真事件、多严重）
② 止损与隔离（切断影响面）
③ 取证与保全（快照、日志、内存）
④ 分析与定位（根因是什么）
⑤ 清除与恢复（根除、恢复业务）
⑥ 加固与监控（防再发）
⑦ 复盘与改进（写报告、更新预案）
```

### 第一步：确认与分级

**要回答四个问题**：

```
① 是不是安全事件？（也可能是一起故障）
② 影响范围多大？（单机 / 单业务 / 全站 / 数据泄露）
③ 数据是否外泄？（决定是否需要上报/通知用户）
④ 是否仍在持续？（决定紧急程度）
```

**分级（P0–P3）**：

| 级别 | 判据 | 响应时间 |
| --- | --- | --- |
| P0 | 核心业务中断/数据泄露 | 立即（全员） |
| P1 | 部分业务不可用/主机被控 | 15 分钟内 |
| P2 | 单机异常/可疑行为 | 1 小时内 |
| P3 | 低危告警/合规检查项 | 当天 |

**分级不是为了流程，是为了"决定谁被叫醒"**。

### 第二步：止损与隔离

**按"影响面"从大到小切**：

```
① 有对外暴露入口被利用 → 先摘流量（改 DNS / 关端口 / 上 WAF 规则）
② 有横向移动迹象 → 隔离受影响主机（网络层，不是关机）
③ 账号被控 → 立即禁用该账号 + 轮换密钥
④ 数据外泄 → 保存证据 + 评估范围 + 启动通报流程
```

**关键：隔离用网络手段，不要关机**

```
关机 → 内存里的证据丢失（恶意进程、内存马）
隔离 → 断网但保留运行状态，可做内存取证
```

**如果必须关机**（如勒索软件在扩散）：

```
先拔网线（保留内存）→ 再决定是否关机
```

### 第三步：取证与保全

**按"易失性顺序"采集**（RFC 3227）：

```
① 内存（最易失）
② 网络连接与路由表
③ 运行中的进程
④ 临时文件与缓存
⑤ 磁盘
⑥ 日志与远程备份
```

**一台 Linux 主机的采集清单**：

```bash
mkdir -p /evidence/$(date +%F-%H%M)
cd /evidence

# 内存（用 LiME 或 avml）
avml memory.lime

# 网络
ss -antp > net.txt
ip addr > ip.txt
ip route > route.txt
iptables-save > iptables.txt

# 进程与模块
ps auxf > ps.txt
lsmod > lsmod.txt
ls -la /proc/*/exe > procs.txt 2>/dev/null

# 登录与审计
last -a > last.txt
lastb -a > lastb.txt
cat /var/log/auth.log > auth.log 2>/dev/null
ausearch -i > audit.txt 2>/dev/null

# 文件变化（关键目录）
find /etc /usr/local /root /tmp -type f -newermt '-7 days' > changed.txt

# 定时任务与启动项
crontab -l > crontab_root.txt
ls -la /etc/cron* > cron_dirs.txt
systemctl list-units --type=service > services.txt

# 哈希校验（防事后篡改质疑）
sha256sum /evidence/*/* > /evidence/sha256.txt
```

**"哈希校验"是取证的基本素养**：证明证据没被改过。

**云端/容器环境**：

```
① 打快照（云主机支持）
② 导出容器日志（kubectl logs --previous）
③ 保存节点事件（kubectl get events）
④ 保存审计日志（API server audit）
```

### 第四步：分析与定位

**必须先回答"入口在哪"**：

```
① 是弱口令？(公网暴露的 SSH/RDP/数据库)
② 是漏洞？(Web 应用 / 中间件 CVE)
③ 是供应链？(依赖包/镜像被投毒)
④ 是内部人？(异常登录、权限滥用)
⑤ 是钓鱼？(员工点了链接/装了木马)
```

**常用排查命令**：

```bash
# 异常进程（父进程可疑、路径在 /tmp）
ps -ef --forest | grep -vE "\[|kernel"

# 外联（与可疑 IP 通信）
ss -antp | grep ESTAB
# 对照威胁情报查 IP

# 隐藏进程/模块（rootkit 迹象）
ls /proc | grep -E '^[0-9]+$' | wc -l   # 与 ps 数量对比
cat /proc/modules | wc -l

# 账号异常
grep -E "uid=0" /etc/passwd            # 除了 root 的 UID 0
awk -F: '$3>=1000' /etc/passwd         # 新增的普通账号
cat /etc/sudoers.d/*

# SSH 授权后门
cat ~/.ssh/authorized_keys
find / -name authorized_keys 2>/dev/null
```

**"UID=0 的非 root 账号"是最常见的后门**。

### 第五步：清除与恢复

```
① 确认清除范围（一个机？整个集群？）
② 重建而非修补（被控主机建议重建）
③ 从可信备份恢复数据（不要从被控机恢复到生产）
④ 轮换所有相关密钥（密码、API key、证书、token）
⑤ 验证恢复（业务正常 + 无异常外联）
```

**"重建"优于"清理"的理由**：

```
① 无法 100% 确认恶意进程/后门被清干净
② 内核级/固件级后门无法通过普通手段清除
③ 重建的成本远低于"二次被攻破"的信誉损失
```

### 第六步：加固与监控

```
① 关闭被利用的入口（端口/账号/漏洞）
② 加固同类资产（其他机器是否也有同样问题）
③ 加检测规则（同样的攻击再来要能告警）
④ 提高日志保留期（事后追查需要）
⑤ 做一次全量扫描（横向是否还有被控）
```

**"同类资产"最容易被忽略**：

```
攻击者能进来的路，其他 100 台机器大概率也能
→ 必须做全量排查
```

### 第七步：复盘

**报告要回答（不是流水账）**：

```
① 时间线（精确到分钟）
② 根因（技术根因 + 管理根因）
③ 影响（数据/业务/合规）
④ 处置过程与效果
⑤ 改进项（每条要有人 + 有期）
```

**"管理根因"往往更重要**：

```
例：一台机器暴露公网 3 个月没人发现
→ 技术根因是"没关端口"
→ 管理根因是"没有暴露面巡检机制"
```

### 五个"越救越糟"的错误动作

**① 直接重启/重装**

```
丢失内存证据，攻击者痕迹消失，无法追因
```

**② 用被控机器上的工具排查**

```
攻击者可能替换了 ps/netstat/ls（rootkit）
→ 用干净环境的工具或静态编译的 busybox
```

**③ 只清一台机器**

```
横向移动：清了 A，B 还在
```

**④ 改了密码但没轮换密钥**

```
SSH key / API token / 数据库连接串还在用旧的 → 后门仍在
```

**⑤ 对外沟通失控**

```
现象：客服/销售在外面乱说"我们没被攻击"
后果：后面通报时前后矛盾，信任崩塌
→ 统一由指定人对外沟通
```

### 沟通模板（对内）

```
【事件通报 #1】
级别：P1
现象：某 API 出现异常外联，已确认主机被入侵
影响：该服务已摘流量，其他业务正常
当前动作：隔离主机 + 取证 + 排查横向
需要配合：各团队检查是否有可疑账号/密钥
下一条更新：30 分钟后
```

**四个要素**：级别、影响、动作、下次更新时间。**不要写猜测**。

### 检查清单

```
□ 有分级标准（P0–P3）与响应人清单
□ 有"止损优先"的决策原则
□ 隔离用网络手段（不关机）
□ 取证按易失性顺序，且做哈希
□ 有内存取证工具（avml/LiME）
□ 有"入口在哪"的必答项
□ 检查 UID=0 账号 / authorized_keys / 定时任务
□ 被控主机倾向重建
□ 所有密钥轮换
□ 同类资产全量排查
□ 复盘含"管理根因"
□ 对外沟通统一口径
```
