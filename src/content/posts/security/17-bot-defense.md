### 先说结论

```
没有一层能单独挡住爬虫
五层叠加才能把成本推到"不值得爬"
```

**而且**：**误杀率与拦截率是一对反向指标**，任何方案都在两者间取平衡。

### 五层的实际效果

| 层 | 手段 | 对新手 | 对中手 | 对老手 |
| --- | --- | --- | --- | --- |
| 1 | UA / Referer 黑名单 | 有效 | 无效 | 无效 |
| 2 | IP 频率限制 | 部分 | 部分 | 无效（换代理池） |
| 3 | 行为特征（访问路径/间隔） | 有效 | 部分 | 部分 |
| 4 | JS 挑战 / 验证码 | 有效 | 有效 | 部分 |
| 5 | TLS 指纹 / 浏览器指纹 | 有效 | 有效 | 有效但非绝对 |

**"三层以上基本能挡住 90% 的爬虫"**。

### 为什么"封 IP"越来越没用

```
① 代理池便宜（住宅代理按流量计费，几美元起）
② 云函数/容器可批量起
③ IPv6 地址几乎无限
④ 正常用户也可能在 NAT 后面（封一段会误杀）
```

**"按 IP 封"的真实成本**：

```
封 1000 个 IP → 攻击者换 1000 个（成本 5 美元）
而你：误杀了多少共享出口的公司/学校用户？
```

### 更有效的手段

**① 频率限制（按"多维度"）**

```nginx
# 不只按 IP，还按 UA + 路径
limit_req_zone $binary_remote_addr zone=ip:10m rate=5r/s;
limit_req_zone $http_user_agent zone=ua:10m rate=20r/s;
limit_req_zone $binary_remote_addr$uri zone=path:10m rate=1r/s;
```

**关键**：**单个维度都能绕过，叠起来成本高**。

**② 行为特征**

```
正常用户：首页 → 列表 → 详情（有间隔、有停留）
爬虫：直接打详情页（无间隔、无 Referer、路径规律）
```

**判断规则**：

```python
# 简化示例
if referer is None and path.startswith("/item/") and interval < 0.2:
    score += 3
if requests_per_minute > 60 and unique_paths > 50:
    score += 5
```

**③ JS 挑战**

```
返回一段 JS，要求计算后带上特定 header 再访问
→ 无头浏览器要执行 JS（成本上升）
```

**代价**：正常用户也会多等 100–500ms；对 SEO 有影响（搜索引擎可能被挡）。

**④ TLS 指纹**

```
不同客户端（curl/Python/Chrome）的 TLS 握手参数不同（JA3 指纹）
→ 识别"声称是 Chrome 但指纹是 Python"的请求
```

**这是目前最有效的一层**，因为改 TLS 指纹比改 UA 难得多。

**⑤ 浏览器指纹**

```
canvas/WebGL 指纹、字体列表、插件、时区、语言
→ 识别"同一个无头浏览器换 IP"
```

### 误杀的代价

**误杀率 1% 意味着什么**：

```
日活 100 万 → 每天 1 万个用户被挡
→ 客服工单、差评、流失
```

**降低误杀的四个做法**：

```
① 分级处置：可疑 → 验证码（不是直接拦）
② 白名单：登录用户、付费用户、搜索引擎
③ 灰度：先"只记录不拦"，观察一周再开
④ 申诉入口：被拦了能找到人
```

**"只记录不拦截"是最重要的一步**：先看日志里"如果拦了会拦掉谁"。

### 一个实用的拦截策略

```
score 计算：
  UA 可疑          +1
  无 Referer       +2
  间隔 < 0.3s      +2
  1 分钟内 > 100 请求 +3
  路径规律（id 递增）+3
  TLS 指纹不匹配   +5

score 0-2   → 放行
score 3-5   → 加 JS 挑战
score 6-8   → 验证码
score > 8   → 429 / 拦截
```

**关键是"分级"而不是"二元"**：绝大多数请求在第一档，不影响体验。

### 被爬的成本核算

**先算"被爬的代价"**：

```
① 带宽成本（图片/视频被大量拉取）
② 计算成本（每次请求都查 DB）
③ 数据价值损失（内容被搬走）
```

**再算"防护成本"**：

```
① WAF/CDN 费用
② 误杀带来的客服与流失
③ 维护规则的人力
```

**结论**：

```
如果被爬的代价 < 防护成本 → 用"缓存 + 限流"就够了
（把成本转到 CDN，而不是拦住）
```

**很多站点的最优解是"让爬虫变慢"，而不是"拦住"**：

```
限流到 1 r/s → 爬 10 万条要 27 小时 → 对方可能放弃
而正常用户完全感知不到
```

### 五个实操要点

**① 静态资源与 API 分开限流**

```
图片/JS/CSS → CDN + 强缓存（被爬也不花你的钱）
API → 严格限流
```

**② 列表页加"翻页上限"**

```
只允许翻到第 50 页（爬虫拿不全，用户够用）
```

**③ 详情页加"随机延迟+签名"**

```
URL 带时效签名（如 5 分钟有效）
→ 爬虫拿到的链接很快失效
```

**④ 敏感数据不进 HTML**

```
价格/联系方式用 XHR 拿（且带鉴权）
→ 爬 HTML 拿不到
```

**⑤ 监控"异常访问模式"**

```
同一 UA 的请求量突增
同一路径的访问来自大量不同 IP
某个 IP 段的请求 100% 是详情页
```

### 检查清单

```
□ 多层叠加（不只封 IP）
□ 限流多维（IP + UA + 路径）
□ 有行为评分（分级处置）
□ 有 TLS 指纹识别（对老手有效）
□ 先"只记录"再开拦截
□ 白名单（登录/付费/搜索引擎）
□ 有申诉入口
□ 静态资源走 CDN + 强缓存
□ 列表页有翻页上限
□ 敏感数据不直接进 HTML
□ 算过"被爬成本 vs 防护成本"
```
