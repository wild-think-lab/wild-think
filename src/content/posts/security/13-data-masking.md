### 一个真实的事故

某系统把完整请求体写进日志（含身份证号、手机号、银行卡号），日志平台有 20 个开发能查，还有一次误把日志文件打包发给了外部厂商。

**这就是"日志里的敏感数据"最典型的三种风险**：

```
① 内部越权查看（能查日志不等于该看身份证号）
② 日志外发（打包给别人、提交到工单）
③ 日志存储被拖（日志平台往往防护较弱）
```

### 敏感字段清单

```
个人信息：姓名、身份证号、手机号、邮箱、住址、生日
金融：银行卡号、CVV、交易密码
认证：密码、token、session id、私钥、API key
生物：人脸、指纹、声纹
健康：诊断、病历
业务敏感：客户名单、合同金额、内部定价
```

**最容易被忽略的三个**：

1. `Authorization` 请求头（整条 token 直接进日志）。
2. 查询参数里的 token（`?access_token=xxx`）。
3. 异常堆栈里带的连接串（含数据库密码）。

### 三类脱敏方式

| 方式 | 做法 | 适用 |
| --- | --- | -- |
| 静态脱敏（Static） | 数据落地前就替换（用于测试库、数据导出） | 测试环境、数据共享 |
| 动态脱敏（Dynamic） | 查询时按权限实时遮蔽 | 生产查询、B 端后台 |
| 展示脱敏（Display） | 前端/日志输出时遮蔽 | 日志、页面展示 |

**测试环境必须静态脱敏**：直接用生产数据是等保/个保法的高风险项。

### 日志脱敏的四个落地位置

**① 应用层（最可靠）**

```python
SENSITIVE = {"password", "id_card", "phone", "card_no", "token"}

def mask(v):
    s = str(v)
    if len(s) <= 6: return "***"
    return s[:3] + "*" * (len(s) - 7) + s[-4:]

def scrub(obj):
    if isinstance(obj, dict):
        return {k: ("***" if k.lower() in SENSITIVE else scrub(v)) for k, v in obj.items()}
    if isinstance(obj, list):
        return [scrub(i) for i in obj]
    return obj
```

用结构化日志的统一入口做，**不要指望每个开发者记得**。

**② 网关/WAF 层**

在入口处就把敏感参数遮蔽（但要小心影响业务）。

**③ 采集层（Filebeat/Promtail）**

```yaml
# promtail 的正则替换
pipeline_stages:
- regex:
    expression: '(1[3-9]\d{9})'
- replace:
    expression: '(1[3-9]\d{9})'
    replace: '1**********'
```

**正则脱敏是最容易漏的**：格式一变（带空格、带 +86）就失效。

**④ 日志平台查询层**

对"谁能查什么"做权限控制（比脱敏更根本）。

### 密码与 token 绝对不落日志

```python
# 差
logger.info("login: %s/%s", user, password)

# 差 — 打印整个请求对象
logger.info("request: %s", req.__dict__)

# 好
logger.info("login attempt: user=%s", user)
```

**框架层的坑**：

- Django/Spring 的默认访问日志会记完整 URL（含 query 里的 token）。
- 异常处理器默认打印完整异常上下文（含请求体）。

要显式配置过滤。

### DLP 能做什么、不能做什么

| 能做 | 不能做 |
| --- | --- |
| 拦截外发邮件里的身份证号格式 | 拦住截图 |
| 阻断 U 盘拷贝 | 拦住手机拍照 |
| 记录外发行为（审计） | 判断"这个数据该不该发" |

**DLP 是"提高门槛"，不是"绝对防护"**。真正的防线是"最小必要"——**不该有的数据就不要采集**。

### 数据最小化：最有效的防护

```
① 不采集：不需要实名的地方不要身份证号
② 不存储：会话结束后就不需要的字段，别落库
③ 不展示：后台页面只显示后四位
④ 不外发：导出功能默认脱敏，需要明文走审批
```

四条里，**第①条最有效**：不存在的字段不会泄露。

### 一次处置过程（日志泄露身份证号）

**发现**：安全扫描在日志平台里搜到了明文身份证号（正则匹配 18 位）。

**处置**：

```
① 立即定位：哪个服务、哪些字段、涉及多少条
   （用日志平台查 json.id_card 存在且非空）
② 止血：应用层加脱敏 + 发布
③ 清理：删除历史日志中相关字段（重建索引或按保留期删除）
④ 评估：是否已外发（查外发记录、工单附件）
⑤ 加固：采集层加正则兜底 + 日志平台查询加权限
⑥ 复盘：为什么代码里没做脱敏（缺规范、缺 review 检查项）
```

**关键的"止血"顺序**：先停止新增泄露，再清理历史。

### 规范落地：三条可执行

```
① 代码规范：所有日志必须走统一 logger（禁止 print/console.log 直接输出对象）
② PR 检查项：日志里是否含敏感字段（写入 review checklist）
③ CI 扫描：grep 常见敏感字段名在日志语句里出现
```

CI 检查示例：

```bash
# 粗筛（会有误报，但能挡住大部分）
grep -rnE 'log(ger)?\.(info|debug|warn|error).*(password|id_card|card_no|token)' src/ \
  && { echo "发现疑似敏感字段日志"; exit 1; }
```

### 检查清单

```
□ 有敏感字段清单（并随业务更新）
□ 日志走统一入口，自动脱敏
□ 密码/token/连接串绝不落日志
□ 采集层有正则兜底
□ 日志平台按角色控制查询权限
□ 测试环境用静态脱敏数据（不用生产数据）
□ 导出功能默认脱敏
□ 有"不该采集的字段"评审机制
```
