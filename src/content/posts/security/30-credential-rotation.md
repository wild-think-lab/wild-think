### 为什么必须轮换

```
① 人员流动（离职者手里的凭据）
② 泄漏（日志/仓库/截图里出现过）
③ 合规（多数标准要求定期更换）
④ 攻击者长期潜伏（不换就永远有效）
```

**"设了 90 天到期"** 往往以"所有人 password123 改成 password124"收场。

### 四类凭据

```
① 静态密码（人用/服务用）
② API Key / Token（服务用）
③ 证书（双向认证/TLS）
④ 数据库/中间件账号
```

**"服务的密码"** 才是最难轮换的（一改就要重启）。

### 双凭据过渡（最实用的方法）

```
阶段 1：新增 B，A 仍然有效
阶段 2：所有客户端切到 B
阶段 3：确认 A 无调用（看日志/审计）
阶段 4：作废 A
```

**"直接改密码"** 会让所有客户端同时断（没有过渡窗口就没有安全）。

### 数据库账号轮换

```sql
-- 1) 建新账号（相同权限）
CREATE USER 'app_v2'@'%' IDENTIFIED BY '<new>';
GRANT SELECT,INSERT,UPDATE ON app.* TO 'app_v2'@'%';

-- 2) 应用侧切换（连接池支持多账号/灰度）

-- 3) 确认旧账号无连接
SELECT user, host, COUNT(*) FROM information_schema.processlist GROUP BY 1,2;

-- 4) 删除旧账号
DROP USER 'app_v1'@'%';
```

**"连接池"** 是最大障碍：改配置要重启，所以要"支持热更新或双账号"。

### 证书轮换（ACME / cert-manager）

```
① 短周期证书（90 天或更短）
② 自动续期（certbot / cert-manager）
③ 提前告警（剩余 14 天）
④ 有"续期失败"告警（最容易静默失败）
```

```bash
certbot renew --dry-run
kubectl get certificates -A
```

### 动态凭据（最省心的方向）

```
Vault 动态数据库凭据：每次连接生成短时账号（如 1 小时）
云上：IAM Role / STS 临时凭据（不用长期 AK/SK）
K8s：ServiceAccount Token 自动轮换（内置）
```

**"没有长期凭据"** = 不需要轮换（从根上解决）。

### 五个"想轮换不敢换"

**① 不知道谁在用**

```
没有调用审计 → 改了怕断
→ 先上审计（记录每个凭据的使用来源）
```

**② 配置散落各处**

```
每台机器一个配置文件，脚本里还有硬编码
→ 集中到配置中心/Vault
```

**③ 没有回滚**

```
改错了无法快速恢复
→ 保留旧凭据一段时间（双凭据）
```

**④ 一改就要全量重启**

```
无热加载 → 分批重启（先灰度）
```

**⑤ 轮换没有记录**

```
谁在什么时候换了什么 → 出问题查不到
→ 轮换要有工单与审计日志
```

### 一个可落地的一年计划

```
Q1：清点（所有凭据清单 + 使用方）
Q2：集中（迁到配置中心/Vault，去掉硬编码）
Q3：自动化（证书/Token 自动续期）
Q4：动态化（数据库/云凭据改短时）
```

### 检查清单

```
□ 有凭据清单（含使用方）
□ 无硬编码（代码/脚本/镜像）
□ 有双凭据过渡流程
□ 数据库账号支持双账号切换
□ 证书自动续期 + 到期告警
□ 云上用临时凭据（无长期 AK）
□ 轮换有记录（工单/审计）
□ 有"作废旧凭据"的确认步骤（看审计无调用）
□ 离职流程包含凭据回收
□ 有轮换演练（至少一次）
```
