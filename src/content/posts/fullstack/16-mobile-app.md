### 四种方案

| 方案 | 技术栈 | 适合 | 不适合 |
| --- | --- | --- | --- |
| 原生（Swift/Kotlin） | 各自语言 | 性能敏感、深度系统能力 | 双端人力成本高 |
| Flutter | Dart | 一致 UI、流畅动画、双端 | 包体较大、原生插件需适配 |
| React Native | JS/TS | 前端团队转型、生态成熟 | 复杂动画/极致性能 |
| uni-app / 小程序 | Vue | 国内多端（小程序+H5+App） | 重度原生能力、复杂交互 |

**关键判断**：

```
① 需要"上架小程序 + H5 + App 三端" → uni-app 优势最大
② 需要"一致的高质量 UI 与动画" → Flutter
③ 已有前端团队、想复用 React → RN
④ 深度系统能力（蓝牙/相机/后台服务）→ 原生 or 混合
```

### 跨端方案的三个隐性成本

**① 原生插件适配**

```
每个"系统能力"（推送、支付、地图、BLE）都要过一次桥
→ 出问题时你要同时懂两端
```

**② 包体与启动**

```
Flutter 基础包体 +10–20MB
RN 需要 JS 引擎
→ 对"低端机 + 弱网"用户不友好
```

**③ 热更新合规**

```
iOS 不允许"改变功能的热更新"
→ 跨端方案的"热更新"在 iOS 上受限（只能修 bug 类）
```

**"以为能随时热更新"是最常见的期待错位**。

### Flutter 的几个实用点

**状态管理**：

```
简单项目：Provider / Riverpod
复杂项目：Riverpod + 分层（data/domain/ui）
```

**列表性能**：

```dart
ListView.builder(
  itemCount: items.length,
  itemBuilder: (c, i) => ItemTile(items[i]),
)
```

**"用 Column 塞 500 个 Item"** 会直接卡死（必须用 builder）。

**包体优化**：

```bash
flutter build apk --split-per-abi
flutter build appbundle
```

**"split-per-abi"** 能显著减小单包体积。

### uni-app 的几个实用点

```
① 条件编译（#ifdef APP-PLUS / MP-WEIXIN）处理多端差异
② 不要在小程序里用"App 专属 API"
③ 分包（小程序有 2MB 主包限制）
```

**"小程序主包超 2MB"是上线最常见的阻塞**。

### 五个"选了跨端又后悔"的原因

**① 团队没有对应语言经验**

```
选 Flutter 但没人会 Dart → 学习成本被低估
```

**② 低估了"原生能力"的量**

```
需求里 20% 是"深度系统功能" → 跨端方案全卡住
```

**③ 只算开发成本，不算维护**

```
两套代码变一套，但"插件升级/平台政策变化"仍需持续投入
```

**④ 性能预期不现实**

```
"跨端也能 60fps" → 复杂列表/动画仍然掉帧
```

**⑤ 上线流程不熟**

```
iOS 审核、隐私清单、隐私政策、权限说明 —— 都是坑
```

### 混合方案（现实中最常见）

```
主流程用跨端（列表/详情/表单）
少数重功能用原生模块（相机/地图/音视频）
```

**"全跨端"与"全原生"都少见，混合才是常态**。

### 上线前必查（国内）

```
① 隐私政策 + 权限申请说明（首次启动）
② SDK 合规（不要"未告知就采集"）
③ 应用备案/软著（安卓渠道要求）
④ 加固（防反编译，安卓）
⑤ 崩溃采集（Firebase/Sentry/Bugly）
```

**"隐私合规"是当前被拒/下架的第一原因**。

### 检查清单

```
□ 明确"要多端还是要性能"
□ 团队语言栈匹配
□ 评估原生能力占比（>20% 慎选跨端）
□ 包体预算（安装包/首启）
□ 有崩溃采集与灰度
□ 有热更新合规方案
□ 小程序分包规划（如适用）
□ 隐私合规（政策/权限/SDK）
□ 有真机测试矩阵（低端机必测）
□ 有发布流程（渠道/审核/回滚）
```
