### 为什么现在要认真考虑

```
① 公网 IPv4 短缺（云上买 IP 越来越贵）
② 移动网络已大规模 IPv6 优先
③ 部分应用商店/合规要求支持 IPv6
④ 万物互联（IoT）地址需求
```

**但"能解析 AAAA"和"真的能用"差很远**。

### 地址规划

```
/64 是"标准子网"（一个子网就该是 /64）
运营商通常给 /56 或 /48（可切 256 或 65536 个 /64）
内部规划：按站点/机房分 /48，按网段分 /64
```

**"用 /120 做子网"是错误的**：

```
/64 之后的部分是"接口标识"（通常 64 位）
用更小的子网会破坏 SLAAC 与隐私地址
```

**地址书写**：

```
2001:db8::/32      缩写（连续的 0 可省）
fe80::/10          链路本地（每个接口都有）
::1                回环（等价 127.0.0.1）
```

### 双栈（最现实的过渡方案）

```
同一接口同时配 IPv4 与 IPv6
应用优先用 IPv6（Happy Eyeballs 会并行尝试）
```

**"Happy Eyeballs"是什么**：

```
客户端同时尝试 A 与 AAAA，谁先通用谁
→ 所以"IPv6 不通但 IPv4 通"时，用户体验可能还行（但有延迟）
```

**风险**：

```
IPv6 路径"半通"（能连但很慢/丢包）→ 每次请求都先等 IPv6 超时
→ 用户感觉"网站变慢了"
```

**这是"上线 IPv6 后变慢"最常见的原因**。

### 三种地址配置方式

**① SLAAC（无状态自动配置）**

```
路由器发 RA（Router Advertisement），客户端自己生成地址
```

**② DHCPv6**

```
类似 DHCPv4，但"默认网关"仍必须由 RA 提供
```

**③ 静态**

```
手工配（服务器场景常见）
```

**常见组合**：

```
客户端：SLAAC（+ DHCPv6 拿 DNS）
服务器：静态（可控、可审计）
```

**"只开 DHCPv6 不开 RA"是错误配置**：

```
IPv6 的网关只能从 RA 来
→ 没有 RA 就没有默认路由 → 上不了网
```

### NAT 的消失意味着什么

```
IPv4：NAT 让外部无法主动访问内部
IPv6：地址全球可达（没有 NAT 这一层"天然防火墙"）
```

**这是最重要的安全变化**：

```
① 内部服务如果监听 0.0.0.0 且防火墙没配 → 直接暴露公网
② 扫描器会扫全网的 IPv6（地址空间大但也会被针对性扫）
```

**必须做的**：

```
① 主机防火墙（nftables/iptables）默认拒绝入站
② 只放行必要端口
③ 不要"依赖 NAT 提供安全"
```

**"上 IPv6 后被攻破"基本都是这个原因**。

### 五个"以为能用其实不通"的原因

**① 只解析了 AAAA，没配路由**

```
dig AAAA 有结果 → 但服务器没有 IPv6 出口 → 连不上
```

**② 防火墙只放行了 IPv4**

```
iptables 规则只写了 -4
→ IPv6 走 nftables/ip6tables 的默认策略（可能全拒或全通）
```

**检查**：

```bash
ip6tables -L -n
nft list ruleset
```

**③ MTU 与 PMTUD 黑洞**

```
IPv6 不允许中间设备分片（只能由源端分片）
如果 ICMPv6 "Packet Too Big" 被防火墙拦 → 大包永远发不出去
```

**现象**：

```
ping 通（小包），但 HTTPS 卡住（大包）
```

**修法**：

```
① 放行 ICMPv6（type 1/2/3/4 至少要放）
② 或把接口 MTU 调到路径最小值（1500 → 1480/1400）
```

**"必须放行 ICMPv6"** 是 IPv6 与 IPv4 最大的运维差异。

**④ DNS 返回了错误的 AAAA**

```
配了 AAAA 但指向的地址不可达（或指向了错误的主机）
→ 客户端优先用 AAAA → 超时
```

**⑤ 应用/中间件不支持**

```
① 老代码绑定 IPv4 only（inet_addr）
② 日志/审计系统只解析 IPv4（显示为 ::ffff:1.2.3.4）
③ 限流/WAF 规则只按 IPv4 写
```

### 排障命令

```bash
# 地址与路由
ip -6 addr
ip -6 route
ip -6 route show default

# 邻居
ip -6 neigh

# 连通（注意 -6）
ping6 2001:db8::1
curl -6 -sI https://example.com

# 路径 MTU
tracepath6 example.com

# DNS
dig AAAA example.com
dig +short AAAA example.com

# 确认服务监听
ss -6 -lntp
```

**`curl -6`** 是验证"应用是否真的走 IPv6"的最快方法。

### 双栈服务端的注意点

```
① 监听 :: 通常同时接受 IPv4（v4-mapped）
② 如果只监听 0.0.0.0，某些系统上不接受 IPv6
③ 日志里的客户端 IP 可能是 ::ffff:1.2.3.4（需要归一化）
④ 访问控制列表要同时包含两类地址
```

**"监听地址写错导致 IPv6 不通"** 是最常见的应用侧问题。

### 一个务实的推进顺序

```
① 内部基础设施先支持（DNS、监控、日志能解析 IPv6）
② 边界设备双栈（LB/防火墙/入口）
③ 对外服务开 AAAA（先在低流量域名试）
④ 内部服务逐步开（先非关键）
⑤ 老应用不改（用 NAT64/DNS64 或代理）
```

**"一次性全切"是最危险的做法**。

### 检查清单

```
□ 子网用 /64（不破坏 SLAAC）
□ 服务器用静态地址（可控）
□ 有 RA（否则没有默认网关）
□ 主机防火墙默认拒绝（不依赖 NAT）
□ 放行必需 ICMPv6（PMTUD 依赖）
□ 检查路径 MTU（大包能否通）
□ DNS 的 AAAA 只指向可达地址
□ 应用监听地址正确（含 IPv6）
□ 日志/风控能处理 ::ffff: 形式
□ 用 curl -6 验证真实可用
□ 按"内部 → 边界 → 对外 → 内部业务"推进
```
