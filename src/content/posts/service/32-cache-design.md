### 三种模式

```
① Cache-Aside（旁路）：读缓存，miss 查库回填（最常用）
② Read-Through：缓存层自己回源
③ Write-Through / Write-Behind：写时同步/异步更新缓存
```

**"大多数业务"用 Cache-Aside 就够**。

### 该缓存什么

```
适合：读多写少、可容忍短暂不一致、计算贵
不适合：强一致（余额）、个性化极强（每人不同）、超大对象
```

**"什么都能缓存"** 会导致"内存被冷数据占满，热数据反而 miss"。

**判据**：

```
访问频次（热点） + 重算成本（贵）+ 时效容忍度（可旧）
```

### key 设计

```
① 稳定（同一逻辑对象 → 同一 key）
② 带版本（schema 变更时可整体失效）
③ 避免"高基数+无意义"（如把 request_id 当 key）
```

```
user:profile:v2:1001
```

**"key 带版本"** 让"改结构"不用逐条删。

### 过期设计

```
① 固定 TTL：简单，但"同一时刻集中失效"（雪崩）
② TTL + 随机抖动：打散失效时间（推荐）
③ 逻辑过期（不真删，后台刷新）：保证可用性
```

```python
ttl = base + random.randint(0, base // 10)
```

**"TTL 全部 300s"** → 300 秒后一起回源，打爆数据库。

### 一致性策略

```
① 先更新库 → 再删缓存（最常用）
② 延迟双删（应对并发读写窗口）
③ 订阅 binlog 删缓存（最可靠）
④ 短 TTL 兜底（最终一致）
```

**"更新缓存而不是删"** 的问题：

```
并发写时写入顺序错乱 → 缓存里留旧值（且没人纠正）
```

### 五个"加了缓存 QPS 没降"

**① 命中率太低**

```
看 hit ratio：< 80% 说明 key/TTL/热点判断有问题
```

**② 缓存的是"非热点"**

```
把 90% 的容量给了 10% 的长尾数据
```

**③ 每次请求 key 都不同**

```
key 里带了时间戳/随机数 → 永远 miss
```

**④ 序列化开销大于查询**

```
缓存大对象 + JSON 解析 → 比查库还慢
```

**⑤ 缓存层本身成瓶颈**

```
单实例 Redis + 大 value → 网络/CPU 打满
```

**"看命中率与延迟分布"** 才能知道缓存是否真有用。

### 三个"必须防"的问题

```
① 穿透：查不存在的数据 → 每次都打库
   → 缓存空值（短 TTL）+ 布隆过滤器
② 击穿：热点 key 失效瞬间 → 大量并发回源
   → 互斥锁/单飞（singleflight）
③ 雪崩：大量 key 同时失效 → 库被打爆
   → TTL 抖动 + 多级缓存 + 降级
```

（三种失效模式的细节见另文《缓存穿透/击穿/雪崩》）

### 多级缓存

```
本地缓存（进程内）→ 分布式缓存（Redis）→ DB
```

**要点**：

```
① 本地缓存要短 TTL（否则多实例不一致）
② 本地缓存适合"极热且变化少"的配置
```

**"本地缓存 1 小时"** → 改配置后部分实例还是旧值。

### 缓存与"业务正确性"

```
① 缓存不能成为"唯一数据源"
② 关键操作（支付/扣库存）不要"只改缓存"
③ 缓存故障要有降级（直查库 + 限流）
```

**"Redis 挂了业务全挂"** = 把缓存当成了依赖。

### 检查清单

```
□ 明确缓存对象（热点 + 贵 + 可旧）
□ key 稳定且带版本
□ TTL 有抖动
□ 一致性问题用"删缓存 + 兜底 TTL"
□ 缓存空值防穿透
□ 热点 key 防击穿（单飞）
□ TTL 抖动防雪崩
□ 有命中率与延迟监控
□ 缓存故障有降级方案
□ 关键业务不依赖缓存正确性
□ 大 value 有压缩与拆分
```
