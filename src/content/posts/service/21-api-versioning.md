### 为什么难

```
API 一旦对外发布，就有你控制不了的客户端
App 在用户手机里，不会因为你升级后端就更新
```

**"改个字段名"在内部是小事，对外是事故**。

### 什么算破坏性变更

**破坏性（必须新版本或兼容期）**：

```
① 删除字段
② 改字段名
③ 改字段类型（int → string）
④ 改语义（amount 从"元"改成"分"）
⑤ 收紧校验（原来可选，现在必填）
⑥ 改状态码含义
⑦ 改默认排序
⑧ 删除或改路径
```

**非破坏性（可以直接发）**：

```
① 新增可选字段（客户端忽略未知字段即可）
② 新增接口
③ 新增枚举值（注意！客户端可能没处理未知值 → 见下）
④ 放宽校验
```

**"新增枚举值"是个坑**：如果客户端用 `switch` 处理返回值且没有 default，新增值会导致崩溃或异常。

**对策**：发布前确认客户端都按"未知值容错"设计，或只在旧值基础上扩展（不谈新值）。

### 四种版本策略

| 策略 | 例子 | 优点 | 缺点 |
| --- | --- | --- | --- |
| URL 路径 | `/v1/users` | 清晰、易调试 | 路径变长、需要路由 |
| Header | `Accept: vnd.api.v2+json` | 路径干净 | 不方便手测 |
| 查询参数 | `/users?version=2` | 灵活 | 容易被漏掉 |
| 无版本（仅演进） | `/users` | 简单 | 依赖"只做兼容变更" |

**推荐：URL 路径**（最实用）：

```
/v1/users        → 老版本
/v2/users        → 新版本
```

**理由**：

```
① 网关/LB 能按路径路由
② 日志里一眼看出是哪个版本
③ 手测方便（curl 直接打）
```

### 什么该新版本，什么该兼容

**判断**：

```
破坏性 + 影响大量客户端 → 新版本（/v2）
破坏性 + 只影响少量/内部 → 兼容期（双字段并存）
非破坏性 → 直接发
```

**"字段双写"的兼容方案**：

```json
{
  "user_name": "alice",     // 旧字段（保留 6 个月）
  "userName": "alice"       // 新字段
}
```

**代价**：响应变大、逻辑冗余。但**比"客户端崩溃"便宜**。

### 兼容期怎么定

```
① 内部服务：2 周（有统一部署能力）
② 内部客户端（可控）：1–3 个月
③ 开放 API：6–12 个月（按合同/公告）
④ 移动 App：按"用户更新率"倒推
   （如果 6 个月后仍有 5% 用户在用旧版本 → 不能下）
```

**移动 App 的现实**：

```
App 的旧版本可能存活 1–2 年（用户不更新、应用商店缓存）
→ 后端要长期兼容多个版本
```

**"App 版本号"的实践**：

```
响应里带 api_version，客户端上报自己的版本
→ 服务端可以统计"哪些版本还在用"
→ 只有占比 < 0.5% 才下线
```

### 如何优雅下线旧版本

```
① 提前公告（邮件/控制台横幅/文档）
② 加"弃用标记"（响应头）：
   Deprecation: true
   Sunset: Sat, 01 Aug 2026 00:00:00 GMT
   Link: <https://api.example.com/docs/v2>; rel="successor-version"
③ 灰度：先对 1% 的请求返回 410/错误提示
④ 监控旧版本的调用量（降到阈值再关）
⑤ 关闭后保留 30 天的"重定向/提示"
```

**`Sunset` 头是 RFC 8594 标准**，用它比"在文档里写一句"专业得多。

### 让"少改版本"成为可能的两个设计

**① 让客户端容错**

```
文档里明确：客户端必须忽略未知字段、必须处理未知枚举值
```

**② 用"扩展点"设计**

```json
{
  "id": 1,
  "attributes": { ... },        // 业务字段
  "meta": { ... }               // 扩展字段（新功能放这里）
}
```

**或者用"选项对象"**：

```json
{
  "id": 1,
  "name": "x",
  "options": {
    "newFeature": true
  }
}
```

**好处**：新增字段永远在"已知的容器"里，客户端容易容错。

### 一次"改字段名"引发的事故

**改动**：把 `create_time` 改成 `created_at`（统一命名规范）。

**结果**：

```
① 内部管理后台挂了（读 create_time）
② 一个第三方合作方报"数据为空"
③ 报表脚本算出 0
```

**根因**：

```
① 以为"内部服务改一下部署就行"
② 没有搜全代码（有一个老脚本没人维护）
③ 第三方没有通知流程
```

**改进**：

```
① 破坏性变更必须"双字段并存"至少一个发布周期
② 有"字段使用清单"（哪个系统读了哪些字段）
③ 第三方变更走通知流程
```

**"内部服务就能随便改"是常见错觉**：内部系统一样会挂。

### 文档与契约

```
① OpenAPI 规范（自动生成文档 + 生成客户端 SDK）
② 契约测试（CI 里验证"响应结构没变"）
③ 变更日志（哪些版本改了什么）
```

**契约测试的例子**：

```python
def test_user_response_schema():
    resp = client.get("/v1/users/1")
    data = resp.json()
    assert set(data.keys()) >= {"id", "name", "create_time"}   # 关键字段必须存在
    assert isinstance(data["id"], int)
```

**这个测试能挡住"删字段/改类型"**，成本很低。

### 检查清单

```
□ 明确"破坏性变更"清单
□ 版本策略统一（推荐 URL 路径 /v1）
□ 破坏性变更用"双字段并存"过渡
□ 兼容期按客户端类型定（App 更长）
□ 下线走：公告 → Deprecation/Sunset 头 → 灰度 → 监控 → 关闭
□ 文档要求客户端忽略未知字段
□ 有 OpenAPI + 契约测试
□ 内部服务也按对外标准做变更
□ 有"字段使用清单"
```
