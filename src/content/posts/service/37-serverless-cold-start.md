把接口搬到按需扩缩的运行时之后，最常见的一句反馈是"平时挺快，偶尔特别慢"。偶尔的那次就是冷启动。它不是一个数，而是四段叠加。

## 四段拆解

```
① 调度/拉起（几毫秒到几百毫秒）
② 镜像拉取（几十毫秒到几秒，取决于镜像大小与节点缓存）
③ 运行时初始化（JVM/Node/Python 解释器与框架加载）
④ 应用初始化（连数据库、加载配置、预热缓存、DNS 首查）
```

测量方法：在应用里打出"进程启动到首个请求处理完成"的时间戳，同时在平台侧记录"请求到达 → 实例就绪"的时长。两段相减，就是平台开销。

```python
# 应用侧打点
import time, os
T0 = time.time()
# ... 初始化 ...
print(f"boot_ms={int((time.time()-T0)*1000)}", flush=True)
```

**判据**：只看端到端 P99 无法定位，必须拆成"平台段 / 应用段"。

## 各段的典型量级（经验区间，需自测）

| 段 | 小镜像 + 轻运行时 | 大镜像 + 重运行时 |
| --- | --- | --- |
| 镜像拉取（节点无缓存） | 0.2-1s | 2-10s |
| 运行时初始化 | 50-300ms | 1-5s（JVM/大框架） |
| 应用初始化 | 100-500ms | 1-3s（连接池/ORM/缓存预热） |
| 合计（首次） | 0.5-2s | 3-15s |

数字随环境差异很大，别抄别人的结论，按上面的方法量自己的。

## 削减手段（按性价比排序）

**① 保留最小副本**

```yaml
# Knative
spec:
  template:
    metadata:
      annotations:
        autoscaling.knative.dev/minScale: "1"
```

代价：常驻资源。判据：核心接口且延迟敏感，就值得。

**② 缩容延迟拉长**

```yaml
        autoscaling.knative.dev/scaleDownDelay: "15m"
```

流量有波峰波谷时，比一直保留副本便宜。

**③ 镜像瘦身**

```
多阶段构建 + distroless/slim，把 800MB 压到 100MB 以内
镜像层减少 → 拉取时间下降最明显
```

**④ 应用启动减负**

```
懒加载非关键模块（日志后端、管理端路由）
连接池最小连接数设 1-2，别在启动时建 20 条
DNS 用固定 IP 或预热
```

**⑤ 预热而不是等请求**

```
启动完成后主动打一次内部健康检查/查询，把 JIT/缓存/连接热起来
```

## 五个常见误判

**① 把"扩缩容"当成"冷启动"**

扩容新实例也有启动成本，但和从 0 到 1 不是一回事，分开看。

**② 用平均值评估**

冷启动是尾部问题，只看 P50 永远看不到。

**③ 忽略节点缓存**

同一节点上跑过的镜像，第二次起是"半冷"；多节点调度会让结果看起来随机。

**④ 忽略依赖预热**

数据库连接池首次建连、TLS 握手、DNS 首查都算在"第一次"里。

**⑤ 为了冷启动把并发调到很高**

瞬间拉起几十个实例，反而拉长每个实例的就绪时间（节点资源争抢）。

## 什么时候不该用

```
P99 要求 < 100ms
流量密集（几乎不需要缩到 0）
状态重（每实例都要暖大量缓存）
```

这三类场景，常驻副本或传统部署更划算。

## 检查清单

```
□ 有"平台段/应用段"分开的耗时打点
□ 镜像 < 100MB（或已压到最小可用）
□ 核心接口有 minScale=1
□ 非核心用缩容延迟而不是常驻
□ 启动时不做重初始化（连接池/预热延后）
□ 有 P99 与冷启动次数监控
□ 扩容并发有上限
□ 依赖预热（DNS/TLS/DB）
□ 压测覆盖"缩到 0 后首个请求"
□ 明确知道哪些场景不该 Serverless
```
