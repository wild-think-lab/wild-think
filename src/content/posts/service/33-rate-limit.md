### 四种算法

```
① 固定窗口：简单，但边界会"双倍突发"
② 滑动窗口：更平滑（内存略高）
③ 漏桶：恒定速率（适合"保护下游"）
④ 令牌桶：允许突发（最适合 API）
```

**"固定窗口计数"** 在窗口边界能放过 2 倍流量（这点常被忽略）。

### 令牌桶的实现要点

```lua
-- Redis + Lua 原子操作
local key = KEYS[1]
local rate = tonumber(ARGV[1])      -- 每秒令牌
local burst = tonumber(ARGV[2])     -- 桶容量
local now = tonumber(ARGV[3])
local data = redis.call("HMGET", key, "tokens", "ts")
local tokens = tonumber(data[1]) or burst
local ts = tonumber(data[2]) or now
tokens = math.min(burst, tokens + (now - ts) * rate)
if tokens < 1 then return 0 end
redis.call("HMSET", key, "tokens", tokens - 1, "ts", now)
return 1
```

**"先 get 再 set"** 在并发下会超发（必须原子）。

### 限流的三个维度

```
① 按 IP（防刷）
② 按用户/租户（公平）
③ 按接口（保护特定资源）
```

**"只按 IP"** 在 NAT 环境下会误伤（整栋楼一个出口）。

### 放在哪一层

```
① 网关/入口（全局保护）
② 应用内（按业务语义）
③ 下游客户端（保护依赖）
```

**"只在应用内限流"** → 请求已经打进来了（连接/带宽已被占）。

### 返回什么

```
429 Too Many Requests
Retry-After: 3
```

**"直接 502/超时"** 会让客户端疯狂重试（雪上加霜）。

### 熔断（比限流更狠的一招）

```
状态：Closed → Open（失败率超阈值，直接拒绝）
      → Half-Open（放少量试探）
      → Closed（恢复）
```

```
判据（示例）：
  10 秒内失败率 > 50% 且请求数 > 20 → Open
  Open 30 秒后 → Half-Open 放 5 个请求
```

**"熔断后直接拒绝"** 比"每个请求都超时 30 秒"好得多（省资源）。

### 隔离舱（Bulkhead）

```
每个依赖一个独立线程池/信号量
A 依赖慢 → 只占满 A 的池子，不影响 B
```

**"共享一个池子"** → 一个慢依赖拖垮全部。

### 五个"加了限流还是挂了"

**① 限流在下游，入口没限**

```
连接数已打满 → 限流没意义
```

**② 限流阈值远高于容量**

```
设 10000 QPS 但系统只能扛 2000
```

**③ 重试放大**

```
客户端自动重试 + 无限流 → 流量 ×3
```

**④ 只限了读，没限写**

```
写请求打满数据库
```

**⑤ 限流后没降级**

```
直接 429 → 用户流失；应该有"排队/缓存/简化返回"
```

### 一个"分层"的保护方案

```
入口网关：IP/租户 QPS 上限 + 连接数上限
应用：按接口限流 + 隔离舱 + 熔断
下游：连接池上限 + 超时 + 重试预算（有限）
业务：降级开关（关掉非核心功能）
```

### 检查清单

```
□ 入口有限流（不只是应用内）
□ 算法与场景匹配（令牌桶/漏桶）
□ 计数原子（Redis Lua）
□ 维度合理（不只按 IP）
□ 返回 429 + Retry-After
□ 有熔断（失败率 + 半开）
□ 每个依赖有独立隔离舱
□ 客户端重试有退避与上限
□ 有限流后的降级策略
□ 有限流命中率与拒绝量监控
□ 阈值基于压测（不是拍脑袋）
```
