### 为什么必须幂等

```
① 网络不可靠（超时不代表失败，可能已成功）
② 客户端会重试（用户点了两次、SDK 自动重试）
③ 消息队列至少一次（必然重复投递）
④ 定时任务可能重复触发
```

**"不幂等的写接口"必然在某个时刻产生重复数据**。

### 五种实现方式

**① 唯一约束（最可靠）**

```sql
CREATE TABLE orders (
  id BIGINT PRIMARY KEY,
  request_id VARCHAR(64) NOT NULL,
  UNIQUE KEY uk_request (request_id)
);
```

```sql
INSERT INTO orders (...) VALUES (...);
-- 冲突 → 说明重复 → 返回已存在的结果
```

**优点**：数据库保证，绝不失效。
**缺点**：需要在业务表里加字段。

**② 去重表（独立表）**

```sql
CREATE TABLE idempotency (
  key VARCHAR(128) PRIMARY KEY,
  status TINYINT,           -- 0 处理中 / 1 成功 / 2 失败
  result TEXT,
  created_at DATETIME
);
```

**流程**：

```
1. INSERT key（唯一键冲突 → 说明已存在）
2. 若存在：status=成功 → 返回缓存结果
          status=处理中 → 返回"处理中"或等待
3. 处理完成后更新 status 与 result
```

**"处理中"状态很重要**：

```
否则并发请求会同时开始处理（都以为是第一次）
```

**③ 状态机（业务天然幂等）**

```
订单状态：待支付 → 已支付 → 已发货 → 已完成
"支付成功"事件重复到达时：
  当前是"待支付" → 推进到"已支付"
  当前已是"已支付" → 忽略（幂等）
  当前是"已取消" → 拒绝/人工介入
```

**状态机的幂等性是"业务层的"**，最强也最难设计。

**④ Redis SETNX（快速去重）**

```python
if redis.set(f"idem:{key}", "1", nx=True, ex=3600):
    do_business()
else:
    return cached_result()
```

**优点**：快。
**缺点**：Redis 丢数据/主从切换可能失效（不能作为唯一保障）。

**⑤ 版本号/乐观锁**

```sql
UPDATE account SET balance = balance - 100, version = version + 1
WHERE id = 1 AND version = 3;
```

**适合"更新"类操作**：

```
影响行数 0 → 说明别人先改了 → 重读重试（或拒绝）
```

### 幂等键怎么生成

**客户端提供（推荐）**：

```
客户端生成 UUID，放在请求头 Idempotency-Key
→ 服务端只需"记住这个 key 的结果"
```

**为什么客户端生成更好**：

```
① 服务端不需要"猜"两次请求是不是同一个意图
② 跨请求（用户重试）也有效
```

**服务端生成（有限场景）**：

```
用"业务字段组合"（user_id + 商品 + 时间窗）
→ 但"时间窗"边界容易出错（23:59:59 与 00:00:01 算不算同一次）
```

**"用业务参数哈希当幂等键"的风险**：

```
参数里含时间戳/随机数 → 每次哈希都不同 → 幂等失效
```

### 重复请求怎么返回

```
① 已成功 → 返回缓存的原结果（相同的响应体）
② 处理中 → 返回 409 或"处理中，请稍后查询"
③ 已失败 → 可以允许重试（但要明确语义）
```

**"返回缓存的原结果"很重要**：

```
客户端重试时期望"同一结果"，而不是"一个新的 ID"
```

**"重试返回了不同的 ID"会让客户端重复下单/重复扣款**。

### 五个"看着幂等其实不幂等"的陷阱

**① 自增 ID 作为去重键**

```
每次重试都生成新 ID → 永远"不重复"
```

**② 时间戳参与键**

```
now() 每次都不同 → 键每次都不同
```

**③ "先查再插"**

```python
if not exists(key):     # 两个请求同时通过
    insert(key)         # 都插入 → 重复
```

**必须用"唯一约束 + 捕获冲突"，而不是"先查再插"**。

**④ 只对"主表"幂等，忘了副表**

```
主表有唯一键，但"明细表/流水表/消息发送"重复了
```

**⑤ 幂等只覆盖"同一秒"**

```
Redis key 过期后重试 → 又"第一次"了
→ 过期时间要覆盖"业务重试窗口"（可能几小时甚至几天）
```

### 一个"通用"的幂等中间件思路

```
请求进入 → 取 Idempotency-Key
  → 有 Key：
      Redis/DB 查 → 存在则返回缓存结果或"处理中"
                  → 不存在则占位（SETNX/唯一键）后处理
  → 无 Key：按业务字段生成（或直接处理，风险自负）
```

**要点**：

```
① 占位与处理在同一事务/同一 key 生命周期内
② 处理失败要"释放占位"或标记失败（允许重试）
③ 成功结果要能缓存（含响应码与响应体）
```

### 幂等与"恰好一次"

```
真正"恰好一次"需要"消费端去重 + 处理与提交在同一个事务"
```

**现实做法**：

```
至少一次 + 消费端幂等 = 事实上的恰好一次
```

**"非要做到恰好一次"通常成本极高**。

### 检查清单

```
□ 所有写接口评估过幂等
□ 优先用唯一约束（数据库保证）
□ 客户端提供 Idempotency-Key
□ 有"处理中"状态（防并发重复）
□ 重复请求返回原结果（不是新结果）
□ 幂等键覆盖业务重试窗口
□ 不用"先查再插"
□ 副表/消息也有幂等
□ 失败时可重试（语义清晰）
□ 不依赖单一 Redis（作为加速而非唯一保障）
```
