### 四种"发现"方式

```
① 配置文件（写死地址）—— 最简单，最脆
② DNS（系统自带）—— 通用，但缓存/更新慢
③ 注册中心（Consul/Nacos/Eureka）—— 动态，功能多
④ K8s Service —— 集群内天然有
```

**"微服务就必须上注册中心"** 是个误解。

### 什么时候真的需要注册中心

```
① 实例动态变化（弹性扩缩容频繁）
② 需要"健康检查 + 自动摘除"
③ 需要"配置中心 + 服务列表"统一
④ 非 K8s 环境、多语言栈
```

**如果已经在 K8s 里、服务通过 Service 访问** → 通常不需要再上 Consul。

### DNS 的边界

```
优点：所有语言都支持、零依赖
缺点：TTL 缓存（改地址要等）、无健康检查
```

**"DNS 轮询做负载均衡"** 的问题：

```
① 客户端缓存 → 摘除的实例仍被访问
② 无健康感知 → 挂了的实例仍在列表
```

**"短 TTL + 优雅下线"** 能缓解，但不是银弹。

### Consul 的定位

```
① 服务注册与发现（HTTP/DNS 接口）
② 健康检查（脚本/TTL）
③ KV 存储（配置）
④ 多数据中心
```

**适合**：

```
非 K8s、多机房、需要"服务目录"
```

**成本**：

```
要维护一个集群（Raft）+ 客户端接入
```

### Nacos 的定位

```
① 注册中心 + 配置中心（国内生态好）
② 支持"命名空间/分组/权重"
③ 与 Spring Cloud 集成成熟
```

**适合**：

```
Java 技术栈、需要"配置热更新"
```

**注意**：

```
Nacos 的"配置中心"能力常被过度使用 → 变成"全局变量仓库"
```

### K8s Service 的定位

```
集群内：Service（ClusterIP）+ CoreDNS
→ 已经是"服务发现"
```

**跨集群/跨机房**：

```
需要额外方案（DNS 跨集群、或网关统一入口）
```

**"K8s 里再叠一层 Consul"** 通常是无用复杂度。

### 五个"上了注册中心反而更乱"

**① 两套发现并存**

```
有的走 DNS，有的走注册中心 → 排障时要查两处
```

**② 注册信息不准确**

```
实例下线没注销 → 注册中心里全是"僵尸实例"
→ 必须有 TTL + 主动注销
```

**③ 客户端缓存**

```
SDK 缓存了实例列表 → 变更后不刷新 → 仍打旧实例
```

**④ 注册中心本身成了单点**

```
注册中心挂了 → 所有服务无法发现 → 全站故障
→ 必须高可用 + 客户端本地缓存兜底
```

**⑤ 把"配置管理"塞进注册中心**

```
几千个配置项 → 每次变更都是"全量推送" → 风险巨大
```

### 一个"最小可用"的组合

```
① 集群内：K8s Service + CoreDNS
② 集群外/多机房：统一入口网关（服务名 → 网关路由）
③ 健康检查：由网关/探针做，不依赖注册中心
④ 配置：配置中心（独立于服务发现）
```

**"用网关做统一入口"** 比"每个服务自己发现"更可控。

### 检查清单

```
□ 明确是否真的需要注册中心
□ 只有一套发现机制（不并存）
□ 有 TTL + 主动注销（防僵尸实例）
□ 客户端有缓存刷新策略
□ 注册中心高可用
□ 客户端有"本地兜底列表"
□ 配置中心与服务发现分离
□ 有"实例列表"可观测（当前有哪些、健康否）
□ 迁移时有双读过渡
```
