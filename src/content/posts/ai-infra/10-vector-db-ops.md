### 四种选择

| 方案 | 特点 | 适用 |
| --- | --- | --- |
| Milvus | 独立服务、功能全、可水平扩展 | 百万级以上、需要独立运维 |
| Qdrant | Rust 实现、过滤能力强 | 中等规模、需要复杂过滤 |
| pgvector | 就在 PostgreSQL 里 | 已有 PG、规模 < 千万 |
| Elasticsearch/OpenSearch | 已有 ES 集群可复用 | 已在用 ES、混合检索 |

**判断**：

```
已有 PG 且数据量不大 → pgvector（最省运维）
要复杂元数据过滤 → Qdrant
百万级以上 → Milvus
已有 ES 做全文检索 → 用 ES 的向量字段做混合检索
```

### 索引类型与召回率

**HNSW**（最常用）：

```
参数：
  M              每个节点的连接数（越大越准，内存越多）
  ef_construction 建索引时的候选数（越大越准，建索引越慢）
  ef_search      查询时的候选数（越大越准，查询越慢）
```

**IVF**（倒排文件）：

```
参数：
  nlist    聚类数（越大越快但越不准）
  nprobe   查询时探测的聚类数（越大越准越慢）
```

**取舍**：

| | HNSW | IVF |
| --- | --- | --- |
| 召回率 | 高 | 中（需要调 nprobe） |
| 内存 | 高（索引全在内存） | 低 |
| 建索引速度 | 慢 | 快 |
| 增量更新 | 好 | 差（要重训） |

**默认建议**：HNSW + `M=16`、`ef_construction=200`、`ef_search=64`，再按实测调。

### 维度与模型

```
维度越高：精度可能更高，但内存与计算成本成倍增长

常见维度：
  768   （bert-base、部分 embedding 模型）
  1024  （bge-large、多数中文模型）
  1536  （OpenAI text-embedding-3-small）
  3072  （text-embedding-3-large）
```

**关键原则：入库与查询必须用同一个模型**。换了模型必须全量重建索引，否则召回会崩。

### 分片与容量规划

```
内存估算（HNSW）：
  向量数据 = 条数 × 维度 × 4 字节（float32）
  加上索引开销约 1.5–2 倍

例：100 万条 × 1024 维 × 4B ≈ 4GB
   加 HNSW 索引 ≈ 8–12GB
```

**量化可以省内存**：

```
float32 → float16：省一半，召回略降
float32 → int8：省 4 倍，需要训练量化参数
```

### 更新的代价

```
① 插入：通常很快
② 更新（改向量）：多数实现是"删除 + 插入"
③ 删除：标记删除（后台压缩），不会立即释放空间
```

**高频更新的场景要小心**：

```
每篇文章每天改一次 → 大量"删除+插入" → 索引碎片 → 需要定期 compact
```

Milvus/Qdrant 都有 compaction 机制，但要监控碎片率。

### 元数据过滤与"预过滤 vs 后过滤"

```
后过滤（post-filter）：先向量检索 TopK，再按条件筛
  → 条件很严时，可能筛完不剩几条

预过滤（pre-filter）：先按条件缩小范围，再向量检索
  → 准确，但要求数据库支持（Qdrant/Milvus 支持）
```

**这是 RAG 里最常见的准确率问题**：按 `tenant_id`/`doc_type` 过滤时，必须用预过滤。

### "召回不准"的排查顺序

```
① 模型一致吗？（入库与查询用了同一个 embedding 模型？）
② 文本切分合理吗？（chunk 太大导致语义稀释，太小导致缺上下文）
③ 索引参数够吗？（ef_search 太小 → 召回低）
④ 过滤是不是后过滤？（严格条件下候选不够）
⑤ 数据本身相关吗？（用关键词先验证"库里有没有答案"）
⑥ 归一化做了吗？（部分模型要求向量归一化后再算余弦）
```

**最常被忽略的是②**：切分不好，再好的模型也召回不准。

### 混合检索（更实用的做法）

```
向量检索（语义）+ 关键词检索（BM25/全文）+ 融合排序
```

原因：**纯向量对"精确匹配"（如订单号、错误码）很差**，而关键词检索正好补上。

融合方式：

```python
# 加权融合
score = 0.6 * vector_score + 0.4 * bm25_score
# 或 RRF（倒数排名融合，不需要归一化）
score = 1/(k + rank_vector) + 1/(k + rank_bm25)
```

### 备份与重建

```
① 向量数据可以重建（只要原文与模型在）→ 不必像数据库那样严格备份
② 但重建耗时：100 万条 + 1024 维，可能要几小时
③ 重建期间服务要降级（用旧索引继续服务）
```

**建议**：

```
- 保留原始文本（这是真正的数据）
- 向量索引可作为"可重建的缓存"
- 模型变更时用"双索引"过渡（新旧并存，逐步切换）
```

### 检查清单

```
□ 选型与规模匹配（小规模优先 pgvector）
□ 入库与查询模型一致（写进代码常量）
□ HNSW 参数实测调过（不是默认值）
□ 内存估算过（含索引开销）
□ 有预过滤（不是后过滤）
□ 有混合检索（向量 + 关键词）
□ 监控碎片率与 compaction
□ 原始文本有备份（向量可重建）
□ 模型变更走"双索引"切换
```
