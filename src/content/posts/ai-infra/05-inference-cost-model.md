### 显存去哪儿了

一台推理服务的显存由四部分组成：

```
总显存 = 模型权重 + KV Cache + 激活值 + 框架开销（约 1–2GB）
```

以 7B 模型、FP16 为例：

- 权重：7B × 2 字节 ≈ **14GB**
- KV Cache：见下
- 激活值：一批 token 的中间结果，通常 1–2GB

所以"7B 模型需要多少显存"这个问题，答案是**14GB 只是入场券**，实际要 20GB 以上才能跑起来。

### KV Cache 怎么估

每个 token 的 KV 大小：

```
2 × layers × heads × head_dim × bytes_per_element
```

以 Llama-3-8B（32 层、32 heads、head_dim 128、FP16）为例：

```
单 token = 2 × 32 × 32 × 128 × 2 ≈ 524KB
```

一条 4096 token 的会话：

```
4096 × 524KB ≈ 2.1GB
```

**这就是为什么"并发数 × 上下文长度"直接决定显存**。10 个并发 × 4K 上下文就要再吃 21GB。想支持 32K 上下文，单会话就要 16GB。

结论：长上下文的成本不在权重，在 KV Cache。

### 批处理为什么能降成本

GPU 的算力是"一次算一批"更划算的：

| 批大小 | 吞吐（token/s） | 单 token 成本 |
| --- | --- | --- |
| 1 | 40 | 1× |
| 8 | 220 | 0.18× |
| 32 | 600 | 0.09× |

批大小 32 时，单 token 成本能降到 1/10。这就是为什么推理服务一定要做 continuous batching（vLLM、TensorRT-LLM 都内置）。

代价：**延迟会略微上升**（要等批凑满）。所以策略是"小批 + 短等待"，通常 `max_num_seqs=32`、超时 10–20ms 就发。

### 量化的四种做法

| 方式 | 精度 | 显存节省 | 质量损失 | 适合 |
| --- | --- | --- | --- | --- |
| FP16/BF16 | 高 | 基准 | 无 | 通用 |
| INT8（权重+激活） | 中高 | ~40% | 小 | 通用，需校准 |
| INT4（AWQ/GPTQ） | 中 | ~60% | 可感知 | 显存紧张、对话场景 |
| FP8（H100 原生） | 高 | ~50% | 极小 | 新卡首选 |

实践建议：

1. **优先 BF16**，除非显存真的不够。
2. 显存不够先用 **FP8**（如果卡支持），比 INT4 稳。
3. 上 INT4 要**做评测**：同一批问题对比答案质量，别只看 perplexity。
4. 量化后的模型**不能直接和原模型共用 tokenizer 缓存假设**，有的 kernel 对序列长度有限制。

### 该买几张卡：一个可算的流程

```
① 目标并发：同时在线会话数 × 平均等待时间占比
② 单会话显存：权重 + 上下文 KV
③ 单卡可用显存 = 卡显存 - 框架开销
④ 卡数 = ceil(① × ② / ③)
⑤ 再乘冗余系数 1.3（应对突增与碎片）
```

例：7B FP16、单卡 24GB（可用 22GB）、支持 16 并发、4K 上下文：

```
权重 14GB + 16 × 2.1GB = 47.6GB
47.6 / 22 ≈ 2.2 → 3 张卡
× 1.3 → 4 张卡
```

如果换成 INT4（权重 3.5GB，KV 不变）：

```
3.5 + 33.6 = 37GB → 2 张卡，×1.3 → 3 张
```

**注意 KV 不会因为量化权重而变小**（除非用 KV Cache 量化，那是另一项技术）。

### 三个降本手段，按性价比排序

1. **提高批大小 / 用 continuous batching**：零成本，收益最大。
2. **缩短上下文**：RAG 里少塞几段，KV 直接下降；`max_tokens` 限制输出长度。
3. **量化**：省显存但要做质量评测。

再往后才是"换更小的模型"或"换更快的卡"。

### 上线后要盯的四个指标

```promql
# 1. 吞吐（token/s）
rate(llm_output_tokens_total[5m])
# 2. TTFT（首 token 延迟）
histogram_quantile(0.95, sum by (le) (rate(llm_ttft_seconds_bucket[5m])))
# 3. GPU 显存利用率
DCGM_FI_DEV_FB_USED / DCGM_FI_DEV_FB_TOTAL
# 4. 队列长度（请求在排队说明容量不够）
llm_requests_waiting
```

`llm_requests_waiting` 持续 > 0，说明并发已满，用户会明显感知变慢。

### 成本核算的一个坑

按"每千 token 多少钱"报价时，要区分：

- **输入 token**（prompt，通常更便宜，可以批处理得很满）
- **输出 token**（自回归逐个生成，最贵）

输出 token 的成本约是输入的 3–10 倍，因为它是串行生成的。做成本预估时别用平均价，要分别算。

### 一句话总结

推理成本 = **权重占的显存 + 上下文占的显存**；降本顺序是**先提吞吐（批处理），再压上下文，最后才量化**。
