### 从 demo 到生产的五个差距

```
demo：拿几篇文档，问一句，答得还不错
生产：10 万份文档、每天 10 万次问答、"答错了要追责"
```

**五个必须解决的问题**：

```
① 切分（chunk）策略不对 → 召回不准
② 没有评估 → 不知道改好了还是改坏了
③ 答案不可溯源 → 用户不信、无法追责
④ 幻觉 → 答得流畅但错误
⑤ 成本与延迟 → 长上下文很贵
```

### ① 切分：最容易被低估的一步

**三种策略**：

| 策略 | 做法 | 适用 |
| --- | --- | --- |
| 固定长度 | 每 500 字切一刀 | 通用，最简单 |
| 按结构 | 按标题/段落/表格切 | 文档有结构（手册、规范） |
| 语义切分 | 按句子相似度分组 | 长文本、无结构 |

**实践建议**：

```
① 按结构切（标题层级是最天然的边界）
② 每个 chunk 保留"父级标题路径"（提升召回时的上下文）
③ 加 10%–20% 重叠（避免跨块信息丢失）
④ chunk 大小 300–800 字（太大稀释语义，太小缺上下文）
```

**"保留父级标题"的具体做法**：

```
原文：手册 > 第三章 网络配置 > 3.2 防火墙

chunk 内容加前缀：
"手册 / 第三章 网络配置 / 3.2 防火墙 —— <正文>"
```

**这一招对召回率提升很明显**，因为用户提问往往包含"章"级的词。

### ② 评估：没有它就是在盲改

**建一个"评估集"**：

```json
[
  {"q": "如何修改防火墙默认策略?", "gold_ids": ["doc_12#c3"]},
  {"q": "K8s Pod 一直 Pending 怎么查?", "gold_ids": ["doc_45#c1", "doc_45#c2"]}
]
```

**至少 50 条**，覆盖：

```
① 高频问题（真实用户问的）
② 长尾/难问题（多跳、需要两段）
③ "知识库里没有"的问题（测"拒答"能力）
```

**两个指标**：

```
召回率 Recall@K：正确答案有没有出现在前 K 个 chunk
答案正确率：基于召回的 chunk，答案对不对（人工/LLM 评）
```

**关键**：**改任何参数（切分/模型/TopK）前后都跑一遍这套评估**。

**没有评估集的典型场景**：

```
"我感觉改了之后好一点" → 实际上退化了，但没人发现
```

### ③ 可溯源：每个结论都要能点回原文

**做法**：

```
① 回答里带引用标记（如 [1][2]）
② 每个标记对应一个 chunk（含文档名、章节、链接）
③ 前端可点击跳转到原文位置
```

**Prompt 里明确要求**：

```
只根据以下资料回答。每个结论后必须标注来源编号，如 [1]。
如果资料中没有答案，直接说明"资料中未提及"。
```

**价值**：

```
① 用户能验证（信任度大幅提升）
② 出问题时能追到"是哪份文档错了"
③ 减少幻觉（模型被强制"看着资料说话"）
```

### ④ 幻觉抑制的四个手段

**① 强制引用**

```
没有引用标记的句子 → 前端标为"未验证"
```

**② 拒答机制**

```
检索结果相似度 < 阈值 → 直接"没有找到相关资料"
不要硬答
```

**③ 两阶段生成**

```
第一步：抽取相关句子（只做抽取，不做生成）
第二步：基于抽取的句子组织答案
```

**④ 一致性校验（成本较高）**

```
生成答案后，把答案拆成若干"事实断言"
逐条回到检索结果里核对是否支持
不支持的标记/删除
```

### ⑤ 成本与延迟

**成本构成**：

```
① Embedding（一次性，按文档量）
② 检索（向量库查询，很便宜）
③ 生成（按 token 计费，最贵）
```

**三个优化点**：

```
① 减少上下文（TopK 从 10 降到 4，质量可能更好——"Lost in the Middle"）
② 缓存（相同问题缓存答案，命中率高）
③ 分级模型（简单问题用小模型，复杂问题用大模型）
```

**"Lost in the Middle" 现象**：

```
把 20 个 chunk 全塞给模型 → 中间部分的 chunk 容易被忽略
→ 少而准 > 多而杂
```

**延迟分解（典型）**：

```
embedding 查询  20ms
向量检索       30ms
重排（可选）   100ms
生成（首 token）300–800ms
```

**用户能接受的是"首 token 1 秒内"**，所以"重排"和"生成"是主要优化对象。

### 一个可上线的处理链

```
用户问题
  ↓
① 改写（把口语化问题改成检索友好的 query）
  ↓
② 混合检索（向量 + BM25）→ Top 20
  ↓
③ 重排（cross-encoder 或 LLM 打分）→ Top 4
  ↓
④ 拼 Prompt（带引用要求 + 拒答指令）
  ↓
⑤ 生成（流式输出）
  ↓
⑥ 后处理（校验引用标记，无引用的句子标灰）
```

**"改写"这一步很关键**：

```
用户问："这个为啥不行"（指代不明）
改写：结合对话历史 → "Pod 处于 Pending 状态的原因"
```

### 常见失败模式

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 答非所问 | 检索没召回对的 chunk | 改切分、加混合检索 |
| 答得对但没用 | chunk 太碎缺上下文 | 加父级标题、增大 chunk |
| 答得很长但空 | 模型在"编" | 强制引用 + 拒答 |
| 引用编号错乱 | Prompt 里编号与 chunk 不对应 | 生成时按顺序编号并校验 |
| 同一问题答得不一样 | 温度太高 | 降到 0–0.2 |
| 慢 | 上下文太长 | 减 TopK、流式输出 |

### 检查清单

```
□ 切分按结构（保留父级标题路径）
□ chunk 300–800 字 + 10% 重叠
□ 有评估集（≥50 条，含"无答案"类）
□ 改动前后都跑评估
□ 回答带引用标记，可跳原文
□ 有拒答阈值
□ 混合检索（向量 + 关键词）
□ 有重排（Top 20 → Top 4）
□ 有缓存（相同问题）
□ 温度低（0–0.2）
□ 首 token < 1 秒
```
