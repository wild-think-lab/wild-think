### 推理服务的四个信号

```
① 请求排队（最关键）：队列长度/等待时间上升
② 延迟（TTFT/P99）
③ GPU 利用率（算力）与显存（并发上限）
④ 错误率（超时/拒绝）
```

**"按 QPS 扩"** 在推理场景往往失效（每个请求成本差异巨大）。

### 为什么 QPS 不准

```
一个 100 token 的请求 与 一个 4000 token 的请求
在同一个副本上成本差 10 倍以上
```

**"QPS 没变但延迟涨了"** → 往往是"输入变长了"。

**更好的指标**：

```
① 排队时长（P95 等待）
② 在途 token 数（prefill+decode 的总量）
③ KV Cache 占用率（最贴近"真实并发上限"）
```

### GPU 场景的两个硬约束

```
① 扩出来的副本"启动慢"（加载权重 30s–5min）
② 显存决定了"最大并发"，不是 CPU
```

**"扩了 10 个副本但都还在加载"** → 扩容期间的延迟照样崩。

**应对**：

```
① 预热副本（pool 常驻 + 弹性）
② 提前扩（按"趋势"而不是"阈值"）
③ 有"排队降级"（超时拒绝 + 友好提示）
```

### 冷启动优化

```
① 模型缓存（本地 NVMe / 共享存储）
② 预热（启动时跑一次 dummy 推理）
③ 分层加载（先加载部分层，边服务边加载）
④ 保留最小副本数（不缩到 0）
```

**"从 0 扩到 5"** 在推理场景通常太慢（这是 serverless GPU 的痛点）。

### 排队与拒绝策略

```
① 排队上限（超过就快速拒绝，别让用户等 30s）
② 按租户/优先级分队列（重要业务先服务）
③ 长请求单独队列（避免"一个超长请求堵住所有人"）
```

**"无限排队"** → 用户等 30 秒后超时，等于白占资源。

### 五个"扩了还是不扛"

**① 扩了副本但共享后端成瓶颈**

```
向量库/数据库连接打满 → 加副本无意义
```

**② 每副本并发配太小**

```
副本数翻倍但每个只允许 1 并发 → 总吞吐没变
```

**③ 批处理参数不合理**

```
batch 太大 → 单请求延迟升高；太小 → GPU 闲
```

**④ 显存碎片**

```
KV Cache 碎片导致"显存够但不能接新请求"
（PagedAttention 能缓解）
```

**⑤ 扩容滞后**

```
按"P99 超阈值"才扩 → 已经慢了 3 分钟
→ 用"排队长度"提前扩
```

### 一个"分级"扩缩容方案

```
① 常驻池（min replicas = 峰值 30%）：应对日常
② 弹性池：按排队/显存扩（60s 一次评估）
③ 应急池：预留实例（大促前预热）
④ 缩容慢（避免抖动）：缩容需要连续 10 分钟低负载
```

**"缩容太快"** 会导致"刚缩完又来流量"→ 反复启停（比不扩还糟）。

### 检查清单

```
□ 用"排队 + 显存 + 在途 token"而不是只看 QPS
□ 有 TTFT 与 P99 监控
□ 副本预热/常驻最小数
□ 冷启动时间已知并优化
□ 有排队上限与快速拒绝
□ 关键业务有优先级队列
□ 扩容按趋势（提前），缩容慢
□ 后端依赖（向量库/DB）有连接池上限
□ 每副本并发参数与显存匹配
□ 有大促前的预热演练
```
