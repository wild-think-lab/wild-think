### RAG 解决的是什么

大模型有两个硬限制：**知识有截止日期**、**不知道你的私有数据**。

三种补法：

| 方式 | 成本 | 时效 | 适合 |
| --- | --- | --- | --- |
| 微调 | 高（要数据、要算力） | 需重训 | 风格、固定任务 |
| 长上下文全塞 | 中（token 贵） | 实时 | 少量文档、一次性问答 |
| RAG 检索后注入 | 低 | 实时 | 大量文档、持续更新 |

RAG 的核心假设：**"找到相关片段"比"让模型记住所有内容"更经济**。

### 五个环节

```
① 采集 → ② 切片(chunk) → ③ 向量化(embedding) → ④ 存储与检索 → ⑤ 组装 prompt 生成
```

每一环都会成为瓶颈，**其中切片与检索占了 80% 的质量问题**。

### 切片：最容易被低估的一步

固定长度切（512 token）简单，但会把一段话切成两半，检索出来的片段缺上下文。

推荐的组合策略：

1. **按结构切**：先按标题、段落、列表切，保证语义单元完整。
2. **加重叠**：相邻块重叠 10–15%，缓解边界丢信息。
3. **保留元数据**：`source`、`title`、`section`、`updated_at` 一起存，检索后能引用来源。
4. **小块检索、大块喂给模型**（small-to-big）：用 200 token 的块做向量匹配，命中后把它所在的 800 token 章节一起送给模型。

```python
chunks = split_by_heading(doc, max_tokens=400, overlap=60)
for i, c in enumerate(chunks):
    store.add(
        text=c.text,
        embedding=embed(c.text),
        meta={"doc_id": doc.id, "title": doc.title, "section": c.heading, "idx": i},
    )
```

### 向量化的三个坑

1. **换模型必须重建索引**。不同 embedding 模型的向量空间不兼容，混用等于随机检索。
2. **模型要对齐语言**。中文文档用英文模型效果会明显下降，选多语言模型（如 bge-m3、multilingual-e5）。
3. **维度不是越高越好**。1024 维比 768 维召回略好，但存储与检索成本翻倍。先用量化（int8）压成本。

### 检索：纯向量不够用

纯向量检索的弱点：**专有名词、编号、错误码**这类"字面匹配"场景表现差。所以生产上基本都做混合检索：

```
final_score = 0.7 * 向量相似度 + 0.3 * BM25 分数
```

或用 RRF（Reciprocal Rank Fusion）融合两路排名：

```python
def rrf(rank_lists, k=60):
    score = {}
    for ranks in rank_lists:
        for i, doc_id in enumerate(ranks):
            score[doc_id] = score.get(doc_id, 0) + 1.0 / (k + i + 1)
    return sorted(score, key=score.get, reverse=True)
```

再加一层**重排（rerank）**：用 cross-encoder 对 top 20 精排，取 top 5 送给模型。这一步通常能显著提升准确率，代价是几十毫秒延迟。

### 向量库怎么选

| 库 | 特点 | 适合 |
| --- | --- | --- |
| pgvector | 复用 Postgres，支持 SQL 过滤 | 数据量中等、已有 PG |
| Milvus | 专用、可水平扩展 | 亿级向量 |
| Qdrant | Rust 实现、过滤能力强 | 中等规模、要复杂过滤 |
| FAISS | 库不是服务 | 离线/嵌入式 |
| Elasticsearch | 天生混合检索（BM25+向量） | 已有 ES 集群 |

选型关键不是"谁最快"，而是**过滤能力**：业务查询通常是"在某类文档里找"，纯 ANN 索引 + 后置过滤会漏召回。要支持"先过滤再检索"（pre-filter）。

### 评估：没有评估就没有优化

三个指标：

- **召回率（Recall@k）**：正确片段是否在 top-k 里。
- **忠实度（Faithfulness）**：答案是否只基于检索到的内容（有没有编）。
- **答案相关性**：是否回答了用户问题。

做法：准备 50–100 条"问题 + 标准答案 + 应命中的文档 id"的评测集，每次改切片/模型/检索参数就跑一遍。

```python
for case in eval_set:
    hits = retriever.search(case.question, k=5)
    recall = any(d.id in [h.id for h in hits] for d in case.gold_docs)
```

没有评测集时，先用"20 个真实用户问题"起步，比拍脑袋调参有效得多。

### 五个常见失败原因

1. **切片太碎**：一句话一块，检索到了但没上下文，模型答不出。
2. **文档太脏**：PDF 里的表格、页眉页脚、目录都进了索引，检索噪声大。清洗比调参重要。
3. **只用向量**：错误码 `E1024` 这类查询向量化后几乎没有区分度。
4. **top-k 太大**：塞 20 个片段进 prompt，模型注意力被稀释，还贵。5 个精排片段通常更好。
5. **没做"不知道"的处理**：检索为空时模型仍然编答案。要在 prompt 里明确"若资料不足，回答不知道"。

### 工程化要补的三件事

- **增量更新**：文档变更后重新切片、只重建受影响的部分，别全量重跑。
- **权限过滤**：不同用户能看的文档不同，检索时必须带上 `tenant_id`/`acl` 过滤，不能靠"事后删"。
- **缓存**：相同问题 + 相同检索结果可以缓存答案，成本能降一半。

### 一句话总结

RAG 的效果主要由**清洗与切片**决定，其次由**混合检索 + 重排**决定，模型只是最后一环。先把评测集建起来，再谈优化。
