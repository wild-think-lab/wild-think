### 为什么 Prompt 需要"工程"

```
随口问 → 结果不稳定、不可测、不可复现
结构化 Prompt → 可版本化、可评估、可回归
```

**"把 Prompt 当成代码来管"** 是核心思路。

### 五个部分

```
① 角色与目标（你是谁、要做什么）
② 输入说明（数据长什么样、边界）
③ 约束（必须/禁止）
④ 输出格式（结构化）
⑤ 示例（few-shot）
```

**示例模板**：

```
你是电商客服助手。根据【工单内容】判断问题类型，并给出回复草稿。

【约束】
- 不要承诺"退款到账时间"以外的时效
- 涉及金额必须引用原文数字
- 不确定时输出 "needs_human": true

【输出格式】
{"type": "logistics|refund|quality|other", "reply": "...", "needs_human": bool}

【示例】
输入：我的快递三天没动了
输出：{"type":"logistics","reply":"...","needs_human":false}
```

### 输出约束的三种手段

**① 结构化格式（JSON Schema）**

```
用厂商的"结构化输出"能力（response_format/guided decoding）
→ 比"请输出 JSON"可靠得多
```

**② 校验 + 重试**

```python
for attempt in range(3):
    out = call(prompt, response_format=schema)
    if validate(out): return out
    prompt += "\n上一次输出不符合格式，请严格按 schema 输出。"
```

**③ 后处理兜底**

```
解析失败 → 走"模板化回复"或转人工
（不要让解析异常直接抛给用户）
```

### 评估：必须有

```
① 20–50 条真实输入 + 期望输出（或期望属性）
② 指标：格式正确率 / 关键字段准确率 / 拒答率
③ 每次改 Prompt 都跑一遍（防回归）
```

**"改完感觉更好了"** 不算验证。

**关键**：

```
评估集要包含"边界/恶意/含糊"输入
```

### 版本管理

```
① Prompt 存文件（不是硬编码在代码里）
② 版本号 + 变更说明
③ 线上用哪个版本要能查（记录到日志里）
④ 支持灰度（A/B 两个 Prompt 版本）
```

**"线上到底用的哪版 Prompt"** 出事时第一个要确认的事。

### 五个"提示词时好时坏"

**① 输入长度波动**

```
长输入把关键信息"淹没" → 显式要求"先摘取关键字段"
```

**② 输出格式不稳定**

```
"请用 JSON 输出" → 有时带 markdown 代码块
→ 用结构化输出能力，而不是靠"请"
```

**③ 顺序敏感**

```
关键约束放在最后 → 模型"忘了"前面的
→ 重要约束放开头与结尾各一次
```

**④ 示例太少/太偏**

```
只给一个示例 → 模型只学会一种形态
→ 3–5 个覆盖不同类型
```

**⑤ 温度/参数不一致**

```
评估时 temperature=0，线上默认 0.7 → 表现不同
→ 评估必须用线上参数
```

### 常用技巧（按收益）

```
① 明确输出格式（最高收益）
② few-shot（覆盖类型边界）
③ 让模型"先列出要点再回答"（提升复杂任务准确率）
④ 分步拆解（复杂任务拆成多次调用）
⑤ 显式"不知道就说不知道"（降低幻觉）
```

**"chain-of-thought"** 对内部分析有效，但要"只输出结论"时要在 Prompt 里说明。

### 一个"落地"的检查

```
□ Prompt 是否在文件里（而非代码字符串）
□ 是否有 schema 约束输出
□ 是否有评估集
□ 评估是否用线上参数
□ 是否有版本号与变更记录
□ 线上日志是否记录了 Prompt 版本
□ 解析失败是否有兜底
□ 是否有"不确定转人工"的路径
```

### 检查清单

```
□ 五部分齐全（角色/输入/约束/格式/示例）
□ 输出用 schema 约束
□ 有校验与重试
□ 解析失败有兜底
□ 有评估集（含边界）
□ 评估用线上参数
□ Prompt 版本化 + 可追溯
□ 支持 A/B 灰度
□ 有"不确定转人工"
□ 关键约束首尾各一次
```
