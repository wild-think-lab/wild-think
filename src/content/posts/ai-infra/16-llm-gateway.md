### 网关该做的六件事

```
① 统一入口（一个 API 对多模型）
② 鉴权与多租户（谁在用、用多少）
③ 路由与降级（主模型失败切备用）
④ 限流与配额（防滥用、防超支）
⑤ 观测（延迟/错误/Token 消耗）
⑥ 缓存（相同请求复用）
```

**"每个业务各自直连模型厂商"** → 成本无法核算、密钥散落各处。

### 统一入口的好处

```python
# 应用只需要一个 SDK/一个 base_url
resp = client.chat(model="auto", messages=[...])
```

```
① 换模型不用改业务代码
② 密钥只在网关里
③ 成本/延迟统一观测
```

### 路由与降级

```
主：gpt-4o（质量优先）
备：qwen-plus（成本优先或国内可用）
降级触发：超时/5xx/限流/配额用尽
```

```python
def chat(req):
    for model in ["primary", "backup"]:
        try:
            return call(model, req, timeout=10)
        except (Timeout, RateLimited, ServerError):
            continue
    raise AllProvidersDown()
```

**"降级要能自动"**，否则主模型一抖业务全挂。

**注意语义差异**：

```
不同模型的输出格式/能力不同 → 降级后要做"输出校验"
```

### 限流的三层

```
① 全局 QPS 上限（保护上游与自身）
② 租户配额（每日 Token 上限）
③ 单用户频率（防脚本刷）
```

```python
# 令牌桶（简化）
if not bucket.allow(tenant): raise QuotaExceeded()
```

**"没有配额"** → 一个脚本能把月度预算烧完。

### Token 计费与成本核算

```
① 记录 input_tokens / output_tokens（按模型分别计价）
② 按租户/业务/模型维度汇总
③ 设置"预算告警"（80% 时提醒）
```

**"成本算不清"是多模型时代最普遍的问题**。

**一个最小表结构**：

```sql
CREATE TABLE llm_calls (
  id BIGINT PRIMARY KEY,
  tenant VARCHAR(64),
  model VARCHAR(64),
  in_tokens INT,
  out_tokens INT,
  latency_ms INT,
  status VARCHAR(16),
  created_at DATETIME
);
```

**"先有表，再谈优化"**。

### 缓存

```
① 精确缓存（完全相同请求 → 复用响应）
② 语义缓存（相似问题 → 复用，需评估风险）
③ 缓存 key 要含 model + 参数 + prompt 版本
```

**"语义缓存"** 能省很多钱，但会带来"回答不一致"的风险：

```
适合"FAQ/知识问答"，不适合"个性化/实时数据"
```

### 流式（SSE）的处理

```
① 网关必须支持"流式透传"（否则首字延迟翻倍）
② 流式下的"用量统计"要在结束时结算
③ 客户端断连要能取消上游请求（省钱）
```

**"网关缓冲整个响应再返回"** 会毁掉流式体验。

### 五个"自建网关后又拆掉"的原因

**① 只做了转发，没做治理**

```
没有配额/没有观测 → 和直连没区别，还多一跳
```

**② 单点**

```
网关挂了 → 所有 AI 功能全挂
→ 至少双副本 + 健康检查
```

**③ 延迟增加明显**

```
多一跳 + 缓冲 → 首字延迟 +200ms
```

**④ 与厂商 SDK 特性不兼容**

```
厂商新能力（工具调用/结构化输出）网关没跟上
```

**⑤ 运维成本被低估**

```
要维护：密钥、配额、模型清单、计费、升级
```

### 什么时候该用现成方案

```
① 规模小（几个业务）→ 用厂商 SDK + 环境变量密钥
② 多云多模型 → 考虑开源网关（LiteLLM/OneAPI 类）
③ 强合规/私有化 → 自建
```

**"先用开源网关，再加自定义逻辑"** 比"从零自建"省时。

### 检查清单

```
□ 统一入口（业务不直连厂商）
□ 密钥只在网关
□ 多租户鉴权
□ 路由 + 自动降级
□ 三层限流（全局/租户/用户）
□ Token 用量落库
□ 有成本看板与预算告警
□ 支持流式透传
□ 断连取消上游
□ 网关自身高可用
□ 有缓存策略（明确适用边界）
```
