### 三种架构一句话

```
NAS（Network Attached Storage）：文件级共享（NFS/SMB）——"共享文件夹"
SAN（Storage Area Network）  ：块级共享（iSCSI/FC）——"共享硬盘"
分布式存储                    ：软件定义，多节点聚合（Ceph/GlusterFS）
```

**关键差别是"共享的粒度"**：

```
块级（SAN）：客户端看到一块"裸盘"，自己格式化文件系统
文件级（NAS）：客户端看到"目录与文件"，文件系统在存储侧
```

**"块级允许多客户端同时挂载吗"** —— 普通文件系统不行（会损坏），必须用集群文件系统（GFS2/OCFS2）或 CephFS。

### 对比表

| 维度 | NAS | SAN | 分布式 |
| --- | --- | --- | --- |
| 粒度 | 文件 | 块 | 文件/块/对象 |
| 协议 | NFS/SMB | iSCSI/FC | 私有/兼容 S3 |
| 扩展 | 纵向（换更大设备） | 纵向 | 横向（加节点） |
| 性能 | 中（协议开销） | 高（尤其 FC） | 中（网络与副本开销） |
| 成本 | 低 | 高 | 中 |
| 运维 | 简单 | 中 | 复杂 |
| 典型场景 | 文件共享、备份 | 数据库、虚拟化 | 云原生、大数据 |

### NAS 的三个性能陷阱

**① 元数据成为瓶颈**

```
一个目录下 10 万个文件 → ls 都要几秒
→ 大量小文件是 NAS 的天敌
```

**处理**：分目录（按日期/哈希）、避免单目录过大。

**② NFS 的 sync/async**

```bash
mount -t nfs -o sync ...    # 每次写都等落盘（安全但极慢）
mount -t nfs -o async ...   # 先缓存后写（快但断电可能丢）
```

**"数据库跑在 NFS 上很慢"往往就是 sync 模式**。

**③ 单点**

```
一台 NAS 挂了 → 所有客户端卡住（hard mount 会永久重试）
```

**处理**：

```
① 用 NAS 双机 HA
② 客户端用 soft + 较短超时（但可能写不完整）
③ 关键业务不要放 NAS
```

**"hard mount 导致进程进入 D 状态"** 是很常见的现场：

```
现象：进程 kill -9 都杀不掉
原因：在等 NFS 响应，内核态不可中断
→ 只能恢复 NFS 服务或重启机器
```

### iSCSI vs FC

| 维度 | iSCSI | FC（光纤通道） |
| --- | --- | --- |
| 传输 | 以太网（10G/25G） | 专用光纤（8G/16G/32G） |
| 成本 | 低（复用现有网络） | 高（HBA + 交换机 + 光纤） |
| 延迟 | 较低 | 最低且稳定 |
| 隔离 | 需 VLAN/QoS 隔离 | 物理隔离（专用网） |
| 适合 | 中小规模、虚拟化 | 核心数据库、高 IOPS |

**"iSCSI 与业务网混跑"是常见错误**：

```
存储流量把业务带宽吃满 → 业务与存储互相拖累
→ 至少用 VLAN + QoS，最好物理隔离
```

### 分布式存储的适用面

**适合**：

```
① 需要横向扩展（容量/性能随节点增长）
② 云原生（K8s 的 PVC）
③ 对象存储（图片/备份/日志）
```

**不适合**：

```
① 单机小规模（3 节点起，成本反而高）
② 极低延迟要求的核心数据库（除非 NVMe + RDMA 全闪）
③ 网络差的机房（分布式对网络极其敏感）
```

**"分布式存储一定要万兆网络"** 不是建议，是底线。

### 五个"选错就要重来"的判断点

**① 是"文件共享"还是"块设备"**

```
文件共享（多人同时读写同一批文件）→ NAS
块设备（数据库/虚拟机的磁盘）→ SAN/iSCSI
方向选错，后面全白费
```

**② 小文件多还是大文件多**

```
小文件多 → 元数据压力 → NAS/分布式都要谨慎
大文件顺序读写 → HDD 阵列也能扛
```

**③ 延迟要求是"毫秒"还是"微秒"**

```
微秒级（核心交易 DB）→ 全闪 + FC/NVMe
毫秒级（一般业务）→ iSCSI/NAS 都能满足
```

**④ 数据一致性要求**

```
多客户端同时写同一文件 → 需要集群文件系统（代价大）
单写多读 → NAS 足够
```

**⑤ 扩容方式**

```
只能"换更大的设备" → 纵向（NAS/SAN）
能"加节点" → 横向（分布式）
未来 3 年数据量增长多少？按这个选
```

### 一个现实的组合

```
核心数据库      → 全闪 SAN（FC 或 iSCSI 独立网）
虚拟化平台      → iSCSI（万兆独立网）
文件共享/备份   → NAS（双机 HA）
云原生/对象      → 分布式（Ceph/对象存储）
```

**"一种存储打天下"是不现实的**。

### 备份与容灾的独立性

```
存储的"高可用"（副本/RAID/双控）≠ 备份
```

**必须独立做备份**：

```
① 存储故障（控制器双挂）→ 数据仍可能丢
② 误删除/勒索 → 副本会同步删掉
③ 3-2-1 原则（3 份、2 种介质、1 份异地）
```

**"我们有 RAID，所以不用备份"是最危险的认知**。

### 检查清单

```
□ 先判断"文件级还是块级"
□ 评估小文件比例（元数据压力）
□ 明确延迟要求（毫秒 vs 微秒）
□ 多客户端写同一文件的场景已识别
□ iSCSI 用独立 VLAN + QoS（或物理隔离）
□ NAS 单点问题已处理（HA 或不做关键业务）
□ 分布式存储用万兆网络
□ 明确扩容方式是纵向还是横向
□ 不同用途用不同存储（不追求统一）
□ 备份独立于高可用（3-2-1）
```
