### 三个概念先分清

| | 备份（Backup） | 快照（Snapshot） | 容灾（DR） |
| --- | --- | --- | --- |
| 解决 | 数据被误删/损坏 | 快速回滚到几分钟前 | 整个站点不可用 |
| 存放 | 独立介质 | 同一存储 | 异地 |
| 恢复时长 | 分钟到小时 | 秒到分钟 | 小时到天 |
| 能否防勒索 | 离线副本可以 | **不能**（会被一起加密） | 可以（隔离） |

**快照不是备份**。存储坏了、被勒索加密了，快照一起没。三者要同时存在。

### RPO 与 RTO

```
RPO（Recovery Point Objective）：能容忍丢多少数据（时间维度）
RTO（Recovery Time Objective）  ：能容忍停多久
```

| 业务 | RPO | RTO | 对应方案 |
| --- | --- | --- | --- |
| 支付/订单 | < 1 分钟 | < 15 分钟 | 同步/半同步复制 + 热备 |
| 用户数据 | < 5 分钟 | < 1 小时 | 异步复制 + 定期备份 |
| 内部系统 | < 24 小时 | < 8 小时 | 每日备份 + 冷备 |
| 归档数据 | < 7 天 | < 3 天 | 周期归档到对象存储 |

**RPO/RTO 由业务定，不是由技术定**。定完再选方案，别反过来（先买了某方案再编一个 RPO 出来）。

费用关系：

```
RPO 越小、RTO 越短 → 成本指数上升
```

从 RTO 4 小时降到 15 分钟，成本可能翻 5 倍。要明确"这 15 分钟值多少钱"。

### 四层备份架构

```
L1 快照      每小时 / 保留 24 小时        （防误删，快速回滚）
L2 增量备份  每天 / 保留 14 天            （防逻辑损坏）
L3 全量备份  每周 / 保留 8 周             （基准恢复点）
L4 离线异地  每月 / 保留 12 个月          （防勒索、防站点灾难）
```

四层的意义：**不同故障用不同层恢复**。

- 误删一张表 → L1 快照（分钟级）。
- 数据被程序写坏 → L2 增量（恢复到昨天）。
- 存储损坏 → L3 全量。
- 机房被攻击/火灾 → L4 离线异地。

只做 L3 的团队，遇到"误删"要恢复整个库，耗时几小时且影响所有人。

### 3-2-1 原则的现代版本

```
3 份数据（1 主 + 2 备份）
2 种介质（如 SSD + 对象存储/磁带）
1 份异地（物理隔离）
+ 1 份离线/不可变（防勒索）
```

"不可变"很关键：备份目标要支持 **WORM / 对象锁**，让攻击者无法删除或加密备份。

```bash
# AWS S3 对象锁（合规模式）
aws s3api put-object-lock-configuration \
  --bucket my-backup --object-lock-enabled
```

### 恢复演练怎么设计

**没有演练的备份不算备份**。演练要覆盖四种场景：

| 场景 | 验证什么 |
| --- | --- |
| 单表恢复 | 能否从备份中只捞一张表（而不是整库） |
| 时间点恢复 | 能否恢复到"误删前 1 分钟" |
| 全量重建 | 从零恢复整套服务需要多久（= 实际 RTO） |
| 备份可用性 | 备份文件能否被正常读取（不是损坏的） |

演练记录必须写清：

```
实际 RTO：从开始恢复到服务可用，用了 47 分钟
瓶颈：拉取备份用了 30 分钟（带宽 100Mbps）
改进：备份放本地缓存 + 增量恢复
```

**瓶颈几乎总在"传输"而不是"恢复"**：1TB 备份走 100Mbps 要 22 小时。

### 五个"备份了但恢复不了"的原因

1. **备份脚本失败但没人知道**：没有"备份成功"的告警，只有"备份失败"的告警，脚本静默失败三个月。
2. **备份文件损坏**：写入时磁盘满、网络中断，产生截断文件。
3. **没有记录恢复步骤**：知道有备份，不知道怎么恢复（顺序、依赖、配置）。
4. **版本不匹配**：备份是 MySQL 5.7，现在跑 8.0，导入失败。
5. **权限与密钥丢失**：加密备份的密钥没备份，等于没有备份。

对应措施：

```
□ 备份完成后校验（checksum + 抽样 restore 到临时库）
□ 备份成功/失败都要有告警（成功也要，否则不知道它还活着）
□ 恢复手册与备份同仓管理
□ 备份保留至少跨一个版本升级周期
□ 加密密钥单独离线保存
```

### 具体工具的对应

| 对象 | 备份方式 |
| --- | --- |
| MySQL | mysqldump（小库）/ XtraBackup（大库，物理备份）+ binlog 归档 |
| PostgreSQL | pg_basebackup + WAL 归档（PITR） |
| Redis | RDB 定时 + AOF；注意 RDB 是快照，不适合当唯一备份 |
| 文件 | rsync + 快照存储 / restic（去重加密） |
| K8s | etcd 快照 + Velero（含 PV 与对象） |
| 虚拟机 | Proxmox vzdump / Veeam |

```bash
# restic：加密去重备份（很实用）
restic -r s3:https://s3.example.com/bucket init
restic backup /data --exclude '*.tmp'
restic check --read-data-subset=5%
restic restore latest --target /restore
```

`restic check` 可以抽检数据完整性，比"文件存在"更可靠。

### 一句话总结

备份体系的设计顺序是：**先定 RPO/RTO → 再分层 → 再解决传输瓶颈 → 最后用演练验证**。跳过任何一步，都会在真出事那天才发现不成立。
