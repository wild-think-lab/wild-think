### 值班最怕的不是故障，是"不知道从哪下手"

一个成熟的 oncall 体系有三个支柱：

1. **分级**：什么告警需要立刻起来，什么可以早上处理。
2. **Runbook**：每个告警都有对应的处置步骤。
3. **升级路径**：自己搞不定时，5 分钟内知道该找谁。

缺了任何一个，值班就是"用人的睡眠填补流程的空白"。

### 告警分级：决定"要不要起来"

| 级别 | 判据 | 响应 |
| --- | --- | --- |
| P1（page） | 核心功能不可用、影响收入、数据风险 | 立即，5 分钟内响应 |
| P2（page 或 IM） | 部分用户受影响、性能明显下降 | 30 分钟内 |
| P3（IM/工单） | 单实例异常、有冗余兜底 | 工作时间内 |
| P4（工单） | 容量预警、日志异常、待优化 | 排期处理 |

判断口诀：**"用户能不能感知？能不能自己绕过？"** 两个都是"否"才配 P1。

大量团队的问题不是"分级不准"，而是**所有告警都是 P1**——结果是值班人对所有告警都麻木。

### 三条纪律

1. **收到 P1 先确认，再动手**。别急着重启，先花 60 秒看"影响范围、开始时间、最近有没有变更"。
2. **先止损，后定位**。回滚/切流/降级，让用户先能用，再慢慢查根因。
3. **所有操作留痕**。在故障群里发"我要做什么"，做完发结果。一个人闷头操作，交接时会丢失全部上下文。

### 上手排查的固定顺序

被叫醒时脑子是懵的，所以顺序必须固定成肌肉记忆：

```
① 现象：什么坏了，谁受影响，从几点开始
② 变更：最近 2 小时有没有发布/配置改动（80% 的故障来自变更）
③ 指标：错误率、延迟、QPS、资源
④ 日志：最早的错误是什么（不是最后一条）
⑤ 依赖：DB/缓存/MQ/第三方是否异常
⑥ 处置：回滚 / 扩容 / 限流 / 降级
```

第 ② 步最容易被跳过，但它能直接省掉 80% 的排查时间：

```bash
# 最近有没有发布
kubectl rollout history deploy/order-api | tail -3
# 最近有没有配置改动
git log --since='2 hours ago' --oneline
```

### Runbook 该写什么

一个能用的 runbook，至少包含六段：

```markdown
# 告警：ApiHighErrorRate（5xx > 5%）

## 1. 这个告警意味着什么
订单接口 5 分钟内 5xx 比例超过 5%，可能是下游不可用或新版本引入错误。

## 2. 先确认影响
- Grafana: [链接]
- 检查是否只有某个接口受影响：
  kubectl -n prod logs deploy/order-api --tail=200 | grep -c ' ERROR '

## 3. 最快的止损手段（按优先级）
① 回滚最近一次发布：
   kubectl -n prod rollout undo deploy/order-api
② 若与发布无关，降级为只读：
   kubectl -n prod set env deploy/order-api READ_ONLY=true
③ 若下游不可用，摘除故障依赖并启用本地缓存开关

## 4. 定位根因
- 查最早的 ERROR（不是最后一条）
- 查 DB 连接数与慢查询
- 查第三方接口状态页

## 5. 判断是否需要升级
出现以下任一情况，立即呼叫 @dba / @架构：
- 数据库不可写
- 数据出现不一致
- 15 分钟内无法止损

## 6. 恢复后的收尾
- 确认指标回到基线（5xx < 0.5%，P99 < 300ms）
- 在故障群发恢复通知
- 24 小时内提交复盘
```

关键点：**第 3 段必须是"可复制的命令"**，不是"检查一下服务状态"。凌晨三点没人想翻译抽象描述。

### 一个真实的处置流程

```
02:14 告警：ApiHighErrorRate 触发
02:15 值班确认：5xx 12%，影响下单，P1
02:16 查变更：02:05 有一次发布 → 高概率是它
02:17 决策：先回滚
02:18 kubectl rollout undo → 02:21 5xx 降到 0.3%
02:22 确认：DB、缓存、下游均正常
02:25 群内通报：已回滚，影响 7 分钟，正在查根因
次日 10:00 复盘：新版本的空指针在特定参数下触发
```

这个流程里，"16 分钟查变更"和"17 分钟决策回滚"是最关键的两步。

### 如何降低同类告警

每次故障后问四个问题：

1. **能不能提前发现**？（加监控或改阈值）
2. **能不能自动止损**？（自动回滚、自动摘除）
3. **能不能不产生这个告警**？（修根因）
4. **runbook 是否够清楚**？（下次能不能更快）

一个有效指标：**同类告警 30 天内重复次数**。重复出现说明"修的是症状，不是原因"。

### 值班不该做的事

- **不要在没确认影响前重启**：可能把证据清掉，也可能让部分用户从"慢"变成"错"。
- **不要在故障中做无关变更**："顺手升级一下"是事故放大器。
- **不要一个人硬扛超过 30 分钟**：升级路径存在的意义就是别让人独自扛。
- **不要跳过留痕**：交接时说不清做过什么，等于从头再来。

### 一句话总结

好的 oncall 不是"技术最强的人随叫随到"，而是**分级清楚、runbook 可执行、升级路径通畅**——让一个普通工程师在凌晨三点也能做出正确动作。
