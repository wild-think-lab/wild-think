### 技术债的四种形态

```
① 代码债：重复代码、超长函数、没有测试
② 架构债：耦合、没有边界、单点
③ 基础设施债：手工部署、无监控、无备份
④ 文档债：没人知道为什么这么设计
```

**最容易忽视的是④**：代码还能读，但"为什么这么做"只存在于某个离职同事的脑子里。

### 利息怎么算

技术债的"利息"体现为：

```
① 每次改这个模块，都要多花 2–3 倍时间（怕改坏）
② 每次发版都要人工验证（没有自动化测试）
③ 每次故障排查都要找"最懂的那个人"
④ 新人上手要 1 个月（而不是 1 天）
```

**量化方法（很实用）**：

```
统计最近 10 次需求：
- 每个需求的实际耗时 vs 估算耗时
- 差距大（> 1.5 倍）的模块，就是利息最高的地方
```

**另一个信号**：

```
git log --since="3 months" --stat -- path/to/module | grep -c "changed"
```

改动越频繁 + 每次改动行数很多 = 这块代码在"反复摩擦"，重构收益最高。

### 什么时候该还

**必须还（否则会出事）**：

```
① 影响可用性（单点、无监控、无备份）
② 阻塞新需求（"要加这个功能必须先重构"）
③ 有安全风险（已知漏洞、权限过大）
④ 团队没人敢改（完全黑盒）
```

**可以拖**：

```
① 那个模块即将下线
② 业务量很小（一年改一次）
③ 重构风险 > 收益
```

**"即将下线"要小心**：很多"即将下线"拖了三年还在跑。判断标准：**有没有明确的下线日期与替代方案**。

### 一个不激怒业务的还债计划

**核心原则：不要提"重构"，要提"为了做 X 必须先做 Y"**。

```
❌ "我们需要两个月重构订单模块"
✅ "下个季度的三个需求（拆单、改价、对账）都要改订单核心，
   现在这块代码没测试，改一次要验证三天。
   先用两周补测试和拆分接口，之后这三个需求能快一倍"
```

**还债的三种"披风"**：

```
① 搭车：做新需求时顺手还（每次需求留 10–20% 时间）
② 前置：新需求的前置条件（"不改这里做不了"）
③ 专项：单独排期（只用于高风险债：安全、可用性）
```

### 搭车还债的具体做法

```
需求：给订单列表加"按状态筛选"
搭车：把订单查询的数据访问层抽出来（写测试），再实现筛选

结果：
- 需求按时交付（甚至更快，因为有测试）
- 技术债还了一部分
- 不需要单独申请排期
```

**关键：搭车的范围要小**（一次只动一个函数/一个文件），否则会变成"顺手重构了整个模块"。

### 拒绝"大重构"的理由

```
① 时间长（3 个月不见效）
② 风险高（一次上线全量替换）
③ 业务方无法接受（"三个月没新功能"）
④ 中途需求变更 → 重构方向要改 → 白做
```

**替代方案：绞杀者模式（Strangler Fig）**

```
① 新代码与老代码并存
② 入口逐步切到新代码（按功能/按比例）
③ 老代码流量归零后删除
```

好处：**每一步都可以上线、可以回滚，业务不受影响**。

### 还债的度量（怎么证明有效）

```
① 需求交付周期（从提出到上线）有没有变短
② 变更失败率有没有下降
③ 平均恢复时间（MTTR）有没有下降
④ "只有某个人能改"的模块数量有没有减少
```

**没有度量，还债就永远排不上优先级**。

### 团队层面的三个动作

**① 建"技术债登记表"**

```markdown
| 位置 | 类型 | 影响 | 利息（每季度浪费时间） | 建议动作 | 状态 |
| --- | --- | --- | --- | --- | --- |
| order/service.go | 代码债 | 改一次要验证 3 天 | 12 人日 | 补测试+拆接口 | 待排期 |
| 部署 | 基础设施债 | 手工 40 分钟 | 8 人日 | 脚本化 | 进行中 |
```

**② 每个迭代留固定比例**

```
10%–20% 的容量用于还债（不要 0，也不要 50%）
0% → 债越滚越大
50% → 业务方会觉得"你们不干活"
```

**③ 定义"新债不许借"的规则**

```
新代码必须有测试（至少核心路径）
新增依赖必须有人维护（不是"随便引一个库"）
新增服务必须有监控与 Runbook
```

**最有效的还债是"不再借新债"**。

### 检查清单

```
□ 有技术债登记表（含位置、影响、利息）
□ 每个迭代留 10%–20% 容量
□ 优先还"影响可用性/阻塞需求/有安全风险"的
□ 大改造用绞杀者模式（可逐步上线）
□ 还债挂在具体需求上（不说"重构"，说"为了做 X"）
□ 有度量（交付周期、失败率、MTTR）
□ 新代码有测试、监控、Runbook 的硬要求
□ "即将下线"必须有下线日期
```
