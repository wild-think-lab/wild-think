### 四个 DORA 指标

```
① 部署频率（Deployment Frequency）
② 变更前置时间（Lead Time for Changes）
③ 变更失败率（Change Failure Rate）
④ 恢复时间（MTTR / Failed Deployment Recovery Time）
```

**"这四个是一组的"**：单看一个容易作弊。

### 前置时间怎么算

```
需求进入 → 代码提交 → 部署到生产
```

**关键**：

```
不是"从写代码开始"，而是"从需求被受理开始"
（否则会漏掉"排队等待"的大头）
```

**"前置时间 3 天但 2 天在等评审"** → 优化点在流程，不在编码。

### 变更失败率

```
需要回滚/热修/紧急补丁的发布 / 总发布
```

**"失败率 0%"** → 可能是"发布太少"或"没统计"。

### 五个"指标好看但交付更慢"

**① 只盯部署频率**

```
把一次发布拆成 10 次小发布 → 频率上去了，价值没变
```

**② 只盯 MTTR**

```
快速重启回滚 → MTTR 好看，根因没修（会复发）
```

**③ 用"代码行数/提交数"度量**

```
鼓励"多写多改"，与质量无关
```

**④ 用"故事点完成率"考核个人**

```
→ 大家开始"估小 + 挑简单的"
```

**⑤ 指标成为 KPI**

```
数字被人为优化（拆分发布、隐藏失败）→ 指标失效
```

**"指标用来改进流程，不用来考核个人"** 是底线。

### 一个"可持续"的用法

```
① 团队维度看趋势（不是个人排名）
② 每季度选 1–2 个指标改进
③ 改进措施要具体（如"减少评审等待"）
④ 下季度复测
```

**"四个指标全都要涨"** 不现实（频率与失败率存在张力）。

### 配套的过程指标（可选）

```
① 评审等待时长
② 构建时长 / 流水线成功率
③ 缺陷逃逸率（上线后发现的问题占比）
④ 值班被叫醒次数
⑤ 平均修复时长（按严重度分层）
```

**"过程指标"用来定位"卡在哪"**，不是用来排名。

### 数据从哪来

```
① CI/CD 平台（部署次数、失败、时长）
② 代码平台（PR 时长、评审等待）
③ 需求系统（受理到上线）
④ 监控/告警（MTTR、故障次数）
```

**"手工填表"** 的指标不可持续（三个月后没人填）。

### 检查清单

```
□ 四个 DORA 指标都有（自动采集）
□ 前置时间从"需求受理"算起
□ 变更失败率含"回滚/热修"
□ 指标按团队看趋势，不做个人排名
□ 每季度只改 1–2 项
□ 有过程指标定位瓶颈
□ 数据自动采集（不靠填表）
□ 指标与改进措施一一对应
□ 不当 KPI 用（防作弊）
```
