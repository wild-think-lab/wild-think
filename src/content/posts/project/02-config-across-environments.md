### 问题的真实形状

第一版只有 6 个配置项，写死在代码里也能跑。半年后：

```text
数据库地址 × 3（主/从/报表）
缓存地址 × 2（本地/集群）
消息队列、对象存储、第三方 API 密钥、开关项……
```

**120 个配置 × 4 个环境 = 480 个值**，还得保证它们互不错配。靠人记是不现实的。

### 三条原则

1. **配置与代码分离**：代码里不出现 IP、密码、环境名。
2. **环境只有差异，没有副本**：每份 env 文件只写"和基线不同的部分"。
3. **缺配置就启动失败**：宁可起不来，也不要带着默认值跑错环境。

第 3 条最重要。用一个默认的连接串启动到错误环境，比直接启动失败危险一百倍。

### 分层配置文件

```text
config/base.yml          # 所有环境共用
config/dev.yml           # 只写差异
config/prod.yml
```

合并逻辑：`base` 为底，环境文件覆盖。启动时打印最终生效的关键项（脱敏）——这一步能挡掉大量"配错环境"的事故。

### 配置校验

```yaml
# 启动时必做
required:
  - DB_HOST
  - DB_PORT
  - REDIS_URL
ranges:
  DB_PORT: { min: 1, max: 65535 }
  POOL_SIZE: { min: 5, max: 200 }
```

校验要覆盖三类：**必填项缺失、格式/范围非法、值与环境不匹配**（比如 dev 环境指向了生产域名）。

### 密钥怎么放

| 方式 | 适合 | 风险 |
| --- | --- | --- |
| 环境变量 | 单机、容器 | 日志里容易被打印出来 |
| 密钥管理服务（Vault/KMS） | 多环境、有审计要求 | 多一个依赖 |
| 加密文件 + 启动解密 | 小团队 | 解密密钥本身怎么管 |

底线是三条：**不进 Git、不进镜像、不进日志**。三条里破任意一条，等于公开。

### 变更的可追溯

```text
谁改了、改了哪个键、从什么值改成什么值、什么时候生效
```

没有这条，出事后只能靠猜。做法很简单：配置变更走评审 + 变更记录表（哪怕就是一个 Git 仓库 + 提交历史）。

### 一个反例

```text
现象：预发环境订单一直写进生产库
原因：预发配置复制自生产，只改了 DB_HOST 的注释，没改值
修复：配置校验里加"环境标识与域名/库名一致性检查"，不一致直接启动失败
```

### 本章要点

- 配置与代码分离，环境只写差异。
- 缺配置就启动失败，绝不带默认值兜底。
- 密钥三不：不进 Git、不进镜像、不进日志。
- 配置变更必须有记录，否则排障只能靠猜。
