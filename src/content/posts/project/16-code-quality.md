### 三类规则

```
① Bug（确定性缺陷）：空指针、资源未关闭、相等判断错
② Vulnerability（安全）：硬编码密码、SQL 注入、弱加密
③ Code Smell（可维护性）：重复代码、过长函数、命名
```

**实践建议**：

```
Bug 与 Vulnerability：严格（阻塞）
Code Smell：宽松（不阻塞，只提示）
```

**"把 Code Smell 做成阻塞"** 会让所有人恨你（老代码一堆）。

### 质量门的正确姿势

**不要用"全量"卡**：

```
老项目全量扫描 → 几千个问题 → 永远不达标 → 门禁被绕过
```

**用"新代码"卡**：

```
Quality Gate on New Code：
  新代码覆盖率 ≥ 80%
  新代码重复率 ≤ 3%
  新代码 0 个 Bug / 0 个 Vulnerability
```

**"新代码零新增问题"** 是可执行、可持续的做法。

### 覆盖率怎么算才不假

```
① 单元测试覆盖率（jacoco/coverage.py 等）
② 只算"新增代码"的覆盖
③ 排除"生成的代码/纯配置"
```

**"为了覆盖率写空断言测试"** 很常见：

```
断言了什么都没验证的测试 → 覆盖率上去了，质量没上去
→ Code Review 要看测试的"断言质量"
```

### CI 里怎么接

```yaml
# GitLab CI 片段
sonar:
  image: sonarsource/sonar-scanner-cli
  script:
  - sonar-scanner
      -Dsonar.projectKey=$CI_PROJECT_PATH_SLUG
      -Dsonar.sources=src
      -Dsonar.host.url=$SONAR_URL
      -Dsonar.token=$SONAR_TOKEN
      -Dsonar.qualitygate.wait=true
```

**`qualitygate.wait=true`** 让流水线真正"等结果"（否则扫完就过）。

**"没有 wait"是最常见的假门禁**。

### 五个"上线就全员抵触"的做法

**① 第一次就开"全量阻塞"**

```
存量问题几千个 → 无法通过 → 大家找领导要求关掉
```

**② 覆盖率卡得太高（新代码 100%）**

```
正常业务代码不可能 100%（异常分支/防御代码）
→ 80% 左右是合理线
```

**③ 规则开了"全部"**

```
几千条规则 → 满屏提示 → 没人看
→ 只开团队认可的核心规则集
```

**④ 不给出"怎么改"**

```
只报"这里有 smell" → 开发者不知道正确做法
→ 规则描述里给示例
```

**⑤ 扫描太慢（半小时）**

```
每次提交都跑全量 → 阻塞节奏
→ 增量扫描 / 只扫变更模块
```

### 规则集的推荐组合

```
必开（阻塞）：
  ▸ 空指针风险
  ▸ 资源未关闭
  ▸ SQL 注入 / 命令注入
  ▸ 硬编码凭证
  ▸ 弱哈希（MD5/SHA1 用于安全场景）
  ▸ equals/hashCode 不一致

提示（不阻塞）：
  ▸ 函数过长（> 80 行）
  ▸ 参数过多（> 5）
  ▸ 重复代码块
  ▸ 命名规范
  ▸ 注释缺失（public API）
```

### 与技术债管理结合

```
① 扫描结果导成"技术债清单"
② 按"修改成本 × 风险"排序
③ 每个迭代固定还一点（如 10% 工时）
④ 新代码零新增（防止债越滚越大）
```

**"只扫不改"是另一种浪费**。

### 检查清单

```
□ 用"新代码"作为门禁口径
□ Bug/安全 阻塞，Smell 提示
□ 覆盖率按新增代码算（80% 左右）
□ CI 里 qualitygate.wait=true
□ 规则集精简且团队认可
□ 有"怎么改"的说明/示例
□ 扫描时长可接受（增量）
□ 结果进入技术债清单并排期
□ 有趋势图（问题数是否在降）
□ 门禁不被"领导特批"绕过（有例外流程）
```
