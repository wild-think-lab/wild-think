### 评审的五问

```
① 这个设计解决什么问题（不解决会怎样）
② 失败会怎样（最坏情况）
③ 10 倍流量会怎样
④ 出问题怎么发现、怎么回滚
⑤ 谁来维护，后续成本
```

**"五问都能答上来"** 才算方案可落地。

### 必看的六个方面

**① 数据流与边界**

```
请求从哪进、经过谁、存哪、谁读
边界在哪（信任边界/故障边界）
```

**② 状态与一致性**

```
有没有"必须强一致"的地方
不一致时的补偿/对账手段
```

**③ 依赖与单点**

```
依赖谁（DB/MQ/第三方）
哪些是单点，挂了影响多大
```

**④ 容量与扩展**

```
当前 QPS/数据量，增长预期
瓶颈在哪，怎么扩（加机器还是改结构）
```

**⑤ 可观测与运维**

```
怎么知道它健康（指标）
出问题怎么定位（日志/链路）
怎么发布与回滚
```

**⑥ 安全与权限**

```
谁能访问、怎么鉴权
敏感数据在哪、怎么保护
```

**"六方面里最容易漏的是 ⑤"**（方案写得很漂亮但"没法运维"）。

### 评审记录要有"结论"

```
① 通过 / 有条件通过 / 不通过
② 条件是什么（谁在什么时候补）
③ 遗留风险（明确接受，谁签字）
```

**"评审开完没有结论"** = 没评审。

### 五个"评审走个过场"

**① 方案已定，评审只是通知**

```
评审前已开发完 → 只能"事后背书"
```

**② 没有量化**

```
"性能会提升" → 没有目标数字 → 无法验收
```

**③ 评审人不是"会被影响的人"**

```
DBA/运维/SRE 不在场 → 上线才发现问题
```

**④ 只看"技术先进性"，不看"团队能不能维护"**

```
引入新技术，团队没人会 → 三个月后成孤儿系统
```

**⑤ 不记录遗留风险**

```
评审时"这个先不管" → 半年后爆了没人认
```

### 一个"轻量"的评审流程

```
1) 一页纸方案（背景/目标/方案/风险/回滚）提前 2 天发
2) 30 分钟会议：只讨论"分歧点"，不逐条念
3) 结论与条件当场记录
4) 条件项进入任务系统（有 owner 与截止日）
5) 上线前复核条件是否完成
```

**"提前发材料"** 是评审有效的第一前提。

### 三种规模对应的评审强度

| 变更规模 | 评审形式 |
| --- | --- |
| 局部改动 | PR review 即可 |
| 单服务重构 | 一页纸 + 2 人评审 |
| 跨系统/新架构 | 正式评审 + 多团队参与 |

**"所有变更都走正式评审"** → 评审疲劳，大家开始敷衍。

### 检查清单

```
□ 有变更分级（对应评审强度）
□ 一页纸方案提前发
□ 五问能答上来
□ 六方面都覆盖（尤其可观测与回滚）
□ 有量化目标
□ 相关方（DBA/运维/安全）在场
□ 结论明确（通过/有条件/不通过）
□ 条件项有 owner 与截止日
□ 遗留风险明确记录并接受
□ 上线前复核条件
```
