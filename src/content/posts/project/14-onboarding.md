### 先算一笔账

```
一个工程师上手 1 个月 vs 3 个月，团队的真实成本差：
工资 × 2 个月 + 老员工带人时间 × 2 个月
```

**"上手慢"不是新人的问题，是环境与文档的问题**。

### 新人第一天的清单（可以照着做）

```
□ 账号（SSO/邮箱/代码仓库/GitHub 组织）
□ 权限（读代码、读日志、读监控、只读生产）
□ 本地环境跑起来（能起服务、能连测试库）
□ 能跑通一次完整的构建
□ 有"第一个任务"（小而明确，1–3 天能完成）
□ 有一个指定的"带的人"（不是"有问题群里问"）
```

**"第一周就能提交一个 PR 到生产"** 是很好的目标（哪怕是很小的改动）。

### 让本地环境"一条命令起"

```bash
make dev          # 或 ./scripts/dev-up.sh
```

**必须做到**：

```
① 依赖版本固定（docker compose / nvm / pyenv）
② 测试数据自动导入（fixture/seed）
③ 有 README 写"怎么验证起来了"（不只是"怎么起"）
```

**"能起"和"能验证"是两件事**：

```
起得来但不知道对不对 → 新人依然不敢动
```

**建议 README 里有一句**：

```
「看到 http://localhost:8080/healthz 返回 ok，说明环境正常」
```

### 文档的四个必备

```
① 架构图（系统边界 + 关键依赖 + 数据流）
② 部署与发布流程（谁按哪个按钮、失败怎么办）
③ 排障手册（常见问题 → 命令 → 判据）
④ 术语表（内部黑话/缩写）
```

**"术语表"最容易被忽略但最有用**：

```
新人听不懂"那个 P0 图在 QA 环境是灰的"
→ 三个月后才知道"P0 图"是"核心链路监控大盘"
```

### 影子跟班（Shadowing）

```
第一周：跟着 on-call 看（只看不做）
第二周：一起处理（新人操作，老员工在旁边）
第三周：新人自己 on-call（老员工待命）
```

**"只看文档就上 on-call"是新人最容易崩的场景**。

**Shadowing 的产出**：

```
新人写一份"我这次处理的事件记录"（不是给领导看，是给自己）
老员工 review 一遍，指出遗漏
```

**这比任何培训材料都有效**。

### 第一个任务怎么设计

```
好的第一个任务：
① 有明确的验收标准（"这个页面能按名称搜索"）
② 改动范围小（1–3 个文件）
③ 需要走完整流程（改代码 → 测试 → review → 发布）
④ 有 review 的人

差的第一个任务：
① "熟悉一下代码"（没有产出）
② "把这个模块重构了"（太大）
③ "帮忙看下这个线上问题"（太模糊）
```

**"走完一次完整流程"比"读懂整个代码库"重要得多**。

### 五个"新人半年还不敢动生产"的原因

**① 权限给得太慢**

```
第 1 周：只给读代码
第 3 周：才给读日志
第 2 月：才给测试环境部署
```

**修法**：权限清单化，第一天就按"只读"全开，写权限按里程碑给。

**② 没有"安全的练习场"**

```
只有生产环境 → 没人敢动
```

**修法**：有独立的测试环境 + 可随意重置的测试数据。

**③ 发布流程黑箱**

```
"发布找 XX 同学，他会帮你发"
→ 新人永远学不会
```

**修法**：发布是"按钮/命令"，文档写清楚，新人自己发一次（有人陪）。

**④ 出事就"老员工上"**

```
新人遇到问题，老员工直接接手
→ 新人没有"自己解决一次"的经验
```

**修法**：老员工只给"提示"，不直接动手（除非影响生产）。

**⑤ 没有"犯错的空间"**

```
一次小错就被严厉批评 → 之后只做最保守的事
```

**修法**：区分"可回滚的小错"（鼓励尝试）与"高危操作"（严格审批）。

### 一份"上手进度表"（可直接用）

| 时间 | 目标 | 验收 |
| --- | --- | --- |
| Day 1 | 账号权限齐全 | 能登录所有系统 |
| Day 2–3 | 本地环境跑通 | 能起服务并通过健康检查 |
| Week 1 | 提交第一个 PR | 已合并 |
| Week 2 | 独立发布一次 | 自己按流程发布到测试环境 |
| Week 3 | 参与一次 on-call | 跟着处理并写记录 |
| Month 1 | 独立处理一个 P2 | 自己定位并修复 |
| Month 2 | 参与一次架构评审 | 能提出问题 |

**"进度表"的价值在于"可检查"**，而不是形式。

### 反向指标：怎么知道上手体系有问题

```
① 新人平均第一次 PR 时间 > 2 周
② 新人前 3 个月的问题 80% 靠问人（而不是文档）
③ 老员工的"带人时间"占比 > 30%
④ 离职后知识断层明显（一问三不知）
⑤ on-call 名单里新人占比 0（半年后仍 0）
```

**"文档没人看"往往不是新人不看，而是文档过期了**。

### 文档保鲜的三个机制

```
① 文档与代码同仓库（改代码时顺手改文档，review 时能看见）
② 每个文档有"最后验证时间"（超过 3 个月要复核）
③ on-call 时发现问题 → 当场补文档（而不是"回头补"）
```

**"回头补"的文档永远不会补**。

### 检查清单

```
□ 第一天账号权限齐全（只读全开）
□ 一条命令起本地环境 + 健康检查方法
□ 四份必备文档（架构/发布/排障/术语表）
□ 有 One-on-one 指定的带的人
□ 第一个任务小而有完整流程
□ 影子跟班（看 → 一起 → 独立）
□ 有可重置的测试环境
□ 发布流程文档化且新人能自己发
□ 老员工"给提示"而不是"直接接手"
□ 区分"可回滚小错"与"高危操作"
□ 文档与代码同仓 + 最后验证时间
□ 有上手进度表可检查
```
