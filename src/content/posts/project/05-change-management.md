### 为什么"小心一点"不管用

人都会犯错，流程的作用不是让人不犯错，而是**让错误可发现、可回退、影响可控**。

三个数字能说明问题：生产事故里，**约 70% 由变更引起**（配置改动、发版、扩容、权限调整）。所以变更管理不是形式主义，它是最有效的降事故手段。

### 变更分级

| 级别 | 例子 | 审批 | 窗口 | 回滚要求 |
| --- | --- | --- | --- | --- |
| A（重大） | 数据库大版本升级、网络架构调整、核心链路切换 | 双人复核 + 负责人批 | 单独约窗口 | 必须演练过 |
| B（常规） | 应用发版、配置调整、扩缩容 | 单人复核 | 固定窗口 | 有回滚脚本 |
| C（低风险） | 日志级别调整、非核心参数 | 自审 | 随时 | 记录即可 |
| D（紧急） | 线上故障修复 | 事后补录 | 立即 | 修复优先 |

分级的价值是**把审批精力放在 A 类**。所有变更都走同一套流程，结果是大家都糊弄。

### 发布窗口怎么定

三个约束条件：

1. **业务低谷**：电商在 20:00–22:00 不发布；企业内系统在上班时间不发布。
2. **有人在**：窗口内必须有开发 + 运维 + 能拍板的人在线。凌晨 3 点一个人发版，出事没人帮。
3. **离监控观察期足够**：发布后至少观察 30–60 分钟，所以窗口要在"业务高峰前 2 小时"结束。

经验值：**周二到周四的 20:00–22:00** 是多数团队的最佳窗口（周一都在处理积压，周五出事没人跟）。

### 变更清单：写什么才算合格

一份能用的变更单至少包含：

```
1. 变更内容：改什么（精确到文件/参数/镜像 tag）
2. 变更原因：为什么现在改（工单号、需求号）
3. 影响范围：哪些服务/用户/接口会受影响
4. 前置检查：发布前要确认的状态（备份、容量、依赖）
5. 执行步骤：按顺序、可复制的命令
6. 验证方法：怎么算"发布成功"（具体指标 + 阈值）
7. 回滚步骤：怎么退、退到哪、多久能退完
8. 观察项与时长：发布后盯什么、盯多久
9. 联系人：谁执行、谁复核、谁拍板
```

第 7 项是关键。**没有回滚方案的变更，本质上是赌博。**

### 回滚的四种形态

| 形态 | 适用 | 耗时 |
| --- | --- | --- |
| 镜像回滚（`rollout undo`） | 应用发版 | 秒级 |
| 配置回滚（保留旧文件 + reload） | 配置调整 | 秒级到分钟 |
| 数据回滚（备份恢复 / 反向 SQL） | 数据变更 | 分钟到小时 |
| 架构回滚（切流回旧集群） | 大改造 | 分钟级（要提前演练） |

数据回滚最难，所以两条纪律：

1. **数据库变更必须前向兼容**：新增字段先加后用，删字段先停用再删（至少隔一个版本）。
2. **破坏性操作前必须有备份 + 恢复验证**，光有备份不算，得确认能恢复。

### 变更冻结期

这些时段禁止非紧急变更：

- 大促、结算日、财报期
- 长假前后 3 天（人不在）
- 重大活动期间
- 刚发生过 P1 故障的 24 小时内（先稳定，别叠风险）

冻结期要**提前公告**，而不是当天临时通知。

### 紧急变更通道

必须有，否则大家会绕过流程。要求三件事：

1. **先止损，后补流程**：故障优先，别让人一边救火一边填表。
2. **24 小时内补录变更单**，写清实际做了什么。
3. **事后复盘**：为什么没走常规流程（是流程太重，还是判断失误）。

紧急通道被滥用，说明常规流程设计得不合理——该简化 B 类，而不是取消审批。

### 双人复核（Four Eyes）

A/B 类变更的执行方式：

- **一人读步骤，一人敲命令**（或一人操作一人看屏幕）。
- 或者"操作者在跳板机上执行，复核者在会议里同步看输出"。

这一步能拦住的错误比想象中多：复制错 IP、漏了某个环境、命令少了个参数，都是"第二双眼睛"能立刻发现的。

### 一份可直接用的模板

```markdown
## 变更单 #CHG-2026-1127

**级别**：B
**窗口**：2026-11-27 20:00–21:00
**执行人**：@ops-a　**复核**：@dev-b　**拍板**：@lead-c

### 1. 变更内容
订单服务镜像从 `order-api:1.4.1` 升级到 `1.4.2`（修复支付回调重复问题）。

### 2. 原因
工单 OPS-2311，线上出现回调重复扣款（已止损）。

### 3. 影响范围
订单创建与支付回调接口；预计 30 秒内滚动更新，无中断。

### 4. 前置检查
- [ ] 镜像已推送到 registry 且可拉取
- [ ] DB 迁移脚本已在 staging 执行成功
- [ ] 当前无进行中的其他变更
- [ ] 监控与告警正常

### 5. 执行步骤
kubectl -n prod set image deploy/order-api api=registry/order-api:1.4.2
kubectl -n prod rollout status deploy/order-api --timeout=180s

### 6. 验证
- 5xx 比例 < 0.5%（当前 0.1%）
- 支付回调成功率 = 100%（抽样 20 笔）
- P99 延迟 < 300ms

### 7. 回滚
kubectl -n prod rollout undo deploy/order-api
预计 60 秒完成；数据层无变更，无需回滚数据。

### 8. 观察
发布后观察 60 分钟，重点看回调重复率与错误日志。
```

### 变更之后：记录与复盘

- 每次变更留下"实际执行记录"（谁、几点、结果），别只留计划。
- 出问题的变更**必须复盘**，且复盘结论要落到"流程改哪里"，而不是"下次注意"。
- 定期统计：变更成功率、回滚率、平均恢复时间。这三个数能反映流程健康度。

### 一句话总结

变更管理不是给运维加负担，而是**把"敢不敢改"变成"知道怎么退"**。有窗口、有清单、有回滚，才谈得上频繁发布。
