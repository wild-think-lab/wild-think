### 三种文档，三种读者

| 文档 | 读者 | 回答的问题 |
| --- | --- | --- |
| README | 新来的人 | 这是什么、怎么跑起来 |
| ADR（架构决策记录） | 未来的自己/同事 | **为什么这样做** |
| Runbook | 值班的人 | 出问题了怎么办 |

**最常见的错误**：只写了 README（怎么跑），没写"为什么这样设计"和"坏了怎么办"。

### README：三分钟能跑起来

模板：

```markdown
# 项目名

一句话说明它做什么。

## 快速开始

```bash
git clone ...
cd ...
make up        # 或 docker compose up -d
curl localhost:8080/health   # 期望返回 ok
```

## 它解决什么问题

（2–3 句，说明业务背景，不要写技术栈罗列）

## 架构

（一张图 + 3 句说明数据流）

## 配置

| 变量 | 说明 | 默认值 |
| --- | --- | --- |
| DB_URL | 数据库连接 | 无（必填） |

## 常见问题

- 启动报 xxx → 原因 → 解决
```

**验收标准**：让一个没接触过项目的人，**不看别的文档，30 分钟内跑起来**。

### ADR：记录"为什么"

格式（很短，一页就够）：

```markdown
# ADR-001：用 PostgreSQL 而不是 MySQL

- 状态：已采纳
- 日期：2026-11-27
- 决策人：xxx

## 背景
需要支持 JSONB 查询与部分索引，且团队更熟 PG。

## 决策
主库使用 PostgreSQL 16。

## 后果
- 好：JSONB 查询与 GIN 索引可直接用；逻辑复制的 DDL 支持更好
- 坏：部分运维工具链需要重学；MySQL 的生态工具（如某些审计插件）不可用
- 风险：团队上手需要 2 周

## 备选方案
- MySQL 8.0：JSON 支持可用但不便；团队更熟
```

**ADR 的价值不是"记录正确"，而是"记录当时的取舍"**。半年后有人问"为什么不用 X"，翻 ADR 就知道了。

规则：

```
① 一个决策一个文件，编号递增
② 只增不改（要改就写新的 ADR 并标记旧的为"已废弃"）
③ 放在仓库 docs/adr/ 下，跟代码一起 review
```

### Runbook：值班时能照着做

模板：

```markdown
# Runbook：订单服务 5xx 升高

## 症状
- 告警：order-api 5xx 率 > 1% 持续 5 分钟
- 用户反馈：下单失败

## 影响
下单链路中断，影响营收。分级 P1。

## 第一步：确认范围
```bash
kubectl get pods -n prod -l app=order-api
kubectl logs -n prod deploy/order-api --tail 100 | grep -c ERROR
```
判断：是全部实例还是个别实例？

## 第二步：常见原因（按概率排序）
1. 数据库连接池耗尽 → 查 `pg_stat_activity` 连接数
2. 下游支付超时 → 查支付网关状态
3. 发布引入的 bug → 看最近 30 分钟有无发布

## 第三步：止血
```bash
# 如果是发布引起：回滚
kubectl rollout undo deploy/order-api -n prod
```

## 第四步：验证
- 5xx 率回到 < 0.1%
- 下单成功率恢复正常

## 升级路径
15 分钟内未恢复 → 通知 @xxx（电话）
```

**Runbook 的验收标准**：**半夜被叫醒、脑子不清醒的人，照着能做完**。

### "文档没人看"的三个原因

**① 找不着**

```
文档散落在：wiki、Git 仓库、聊天记录、某人的本地文件
```

对策：**一个入口**（如 `docs/` 目录 + 索引页），从 README 链过去。

**② 过期了**

旧的部署步骤还在，按它做会出错。

对策：

```
- 文档与代码同仓库（改代码的 PR 里一起改文档）
- 关键文档有"最后验证日期"
- 定期抽查（每季度挑 3 篇按步骤走一遍）
```

**③ 太长**

一篇 50 页的"运维手册"，没人会读完。

对策：**按场景拆分**——"部署"一篇、"排障"一篇、"备份恢复"一篇，每篇不超过 2 屏。

### 写作的三条硬规则

```
① 先写"给谁看、解决什么问题"，再写内容
② 步骤必须可执行（有命令、有期望输出）
③ 每篇结尾写"最后验证：YYYY-MM-DD"
```

第②条最重要：**"配置好数据库"不是步骤，"执行 `createdb app`，期望无报错"才是**。

### 一个团队的最小文档集

```
docs/
├── README.md              项目入口
├── ARCHITECTURE.md         一张图 + 数据流
├── adr/                    决策记录
├── runbooks/               每个关键服务的排障手册
├── deploy.md               部署步骤（含回滚）
└── oncall.md               值班表与升级路径
```

七份文档，覆盖"上手、理解、决策、救火"四类需求。

### 检查清单

```
□ README 能让新人 30 分钟跑起来
□ 关键决策有 ADR（含备选方案与取舍）
□ 每个 P1 服务有 Runbook（含第一步命令与升级路径）
□ 文档与代码同仓库
□ 有统一的文档入口
□ 关键文档有最后验证日期
□ 每季度抽查 3 篇按步骤走一遍
```
