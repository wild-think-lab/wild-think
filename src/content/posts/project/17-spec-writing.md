### 六段结构（一页纸）

```
① 背景与问题（为什么现在要做）
② 目标与非目标（做到什么、明确不做什么）
③ 方案（核心设计 + 关键取舍）
④ 影响面（谁受影响、需要谁配合）
⑤ 风险与回滚（最坏情况怎么办）
⑥ 里程碑与验收（什么时候、怎么算完成）
```

**"非目标"是最容易被省略但最重要的一段**（防范围膨胀）。

### ① 背景：写"问题"不写"愿景"

**差**：

```
随着业务发展，我们需要一套更先进的架构……
```

**好**：

```
现状：订单服务单库 3.2TB，DDL 需 4 小时，写入 TPS 已到 900（上限 1000）
问题：下季度大促预计 TPS 1500，当前架构无法支撑
证据：11 月 20 日压测报告 / 近 30 天慢查询占比 8%
```

**"带数字的问题"** 才能让人相信"现在必须做"。

### ② 目标要可验收

**差**：

```
提升系统性能与可维护性
```

**好**：

```
① 大促峰值 TPS ≥ 2000（压测验证）
② P99 延迟 ≤ 100ms
③ 单表 ≤ 500GB，DDL 时间 ≤ 10 分钟
非目标：本次不改动支付链路
```

**"可验收的目标"** 才是目标，否则是口号。

### ③ 方案：先给"取舍"

```
方案 A（分库分表）：改造成本高，能撑到 5000 TPS
方案 B（读写分离 + 归档）：成本低，能撑到 1500 TPS
方案 C（换分布式数据库）：成本最高，能撑到 10000 TPS

推荐 B：满足未来 12 个月需求，成本最低；A 作为 12 个月后的预案
```

**"列方案 + 给推荐 + 说理由"** 比"只写我选的方案"更可信。

**取舍要说清"放弃了什么"**：

```
选 B → 放弃了"写入扩展性"，接受"写仍单点"
```

### ④ 影响面

```
① 哪些服务要改（清单）
② 哪些团队要配合（人）
③ 哪些监控/告警要调整
④ 哪些文档/流程要更新
⑤ 数据迁移的影响（谁需要停机/降级）
```

**"影响面清单"** 是评审时最容易漏、事后最容易被追责的部分。

### ⑤ 风险与回滚

```
风险 1：迁移期间双写不一致 → 缓解：对账任务 + 差异告警
风险 2：新库性能不达标 → 缓解：灰度 10% 流量 + 快速切回
回滚方案：保留旧库 30 天，切回耗时 ≤ 10 分钟
```

**"回滚方案"** 必须写"多久能切回、怎么切"。

### ⑥ 里程碑

```
第 1 周：方案评审 + 环境准备
第 2–3 周：代码改造 + 单测
第 4 周：灰度 10%
第 5 周：全量
验收：压测报告 + 一周观察期指标达标
```

**"验收标准"** 与第 ② 段的目标一一对应。

### 评审最常被问的五个问题

```
① 为什么不用现成方案（XX 中间件）？
② 数据量/并发量估算的依据是什么？
③ 出问题怎么回滚？多久？
④ 谁来维护？后续成本多少？
⑤ 有没有更小的第一步（能先验证的）？
```

**提前在文档里回答**，评审会顺畅很多。

### 五个"写了没人看"的原因

**① 太长（20 页）**

```
决策者只看前两页
→ 一页纸 + 附录详述
```

**② 没有结论**

```
通篇"可以考虑/建议评估" → 没人知道要批什么
→ 明确"需要批准的是 X"
```

**③ 全是技术细节，没有业务影响**

```
领导关心"影响多少用户/多少成本/多少风险"
```

**④ 没有数字**

```
"性能会提升" → 提升多少？
```

**⑤ 不写"不做会怎样"**

```
没有紧迫性 → 永远排不上优先级
```

### 检查清单

```
□ 背景带数字（现状与瓶颈）
□ 目标可验收（含非目标）
□ 至少两个方案 + 明确推荐 + 取舍
□ 影响面清单（服务/团队/监控/流程）
□ 风险与回滚（耗时明确）
□ 里程碑与验收标准对应目标
□ 一页纸能读完全貌
□ 有"需要批准的是什么"
□ 有"不做会怎样"
□ 附录放细节（不塞进正文）
```
