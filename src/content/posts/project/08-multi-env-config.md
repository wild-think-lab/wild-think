### 三种隔离方式

| 方式 | 隔离度 | 成本 | 适用 |
| --- | --- | --- | --- |
| 逻辑隔离（同一集群，namespace/前缀） | 弱 | 低 | 小团队、dev 与 test |
| 物理隔离（独立集群/独立 VPC） | 强 | 中 | staging 与 prod |
| 完全独立（独立云账号） | 最强 | 高 | 金融/合规 |

原则：**生产必须物理隔离**。逻辑隔离里"误把 prod 的配置打到 dev"这种事一定会发生。

### 配置分层

```
① 代码里的默认值（适合本地开发）
② 环境配置文件（dev.yaml / prod.yaml）
③ 环境变量（部署平台注入）
④ 密钥服务（Vault/KMS）
```

优先级从低到高。**只有 ① 可以进 Git 且不含敏感值**。

```yaml
# config/base.yaml（提交）
server:
  port: 8080
  timeout: 30s
db:
  max_conns: 10

# config/prod.yaml（提交，只覆盖差异）
db:
  max_conns: 50

# 密钥不进文件，走环境变量或 Vault
```

判断标准：**"把 prod.yaml 给别人看会不会出事"**。会 → 里面有密钥，要移出去。

### 12-Factor 的配置原则

```
在环境中存储配置（Config），而不是在代码里
```

理由：

- 同一份构建产物可以部署到任何环境（构建一次，处处运行）。
- 改配置不需要重新打包。

反例：

```python
if os.environ.get("ENV") == "prod":
    DB_HOST = "10.0.1.5"        # 硬编码
```

这会让"哪个环境用哪个数据库"分散在代码各处，且无法审计。

### 配置命名规范

```
统一前缀，避免不同来源冲突：

APP_DB_HOST
APP_DB_PORT
APP_REDIS_URL
APP_FEATURE_NEW_CHECKOUT   # 布尔用 true/false，不用 1/0
```

三条纪律：

1. **布尔值统一 `true/false`**（`1`/`yes`/`on` 混用会让解析出错）。
2. **必填项启动时校验**，缺失直接退出（不要用默认值悄悄跑起来）。
3. **敏感项用 `_SECRET` 后缀**，便于扫描与脱敏。

```python
required = ["APP_DB_HOST", "APP_DB_PORT", "APP_JWT_SECRET"]
missing = [k for k in required if not os.environ.get(k)]
if missing:
    raise SystemExit(f"missing env: {missing}")
```

### 环境差异清单

必须显式列出"哪些东西每个环境不同"：

| 项 | dev | staging | prod |
| --- | --- | --- | --- |
| 数据库 | 本地/容器 | 独立实例 | 主从集群 |
| 副本数 | 1 | 2 | 6 |
| 日志级别 | debug | info | info |
| 外部支付 | mock | 沙箱 | 生产 |
| 域名 | localhost | stg.example.com | example.com |
| 备份 | 无 | 每日 | 每小时 |

这张表要进文档，**它是"上线前检查"的依据**。

### 配置漂移怎么发现

漂移 = "实际运行的配置"与"Git 里的配置"不一致。

三种发现方式：

1. **启动时打印生效配置**（脱敏后），日志里能核对。
2. **配置接口**（`/debug/config` 只在内部暴露）。
3. **定期 diff**（IaC 场景：`terraform plan` 应该无差异）。

```bash
# 检查 K8s 里实际生效的配置与 Git 是否一致
kubectl get cm app-config -o yaml | diff - <(yq '.data' git/config.yaml)
```

**漂移是事故的前兆**：手工改过但没回写 Git 的配置，下次发布就会被覆盖，行为突变。

### 功能开关 vs 环境配置

两者的区别：

| | 环境配置 | 功能开关 |
| --- | --- | --- |
| 维度 | 环境之间不同 | 同一环境内逐步放量 |
| 存储 | 配置文件/环境变量 | 配置中心/数据库 |
| 变更频率 | 低 | 高（每天多次） |
| 谁改 | 运维/部署 | 产品/开发 |

不要把功能开关塞进环境变量——它需要动态变更，而环境变量通常要重启才生效。

### 常见错误

1. **用 `latest` 镜像 + 环境配置**：同一 tag 在不同时间部署可能是不同代码，无法复现。
2. **prod 与 staging 用不同代码分支**：staging 验证的不是要发布的东西。
3. **配置里带绝对路径**：容器化后路径全变。
4. **本地有 default、线上靠"记得配"**：忘了配就走默认值，行为与预期不符。
5. **环境变量太多（100+）**：说明该合并成分组配置或配置中心。

### 检查清单

```
□ 构建一次，所有环境用同一产物
□ 敏感值不在配置文件里
□ 必填配置启动时校验，缺失即失败
□ 启动日志打印生效配置（脱敏）
□ 环境差异有文档表
□ 生产与预发物理隔离
□ 有漂移检查机制（定期 diff 或启动校验）
```
