### 起因

一开始只是几个脚本：巡检、备份、清理日志。三个月后变成 40 个脚本，谁都不敢改，因为不知道哪个还在被定时调用。

这是大多数"内部平台"的起点。问题不在脚本，在**没有分层，就没有边界**。

### 四层结构

```text
界面层    Web / CLI / 机器人命令     —— 只负责收参数、显示结果
编排层    任务定义、依赖、重试、权限  —— 决定"谁在什么条件下执行"
执行层    Agent / SSH / API 调用      —— 真正碰到目标机器
采集层    指标、日志、资产信息        —— 只读，尽量无侵入
```

分层的判断标准很简单：**任何一层的实现方式变了，其他层不需要跟着改**。换个 SSH 库不该影响任务定义；加一个指标不该影响界面。

### 各层的关键设计

**采集层**：只读、幂等、可缓存。采集失败不能影响主流程，必须有超时与降级。

**执行层**：所有动作要有**幂等键**。同一任务重跑两次不能产生两份结果。"执行成功"要以目标状态为准（查端口、查进程），不能只看命令退出码。

**编排层**：任务 = 名称 + 目标集合 + 脚本 + 前置检查 + 超时 + 回滚动作。没有回滚动作的变更任务，不允许进生产队列。

**界面层**：只做展示与触发。**绝不在界面里写业务逻辑**，否则换个入口就要写第二遍。

### 不该自己做的三件事

| 能力 | 建议 | 原因 |
| --- | --- | --- |
| 指标存储与查询 | Prometheus / VictoriaMetrics | 时序存储的坑极多 |
| 日志收集 | Loki / ELK | 采、存、检索全链路成本高 |
| 调度与依赖 | systemd timer / Airflow / Cron | 自己写调度器必然踩并发与时区 |

平台的竞争力在"贴合自己业务的编排"，不在重复造存储和调度。

### 一条可执行的落地顺序

```text
1. 先把资产信息结构化（谁、在哪、什么角色）
2. 再把 5 个最高频脚本收敛成"任务定义"
3. 加上执行记录与审计（谁在什么时候改了哪台机器）
4. 最后才做界面
```

第 3 步最容易被跳过，但它决定了平台能不能被信任：**没有审计的自动化，等于给事故加了个加速器**。

### 本章要点

- 分层的唯一标准：下层实现变了，上层不用改。
- 执行要幂等，成功要以目标状态为准。
- 时序存储、日志、调度别自己做。
- 审计先行，界面最后。
