### 三个层次的 review

```
① 正确性：会不会出错（逻辑、边界、并发、错误处理）
② 可维护性：别人能不能改（命名、结构、重复、测试）
③ 风格：格式、命名习惯、注释（应交给工具）
```

**最大的浪费**：把 80% 的时间花在③（该由 linter 做）。

### 六类必须挡住的问题

**① 边界与空值**

```python
# 差：没考虑空列表
total = sum(items) / len(items)      # items 为空 → ZeroDivisionError

# 好
if not items:
    return 0
```

**② 错误处理被吞掉**

```go
// 差
data, _ := readFile(path)     // 忽略错误 → 后面用空数据

// 好
data, err := readFile(path)
if err != nil {
    return fmt.Errorf("read %s: %w", path, err)
}
```

**③ 并发问题**

```go
// 差：map 并发读写
var cache = map[string]string{}
go func() { cache[k] = v }()

// 好：加锁或用 sync.Map
```

**review 时要问**："这个变量被多个 goroutine/线程访问吗？"

**④ 资源泄漏**

```python
# 差
f = open(path)
data = f.read()      # 异常时 f 不关闭

# 好
with open(path) as f:
    data = f.read()
```

**⑤ 安全问题**

```
- SQL 拼字符串（注入）
- 日志打印密码/token
- 用户输入直接拼到命令（命令注入）
- 权限校验在错误的层（只在网关校验，服务内部不校验）
```

**⑥ 性能陷阱**

```
- 循环里查数据库（N+1）
- 循环里做字符串拼接（应 join）
- 没有分页的列表查询
- 在事务里做远程调用（锁持有时间长）
```

### 怎么提意见才不伤人

**三种表达方式**：

```
❌ "这里写错了"
✅ "这里如果 items 为空会除零，建议先判空"
（指出问题 + 具体场景 + 建议）

❌ "这样不行"
✅ "我理解你的考虑是…；不过如果并发上来，这里会有…，要不要考虑…"
（先承认意图，再讲风险）

❌ "必须改成 X"
✅ "nit: 命名可以更具体（非阻塞，你决定）"
（区分"必须改"与"建议改"）
```

**用前缀区分严重程度**（这是很好用的约定）：

```
blocker:  必须改（有 bug / 安全 / 数据风险）
major:    应该改（可维护性有明显问题）
nit:      可以不改（风格、措辞）
question: 我不确定，想请教
praise:   这里写得好（正向反馈也很重要）
```

### "review 太慢"的四个解法

**① 控制 PR 大小**

```
理想：< 400 行改动
超过 1000 行 → 评审质量断崖下降（人看不完）
```

**大改动怎么拆**：

```
① 先提交"纯重构"（不动行为），单独 PR
② 再提交"功能改动"（基于重构后的代码）
③ 每步都可独立上线与回滚
```

**② 明确 SLA**

```
承诺：工作时间内 4 小时内有第一次响应
超出 → 找 backup reviewer
```

**没有 SLA 的后果**：PR 挂着两天，作者只能自己合并（review 形同虚设）。

**③ 用工具挡住"机器能查的"**

```
格式（gofmt/prettier）
静态检查（eslint/golangci-lint）
类型检查（mypy/tsc）
测试覆盖率
```

**这四类必须在 CI 里自动挡**，不该占用人的时间。

**④ 分工评审**

```
按模块指定 owner：
- 前端改 → 前端 owner
- 数据库迁移 → DBA
- 基础设施 → 平台组
```

**"谁都能审"等于"没人认真审"**。

### 作者该做的四件事

```
① PR 描述写清"为什么"，不只是"改了什么"
② 自己先 review 一遍（别把明显问题丢给别人）
③ 标注"重点看哪里"（reviewer 的注意力有限）
④ 拆小 PR，一次只做一件事
```

**PR 描述模板**：

```markdown
## 为什么
订单列表在 1 万条以上时接口超时（用户反馈 3 次）

## 改了什么
1. 列表查询加分页（默认 20 条）
2. 加索引 idx_created_at

## 怎么验证
- 本地造 5 万条数据，接口从 8s 降到 80ms
- 单测覆盖分页边界（0、1、超总数）

## 重点看
- `order/repo.go` 的分页 SQL（是否用了覆盖索引）
- 迁移脚本是否能回滚
```

### 一次"review 救了生产"的实际案例

**改动**：

```go
// 原：批量删除
for _, id := range ids {
    db.Delete(&Item{}, id)
}
```

**改成**：

```go
db.Where("id IN ?", ids).Delete(&Item{})
```

**看起来是优化（N 次变 1 次），但 review 里有人问**：

```
"如果 ids 有 100 万个，这条 SQL 会不会超时或锁表？"
```

**结果**：改成按批（每批 1000 条）。

**这次 review 的价值**：避免了一次"大事务锁表"。

**这也说明**：**"只问一个问题"的 review 也是有价值的**，不必写长篇。

### 检查清单

```
□ PR 小（< 400 行为佳，不超过 1000）
□ CI 挡住格式/静态检查/测试
□ PR 描述有"为什么"与"重点看哪里"
□ 有 review SLA（4 小时内首次响应）
□ 评论区分严重程度（blocker/major/nit）
□ 按模块指定 owner
□ 关注点优先：边界/错误/并发/资源/安全/N+1
□ 有正向反馈（praise）
□ 作者先自查
```
