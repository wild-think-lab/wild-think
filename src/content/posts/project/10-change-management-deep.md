### 三类变更

| 类型 | 例子 | 审批 |
| --- | --- | --- |
| 标准变更 | 日常发布、扩容、证书续期 | 免审或轻审（有标准操作手册） |
| 常规变更 | 配置调整、中间件参数、网络策略 | 需评审 + 窗口 |
| 紧急变更 | 故障修复、安全补丁 | 事后补单，但必须有回滚 |

**分级的目的不是增加审批，而是让"高风险变更"有人看**。标准变更是因为"做过很多次、有手册、可回滚"才免审 —— 前提是**真的按手册做**。

### 变更单该写什么

一份能用的变更单，只有六项：

```
① 做什么（一句话）
② 影响范围（哪些服务、哪些用户、预计中断多久）
③ 操作步骤（可复制执行的命令，含验证步骤）
④ 回滚方案（具体命令，且已演练过）
⑤ 时间窗口（开始/结束，谁值班）
⑥ 成功判据（怎么算成功，测量方式）
```

**最常缺的是 ④ 和 ⑥**：没有回滚方案的变更，本质是赌博。

### 灰度是硬要求

```
① 小流量灰度（1%–10%，或单台机器）
② 观察指标（错误率、延迟、关键业务指标）
③ 逐步放量（10% → 50% → 100%）
④ 每步都有"停"的判据
```

判据示例：

```
灰度期间：
- 5xx 率 < 0.5%（对比基线）
- P99 延迟 < 200ms（不超过基线 20%）
- 业务指标（下单成功率）无下降
任一项不达标 → 立即回滚
```

**"观察 10 分钟没问题就全量"是最常见的错误**：很多问题要等流量峰值或缓存失效才暴露。

### 窗口期怎么选

| 变更 | 推荐窗口 |
| --- | --- |
| 常规发布 | 工作日 10:00–16:00（人在，能快速响应） |
| 数据库结构变更 | 低峰（凌晨），但要有人值守 |
| 网络/存储变更 | 周末低峰，提前通知 |
| 紧急修复 | 随时，但要走紧急流程 |

**反直觉但正确**：**日常发布不要放在周五晚上或节假日前**。不是因为"迷信"，而是故障时要有人能到岗，且上游厂商支持也在。

### 回滚的三个层次

```
① 应用层回滚（最快，秒级）：切回上一个版本/镜像 tag
② 配置层回滚（分钟级）：恢复上一份配置文件，reload
③ 数据层回滚（最难）：备份恢复 / PITR
```

**变更前确认 ① 可用**：

```bash
kubectl rollout history deploy/api -n prod
kubectl rollout undo deploy/api -n prod
```

**配置类变更必须保留上一版**：

```bash
cp /etc/nginx/nginx.conf /etc/nginx/nginx.conf.$(date +%F-%H%M)
nginx -t && nginx -s reload
```

**数据变更最难回滚** → 所以 DDL 要走"扩展-收缩"（见数据库专题），且变更当天不做数据清理。

### 一次"改配置导致全站 502"的复盘

**变更内容**：给 Nginx 加一行 `proxy_read_timeout 30s`（原本 60s），理由是"有些请求太慢占连接"。

**发生什么**：

```
变更后 20 分钟，报表导出功能全部 504/502
用户投诉集中爆发
回滚花了 15 分钟（含找备份文件的时间）
```

**根因**：

```
报表导出需要 45 秒
超时从 60s 改成 30s → 后端被 Nginx 主动断开
而"导出功能"不在变更评估的"影响范围"里
```

**流程上的三个问题**：

1. 变更单没写"影响范围"（只写了"优化超时配置"）。
2. 没有灰度（Nginx 配置直接全量 reload）。
3. 回滚方案写了"恢复备份"，但没写备份在哪、谁有权限。

**改进**：

```
① 变更单模板强制填"受影响的接口/功能清单"
② Nginx 配置变更：先改一台，观察 30 分钟，再滚动
③ 变更前把配置文件备份路径写进变更单
④ 关键超时参数加注释说明"为什么是 60s"
```

### 变更与"配置漂移"

```
变更走流程，但有人直接改线上 → 漂移
下次发布覆盖 → "我的修改怎么没了"
```

治理：

```
① 配置全在 Git（唯一真相）
② 线上直改一律禁止（有审计）
③ 定期 diff 线上与 Git（发现漂移）
```

### 小团队的可执行版本

不需要复杂的工单系统，但这四件事必须有：

```
① 一个变更记录（表格/文档即可）：时间、内容、操作人、结果
② 高风险变更有第二个人看（"四眼原则"）
③ 每个变更都有回滚命令
④ 变更后 24 小时内复盘异常
```

### 检查清单

```
□ 变更分三级，标准变更需有手册才免审
□ 变更单六项齐全（尤其回滚与成功判据）
□ 高风险变更有灰度与停的判据
□ 变更窗口避开周五晚/节假日前
□ 应用层回滚已验证可用
□ 配置变更保留上一版
□ 变更记录可查（谁、何时、做了什么、结果）
□ 定期检查配置漂移
```
