### 先分清四类文档

| 类型 | 回答什么问题 | 更新频率 |
| --- | --- | --- |
| 手册（Guide） | "这事怎么做" | 变更时更新 |
| 参考（Reference） | "这个参数是什么" | 稳定，很少改 |
| 记录（Record） | "当时发生了什么" | 一次性，不再改 |
| 决策（ADR） | "为什么这么选" | 一次性，可追加 |

**最常见的错误是只用一种形式写所有内容**：把决策写成手册（下次有人照着做却不理解为什么），或把记录当手册（把一次性操作当规范）。

### 必须有的六份文档

1. **架构概览**（一页图 + 一段话）：有哪些服务、怎么连、依赖谁。
2. **部署手册**：从零搭起来，新人照做能跑通。
3. **Runbook**：每个告警对应"先看什么、怎么判断、怎么处置"。
4. **变更记录**：每次发布的变更点、影响面、回滚方式。
5. **备份恢复手册**：备份在哪、怎么恢复、多久演练一次。
6. **值班手册**：谁值班、升级路径、常见问题。

这六份是"人不在也能运转"的底线。

### 目录结构与命名

```
docs/
├─ README.md                  入口：这个仓库是什么、怎么找
├─ architecture/
│  ├─ overview.md             一页架构
│  └─ network.md
├─ runbooks/
│  ├─ api-5xx.md              告警名对应文件名
│  ├─ db-conn-exhausted.md
│  └─ disk-full.md
├─ guides/
│  ├─ deploy.md
│  └─ backup-restore.md
├─ adr/
│  ├─ 0001-use-postgres.md
│  └─ 0002-kafka-vs-rabbitmq.md
└─ records/
   └─ 2026-11-20-outage.md
```

命名规则：

- **文件名用"现象/主题"，不用日期**（`api-5xx.md` 而不是 `20261120.md`）。
- ADR 用编号 + 短标题，编号只增不改。
- 记录类才用日期前缀。

### Runbook 的模板

```markdown
# 告警：API 5xx 比例超过 1%

## 影响
用户请求失败，影响下单链路。

## 先看什么（按顺序）
1. `kubectl -n prod get pod -l app=api` → 是否有 CrashLoop
2. Grafana「API 健康」面板 → 错误集中在哪个接口
3. 日志 `{app="api", level="error"}` 最近 10 分钟 → 高频错误信息
4. 依赖状态：数据库连接数、Redis 延迟

## 判断表
| 现象 | 结论 | 动作 |
| --- | --- | --- |
| Pod 重启中 | 发布或 OOM | 回滚上一版 |
| 只有某接口错 | 该依赖故障 | 降级/熔断该功能 |
| 全部接口错 | 基础设施 | 查 LB/DNS/证书 |

## 处置
（每步给具体命令）

## 升级
15 分钟未恢复 → 通知 @oncall-backend；30 分钟 → 通知负责人

## 事后
写记录到 records/，并在 3 天内补监控或自动化
```

关键：**判断表**。没有判断表的 Runbook 只是"命令集合"，值班的人还是不知道怎么决策。

### ADR 的模板

```markdown
# 0002 消息队列选 Kafka 而不是 RabbitMQ

日期：2026-11-20
状态：已采纳

## 背景
订单事件需要被 4 个下游消费，且要支持重放。

## 选项
A. Kafka：事件流、可重放、高吞吐；运维成本高
B. RabbitMQ：路由灵活、单条确认；消息消费后不可重放
C. Redis Stream：轻量；可靠性不足

## 决定
选 A。核心判据是"必须支持重放"。

## 代价
需要额外维护 ZooKeeper/KRaft 与监控；团队需学习分区与 offset。

## 后续
若只需任务分发（无重放需求），单独立项评估 RabbitMQ。
```

ADR 的价值：**半年后有人问"为什么不用 RabbitMQ"，答案是现成的**，不用重新开会。

### 三种死法

**① 写在个人笔记里**

文档在某人 Obsidian 里，人一走就没了。**必须进版本控制**（Git 仓库），且与代码同仓或同组织。

**② 写完就不管**

配置变了文档没变 → 下次照文档做出事故 → 大家不再信文档 → 文档彻底废弃。

修法：**把文档更新写进变更流程的 checklist**。改配置的 PR 必须同时改文档，否则不合入。

**③ 只有文档没有入口**

写了 200 篇，没人知道在哪。修法：一个 `docs/README.md` 作为唯一入口，按"我要做什么"分类索引，而不是按"文档类型"分类。

### 维护机制

三个角色，缺一不可：

| 角色 | 职责 |
| --- | --- |
| 作者 | 变更时同步更新 |
| 审阅 | 季度抽查 3 篇，验证"照着做能不能跑通" |
| 清理 | 半年未更新的标记 `stale`，一年未更新的归档 |

自动化检查（低成本高收益）：

```bash
# 找出 90 天未更新的文档
find docs -name '*.md' -mtime +90 -not -path '*/records/*'
```

```yaml
# CI 里检查：改代码但没改 docs 时提示
- name: docs check
  run: |
    if git diff --name-only HEAD~1 | grep -q '^src/'; then
      git diff --name-only HEAD~1 | grep -q '^docs/' || echo "::warning::代码改了但文档没改"
    fi
```

### 一句话总结

文档体系的价值不在"写得多"，而在**三类信息能被对应的人在对的时候找到**：新人找手册、值班找 Runbook、后来人找决策。按这三条设计目录，比写 100 篇杂文有用。
