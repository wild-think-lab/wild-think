### 一个判断标准

面试官问"服务器 CPU 100% 了怎么办"，不是要你背命令，而是在听三件事：

1. 你有没有**分类框架**（CPU/内存/IO/网络/外部依赖）。
2. 你会不会**按顺序收敛**（先看整体再看进程，先看现象再看原因）。
3. 你有没有**验证与边界**（怎么确认修好了、什么情况下我的结论不成立）。

背命令的人会在第三层露馅。

### 答题四步模板

**第一步：澄清**（10 秒）

"是单台还是整批？业务是变慢还是完全不可用？最近有变更吗？"

这三个问题决定了排查方向：整批 → 平台/网络；单台 → 主机；最近有变更 → 先看变更。

**第二步：分层定位**

"我先分清是 CPU 打满、内存换页、磁盘 IO 饱和，还是外部依赖慢。"

**第三步：给验证动作**

"`uptime` 看 load，`vmstat 1` 看 `r/b/si/so/wa`，`iostat -xz 1` 看 `%util` 与 `await`，`pidstat -u -d 1` 定位进程。"

**第四步：说处置与边界**

"如果确认是单核打满，加机器没用，要改多进程；如果是 IO 饱和，先摘掉备份/日志刷盘任务。"

### 四道高频题的完整答法

#### 题一：CPU 使用率 100%

答：

1. 先确认是 `us` 高还是 `sy` 高。`us` 高 = 应用计算，`sy` 高 = 系统调用密集（大量 IO、网络、fork）。
2. 看是否单核：`mpstat -P ALL 1`。单核 100% 是单线程瓶颈，扩容无效。
3. 定位进程：`top` → `pidstat -u -t 1` → 线程级。
4. 应用侧：Java 看 GC（`jstat -gcutil`），Python 看是否 GIL 阻塞，Go 看 `pprof`。
5. 处置：限流 → 优化 → 扩容，顺序不能反。

边界："如果 load 高但 CPU 空，那不是 CPU 问题，去查 IO 或 D 状态进程。"

#### 题二：磁盘满了，但 `du` 找不到大文件

这是经典题，答出三点就能加分：

1. **被删除但被进程占用**：`lsof +L1` 找 deleted 文件，重启或 `: > /proc/<pid>/fd/<n>` 释放。
2. **inode 满**：`df -i`，大量小文件（session、缓存碎片）。
3. **保留块**：`tune2fs -l` 看 reserved blocks（默认 5%），`df` 显示和使用有差异。

处置：先清日志（logrotate 配置错），再谈扩容。

#### 题三：网站能 ping 通，但打不开

答：

1. 分层：DNS → TCP → TLS → HTTP → 应用。
2. `dig` 域名解析，`curl -v` 看卡在哪一步，`ss -tnp` 看连接是否建立。
3. 常见原因：DNS 指错、443 端口没开、证书过期、后端 502、连接池耗尽、WAF 拦截。
4. 判断依据：`curl` 返回码（连接超时 vs 有响应但 5xx）。

加分："如果是部分用户打不开，先怀疑 CDN 与 DNS 缓存，再怀疑地域网络。"

#### 题四：数据库变慢，怎么定位

答：

1. 先分清：连接慢（网络/连接池）、查询慢（索引/锁）、写入慢（IO/锁竞争）。
2. 工具：`SHOW FULL PROCESSLIST`、慢查询日志、`EXPLAIN`、`performance_schema.data_lock_waits`。
3. 看是否长事务持有锁、是否有全表扫描、是否有大结果集排序。
4. 处置：加索引 / 拆查询 / 缩短事务 / 读写分离 / 缓存。

边界："如果 QPS 没涨但变慢，优先怀疑锁与 IO，而不是索引。"

### 面试官最反感的三种回答

- **一上来报命令清单**，没有顺序与逻辑。
- **只说"重启一下"**，没有根因。
- **过度自信**，不给边界条件（"肯定是索引问题"）。

### 一个可以通用的表达结构

```
现象 → 分层假设（2–3 个） → 用哪个指标/命令区分 → 处置顺序 → 如何验证已恢复 → 什么情况下我判断不了
```

这六段讲完，即使结论不完美，面试官也会认为你"会干活"。

### 加分项：把故事讲成案例

"上周线上出现过一次，CPU 90% 但 load 只有 2，最后发现是监控采集脚本在单核压缩日志。我们把它改成多线程并限了 CPU 配额。"

具体案例 + 具体数字 + 具体处置，比任何理论都可信。
