### 简历只解决一件事

**让面试官产生"想问他两句"的冲动。**

如果简历上写"负责服务器日常运维、参与项目建设、熟悉 Linux"，面试官不会追问，因为你没给他钩子。

钩子 = 具体数字 + 具体技术 + 具体结果。

### 三条硬规则

1. **一条一行，写结果不写职责**。"负责监控" 是职责；"把平均故障发现时间从 40 分钟降到 6 分钟" 是结果。
2. **技术名词要能被追问**。写了"熟悉 K8s"，就必须能答 Pod 调度、探针、滚动升级。写了不懂的，等于自爆。
3. **控制在一页到两页**。三年以内一页，五年以上两页。没人看你第 3 页的"兴趣爱好"。

### 项目描述的写法

推荐结构（比 STAR 更短，适合简历）：

```
项目名 | 角色 | 时间
· 背景：原来是什么状态，痛点在哪（一句话）
· 做了什么：关键技术决策 + 你的具体动作
· 结果：可量化的变化（数字）
```

示例（运维平台）：

> **内网运维平台（配置下发 + 巡检）** | 主要开发 | 2025.06–2025.12
> · 背景：300 台服务器配置靠手工改，一次变更出错率约 15%
> · 做：Ansible 角色化重构 42 个配置项，写幂等校验与失败回滚；巡检脚本产出 HTML 报告，接入企业微信告警
> · 结果：配置变更耗时从 2 小时降到 15 分钟，人为配置错误下降 90%

面试官会追问的点：幂等怎么做的？失败了怎么回滚？42 个配置项怎么分类的？——这些你都能答，因为你真做过。

### 简历上最该有的四类内容

| 类型 | 例子 |
| --- | --- |
| 稳定性成果 | 主导 3 次重大故障复盘，复发率从 60% 降到 10% |
| 效率成果 | 发布从人工 40 分钟到 CI 全自动 5 分钟 |
| 成本成果 | 通过容量治理把云资源费用降 22% |
| 体系成果 | 建立监控告警规范，噪声告警下降 80% |

没有数字时，用**范围 + 频次 + 规模**替代：200 台服务器、日均 3 次发布、日均 2TB 日志。

### 自我介绍（60 秒版）

```
我是做 X 方向的，目前在某公司负责 N 台服务器 / 某业务线的稳定性。
最擅长的是 A（举一个具体能力，如"K8s 上的故障定位"）。
最近一年主要在做 B（举一个成果，带数字）。
这次看机会主要是想往 C 方向发展。
```

关键是**给面试官一个明确的提问入口**。

### 高频追问与应答

**"你最大的技术成就是什么？"**
别说"搭了一套监控"，说"把 MTTR 从 4 小时压到 25 分钟，靠的是把告警和 runbook 绑定"。

**"你遇到最难的问题是什么？"**
选一个**有技术深度 + 有过程**的：现象 → 误判 → 关键证据 → 根因 → 修复 → 预防。别选"重启解决"的故事。

**"为什么离职？"**
中性表述："想接触更大规模的系统"、"团队在做方向调整"。不要说前公司坏话，这一条是性格测试。

**"你觉得自己最大的不足？"**
给一个真实但不致命的 + 正在改进的动作："我对成本的敏感度不够，最近在补容量与费用模型。"

### 容易被问倒的技术点（提前准备）

- **你写的脚本出过什么事故？**——答出"我加了 flock 和 dry-run 之后就没再出过"。
- **你的监控有哪些是没用的？**——承认有噪声，并说明怎么治理的。
- **如果让你重做一次，你会怎么改？**——这题考反思能力，必须有答案。
- **你怎么保证变更不出事？**——灰度、回滚、变更窗口、评审，四件套。

### 一页简历的结构

```
姓名 / 联系方式 / GitHub（可选）
一句话定位（如：5 年 Linux 运维，专注自动化与稳定性）
技能（分三层：熟练 / 掌握 / 了解，别堆砌）
工作经历（公司 / 职位 / 时间 + 2–3 条成果）
项目（2–3 个，按上面的结构写）
教育与其他（证书、开源、文章）
```

技能栏的三层分法很关键：写"熟悉"的必须能扛住追问，写"了解"的可以答不出细节。**诚实分层比什么都会更可信。**

### 最后一个建议

简历不是写出来的，是**攒出来的**。每做完一件事，立刻记下：做了什么、用了什么、结果数字是多少。半年后写简历时，你只需要挑选，而不是回忆。
