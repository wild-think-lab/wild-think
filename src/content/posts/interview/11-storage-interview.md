### 分层答法

面试存储岗的题目通常三层：

```
① 概念层：RAID 是什么、副本和纠删码的区别
② 原理层：为什么 RAID5 写性能差、Ceph 的 PG 是什么
③ 场景层：一块盘坏了怎么处理、容量规划怎么算
```

**只答概念层会被判定"背书"，能答场景层才算做过**。

### RAID 的核心取舍

| 级别 | 最少盘 | 容量利用率 | 冗余 | 写性能 | 适用 |
| --- | --- | --- | --- | --- | --- |
| RAID0 | 2 | 100% | 无 | 高 | 临时/缓存 |
| RAID1 | 2 | 50% | 1 盘 | 中 | 系统盘、小容量 |
| RAID5 | 3 | (n-1)/n | 1 盘 | **低**（写惩罚） | 读多写少 |
| RAID6 | 4 | (n-2)/n | 2 盘 | 更低 | 大容量归档 |
| RAID10 | 4 | 50% | 每镜像组 1 盘 | 高 | 数据库 |

**为什么 RAID5 写性能差**：

```
改一个块 → 要读旧数据 + 旧校验 → 算出新校验 → 写数据 + 写校验
= 2 读 + 2 写（写惩罚 4）
RAID6 更惨：写惩罚 6
```

**重建风险**（高频追问）：

```
RAID5 + 大容量盘（如 8TB）：重建要十几个小时
期间如果再坏一块 → 数据全丢
所以：大容量盘不要用 RAID5，用 RAID6 或 RAID10
```

这是一道"能看出有没有实际经验"的题。

### SSD 的写放大与寿命

```
写放大 = 实际写入闪存的数据 / 主机请求写入的数据
原因：闪存按"块"擦除、按"页"写入，改一页要搬迁整块
```

对策：

```
① 预留空间（OP）：企业级盘通常留 7%–28%
② TRIM：让盘知道哪些块可以回收
③ 4K 对齐（分区起始对齐）
④ 避免满盘运行（> 90% 时写放大剧增）
```

寿命计算：

```
DWPD（每天全盘写次数）× 容量 × 365 × 保修年数 = TBW
例：1TB、1 DWPD、5 年 → 1.8 PB
```

**回答要点**：能说出"企业级 SSD 与消费级的差别主要在 DWPD 与掉电保护（PLP）"，比背 TBW 数字更加分。

### Ceph 的关键概念

**① CRUSH 算法**

```
输入：对象名 → hash → PG ID → 一组 OSD
特点：去中心化（不需要查表），客户端自己算出位置
```

追问："加一个 OSD 后数据会怎么动？" → **只有部分 PG 会重新映射**（约 1/n 的数据迁移），不是全量重分布。

**② PG（Placement Group）**

```
PG = 数据分布的"最小调度单位"
一个 PG 内的对象共享同一组 OSD
PG 数量在创建池时定死（后续改很麻烦）
```

PG 数量建议：

```
总 PG 数 ≈ (OSD 数量 × 100) / 副本数
例：12 OSD、3 副本 → 400 个 PG
```

**③ 副本 vs 纠删码**

| | 副本（3 副本） | 纠删码（4+2） |
| --- | --- | --- |
| 容量利用率 | 33% | 67% |
| 写性能 | 好 | 差（要算校验） |
| 恢复开销 | 大（整副本重建） | 小 |
| 适用 | 热数据、VM 盘 | 冷数据、归档、对象存储 |

追问："为什么纠删码不适合虚拟机盘？" → 写放大高、延迟大、部分读要跨节点。

### 场景题：一块盘坏了怎么处理

**答法必须有顺序**：

```
① 确认故障（SMART / Ceph health / RAID 卡日志）
② 判断影响：是单盘故障还是有冗余下降
③ 立即让重建开始（如果是 RAID，热备自动顶上；Ceph 会自动回填）
④ 限制重建速率（避免影响业务 IO）
⑤ 重建期间密切监控（其他盘的健康）
⑥ 重建完成后校验（scrub）
⑦ 分析根因（是同批次盘的批次问题？）
```

Ceph 限速：

```bash
ceph tell osd.* injectargs '--osd-recovery-max-active 2'
ceph config set osd osd_recovery_sleep 0.1
ceph -s        # 看 recovering 进度
```

**加分点**：提到"重建风暴"——多块盘同时重建会把集群 IO 打满。

### 场景题：容量怎么规划

```
① 有效容量 = 物理容量 × 利用率 × (1 - 预留)
   RAID6 8 盘 × 8TB：物理 64TB，有效 (6/8) = 48TB
   再留 20% 水位 → 可用约 38TB
② 预留要算：快照、副本、重建空间、未来增长
③ 别忘了备份空间（通常是生产容量的 1.2–2 倍）
```

**常见错误**：按"物理容量"报预算，上线后发现可用只有一半。

### 场景题：性能上不去

```
分层排查：
① 客户端：是不是单线程、块大小是否匹配
② 网络：带宽/延迟（iSCSI 场景最常见）
③ 存储层：IOPS 是否打满、队列深度、缓存命中
④ 介质：机械盘的 IOPS 只有 ~150，SSD 是几万
```

一句话判断：

```
大块顺序 → 看带宽（MB/s）
小块随机 → 看 IOPS
```

### 高频"送分题"与"送命题"

| 题 | 要点 |
| --- | --- |
| RAID0 能不能做冗余 | 不能，任何一块坏全丢 |
| 热备盘的作用 | 自动顶替故障盘，缩短无冗余窗口 |
| 副本数为什么常是 3 | 2 副本时重建期间无冗余，3 副本可容忍"坏一块 + 重建中再坏一块" |
| 快照是不是备份 | 不是，同存储上，存储坏了快照一起丢 |
| 对象存储与文件存储区别 | 对象存储无目录层级，按 key 寻址，适合海量非结构化 |
| 为什么 NFS 不适合高并发写 | 单点服务端 + 锁开销，扩展性差 |

### 反问

① 你们存储规模多大？用的什么方案（Ceph/商业存储/云盘）？
