### 一、为什么 where 有索引还是很慢

```
① 索引没命中（类型隐式转换、函数包裹字段、前导列缺失）
② 索引区分度低（可选性差）
③ 回表次数太多（覆盖索引可解）
④ 数据量集中在少数值（数据倾斜）
⑤ 统计信息过期（优化器选错计划）
```

```sql
EXPLAIN ANALYZE SELECT ...;
SHOW INDEX FROM t;
ANALYZE TABLE t;
```

**"索引存在 ≠ 索引被用"** —— 这是第一道题的核心。

### 二、最左前缀原则是怎么回事

```
联合索引 (a, b, c)
能用：a / a,b / a,b,c
部分能用：a,c（c 只能用于过滤，不能用于范围优化）
不能用：b / c / b,c
```

**"a,c 能不能用"** 是常考细节：

```
8.0 的"索引跳跃扫描"（skip scan）可以部分用，但依赖优化器与统计
不要依赖它，按最左前缀设计
```

### 三、事务隔离级别与幻读

| 级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| 读未提交 | 有 | 有 | 有 |
| 读已提交 | 无 | 有 | 有 |
| 可重复读 | 无 | 无 | InnoDB 用 MVCC + 间隙锁基本解决 |
| 串行化 | 无 | 无 | 无 |

**关键点**：

```
① InnoDB 可重复读下，"快照读"看不到幻影（MVCC）
② "当前读"（for update）下用间隙锁（next-key lock）防幻读
③ 间隙锁会带来"死锁风险"
```

**"可重复读在 InnoDB 下能防幻读吗"** → 快照读可以，当前读靠间隙锁，但有代价。

### 四、为什么会有死锁

```
两个事务以不同顺序锁同一批资源
```

**真实例子**：

```
T1: update A → update B
T2: update B → update A
```

**排查**：

```sql
SHOW ENGINE INNODB STATUS\G    -- LATEST DETECTED DEADLOCK
SELECT * FROM performance_schema.data_locks;
```

**减少死锁**：

```
① 固定加锁顺序（按主键排序批量更新）
② 缩短事务（不要在事务里做 RPC）
③ 降低隔离级别（读已提交可减少间隙锁）
④ 批量更新分小批
```

### 五、主从延迟怎么办

```
① 半同步复制（至少一个从库确认）
② 读请求"强制走主"（关键读）
③ 按"业务可接受延迟"分流（报表走从库）
④ 并行复制（多线程回放）
⑤ 优化大事务（拆小）
```

**"写完立刻读"** 是最容易被延迟坑的场景：

```
写主库 → 立即读从库 → 数据还没同步 → 用户看到"没成功"
→ 方案：写后一段时间内的读走主库（或按 GTID 判断）
```

### 六、binlog 三种格式

```
STATEMENT：记录 SQL（日志小，但某些函数不确定）
ROW      ：记录行变更（最安全，日志大）
MIXED    ：自动选择
```

**生产推荐 ROW**：

```
① 复制一致性强
② 可以做"闪回/审计"（解析行变更）
③ 缺点：批量更新日志巨大
```

### 七、分库分表之后的问题

```
① 跨库 JOIN（不能做了）
② 分布式事务（用最终一致/事务消息）
③ 全局唯一 ID（雪花/号段）
④ 跨分片排序/分页（内存归并，深分页代价高）
⑤ 扩容（一致性哈希/双写迁移）
⑥ 统计报表（走数仓，不在分片库做）
```

**"分库分表不是万能"**：

```
能靠"归档 + 读写分离 + 缓存"撑住的，先别分
```

### 八、缓存与数据库一致性

```
① 先更新库再删缓存（最常用）
② 延迟双删（应对并发读写）
③ 订阅 binlog 异步删缓存（最可靠）
④ 缓存加短 TTL（兜底）
```

**"为什么不更新缓存而是删缓存"**：

```
更新缓存容易"写入顺序错乱"（两个并发写导致旧值残留）
删缓存让下次读重建，更安全
```

### 九、怎么定位"偶发慢查询"

```
① 慢查询日志（long_query_time=0.5）
② performance_schema 的 events_statements_summary_by_digest
③ 看"是否偶发"：QPS 突增 / 锁等待 / 刷脏页
④ 检查"是否同一时刻"（定时任务/备份/大查询）
```

```sql
SELECT digest_text, count_star, avg_timer_wait/1e9 AS avg_ms
FROM performance_schema.events_statements_summary_by_digest
ORDER BY avg_timer_wait DESC LIMIT 10;
```

**"偶发"往往不是 SQL，而是环境**（IO/锁/备份/网络）。

### 十、什么时候该换数据库

```
① 写入量超过单机（分片也难解）→ 分布式（TiDB/OceanBase）
② 时序/日志类 → ClickHouse/时序库
③ 强一致 + 高并发 → 换架构前先优化
④ 全文检索 → ES（但要注意一致性）
⑤ 图关系 → Neo4j
```

**"换库前先问：现有库真的到极限了吗"** —— 多数情况是"SQL 写得不好"或" schema 设计问题"。

### 面试官想听的那句话

```
"我会先看执行计划和锁等待，再判断是 SQL、索引、还是环境问题"
```

**"直接说'加索引'"** 往往暴露"只会背结论"。

### 检查清单（自测）

```
□ 能讲清"有索引但慢"的五种原因
□ 知道最左前缀的边界（a,c）
□ 能区分快照读与当前读
□ 会说死锁的排查与减少手段
□ 知道"写完立刻读"的延迟处理
□ 知道 ROW 格式的好处
□ 能列分库分表的六个连带问题
□ 会讲"删缓存而非更新缓存"的理由
□ 会用 performance_schema 找慢 SQL
□ 能说"什么时候才该换库"
```
