### 面试官在听什么

```
① 你会不会先问需求（不是上来就画架构）
② 你的取舍有没有理由（不是"业界都这样"）
③ 你知道系统的边界在哪（十万 QPS 和十亿 QPS 是两套设计）
④ 你能不能估算（容量、存储、带宽）
```

**"讲得完整"不如"讲得有理"**。

### 一套可复用的框架

```
① 澄清需求（3–5 分钟）
② 估算规模（2 分钟）
③ 接口设计（2 分钟）
④ 数据模型（3 分钟）
⑤ 高层架构（5 分钟）
⑥ 深入一两处（10 分钟）
⑦ 取舍与演进（5 分钟）
```

**别一上来就画框**。先问清楚，是加分项。

### ① 澄清需求（短链接服务）

**必问的五个问题**：

```
① 规模：每天新增多少链接？读多少？（读写比）
② 链接有效期：永久还是可配置？
③ 是否要自定义短码（vanity URL）？
④ 是否需要统计（点击数、地域）？
⑤ 是否要防滥用（恶意跳转、钓鱼）？
```

**假设（说出来）**：

```
每天新增 1000 万条，读写比 100:1
→ 写 QPS ≈ 115，读 QPS ≈ 11500
短码 7 位，永久有效
需要基础统计
```

**"说出假设"本身就是加分项**：面试官在意的是你的推理，不是数字精确。

### ② 估算

```
存储：1000 万/天 × 365 × 5 年 = 182 亿条
每条：短码 7B + 长链 100B + 元数据 50B ≈ 160B
总量 ≈ 2.9 TB（不含索引）
加索引与副本 ≈ 6 TB

读 QPS 11500，峰值 ×3 ≈ 35000
```

**关键结论**：

```
写 QPS 只有 115 → 写不是瓶颈
读 QPS 35000 → 必须靠缓存
存储 6TB → 单机 MySQL 勉强，最好分片或对象存储
```

**`35000` 这个读 QPS 决定了全部设计**。

### ③ 接口

```
POST /api/v1/links
  body: { long_url, expire_at?, custom_code? }
  resp: { short_url, code }

GET /{code}          → 302 跳转（不是 301！）
GET /api/v1/links/{code}/stats
```

**`302` 而不是 `301` 是个重要细节**：

```
301 永久重定向 → 浏览器缓存 → 统计丢失、改不了目标
302 临时重定向 → 每次请求都到服务端 → 可统计、可改
```

**主动说出这个取舍，面试官会加分**。

### ④ 数据模型

```sql
CREATE TABLE links (
  code       CHAR(7)     PRIMARY KEY,
  long_url   VARCHAR(2048) NOT NULL,
  created_at DATETIME    NOT NULL,
  expire_at  DATETIME    NULL,
  owner_id   BIGINT      NULL,
  KEY idx_owner (owner_id)
);
```

**为什么用 `code` 做主键而不是自增 ID**：

```
查询永远按 code 查 → 主键就是 code，直接命中
自增 ID 做主键会导致"按 code 查还要二级索引"
```

**长链的存储取舍**：

```
方案 A：存在 MySQL（简单，但 2.9TB 有压力）
方案 B：长链存对象存储/S3，MySQL 只存 code → 指针
```

**说出这个取舍**：数据量大时 B 更合理。

### ⑤ 高层架构

```
客户端
  ↓
CDN / LB
  ↓
API 服务（无状态，多实例）
  ↓        ↘
Redis 缓存   MySQL 分片（按 code hash）
  ↓
统计：异步写 Kafka → 数仓
```

**每个组件都要能回答"为什么有它"**：

```
Redis：读 QPS 35000，必须挡住
分片：2.9TB 单机不行
Kafka：统计不能同步写（会拖慢跳转）
```

### ⑥ 深入：短码怎么生成

**三种方案**：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 自增 ID + 进制转换 | ID 转 62 进制 | 无冲突、短 | 可被枚举（顺序可猜） |
| 随机生成 + 查重 | 随机 7 位，冲突则重试 | 不可枚举 | 高负载下冲突重试 |
| 预生成号段 | 预先批量生成，用发号器分配 | 无冲突、不可枚举 | 需维护号段 |

**推荐：预生成号段**

```
① 用发号器（如 Redis INCR 或数据库号段）取一段 ID
② 把 ID 做"打散 + 62 进制编码"（避免顺序可枚举）
③ 冲突几乎不可能（号段唯一）
```

**打散的例子**：用"乘法混淆"（`id * 素数 mod 62^7`），让相邻 ID 的编码不连续。

**"可被枚举"为什么是问题**：

```
顺序短码 → 攻击者能遍历所有链接 → 数据泄露/被爬
```

**主动提到这点，是"安全意识"的加分**。

### ⑥ 深入：缓存策略

```
① 缓存什么：code → long_url 的映射
② 缓存多久：永久有效（除非过期/删除）
③ 缓存多大：热数据（80/20 法则）
④ 缓存穿透：查不到的 code → 缓存空值（短 TTL）
⑤ 缓存一致性：改链接 → 删缓存（不是改缓存）
```

**命中率估算**：

```
天级访问集中在前 10% 链接 → 命中率 90%+
→ DB 只需承受 10% 的读（3500 QPS，轻松）
```

### ⑦ 取舍与演进

**面试官很可能问"如果 QPS 涨 10 倍"**：

```
① 缓存层加本地缓存（多级）
② MySQL 分片（按 code hash，一致性哈希便于扩容）
③ 跳转改由边缘节点处理（CDN + Edge Function）
④ 统计改"采样 + 估算"
```

**"如果成本要降低"**：

```
① 冷数据从 MySQL 移到对象存储
② 短链有效期缩短（减少存量）
③ 多级缓存减少 DB 与 Redis 压力
```

### 三个讲不明白的常见问题

**① 上来就画一堆框，不说为什么**

```
"这是 Kafka，这是 Redis" → 面试官问"为什么需要 Kafka"，答不上来
```

**对策**：每个组件说一句"因为 X 问题，所以需要 Y"。

**② 不说规模，直接讲"高并发"**

```
十万 QPS 和一百万 QPS 的设计完全不同
```

**对策**：先算，再设计。

**③ 只说"能行"，不说"代价"**

```
任何方案都有代价（成本/一致性/复杂度）
```

**对策**：每个关键选择都补一句"代价是…，但我认为值得，因为…"。

### 通用答题模板

```markdown
## 需求假设
规模：X 写 / Y 读，读写比 Z
有效期/自定义/统计：...

## 估算
存储 X TB，读 QPS Y，瓶颈在 ...

## 接口
最关键的一个取舍：（如 302 而不是 301）

## 数据模型
主键选择：为什么

## 架构
组件 + 每个组件的理由

## 深入
选一个（生成算法/缓存/分片）

## 演进
QPS ×10 / 成本减半 的应对
```

### 检查清单

```
□ 先澄清需求（规模/读写比/有效期/自定义/统计）
□ 做数量级估算（存储、QPS、瓶颈）
□ 接口里体现关键取舍（302 vs 301）
□ 数据模型说清主键选择
□ 每个组件有"为什么"
□ 深入一处讲透（生成算法/缓存/分片）
□ 主动提安全（可枚举问题）
□ 提演进路径（×10 流量、降成本）
□ 每个选择说代价
```
