### 先说面试官在考什么

```
① 会不会先问需求（而不是直接画架构）
② 会不会做容量估算（数字感）
③ 能不能识别瓶颈并给出取舍
④ 表达是否结构化（先主干后细节）
```

**"给答案"远不如"展示推理过程"**。

### 推演一：短链服务（t.cn 类）

**第一步：澄清需求**

```
① 量级：每天新增多少？读多少？（假设 100 万/天，读写比 100:1）
② 长度要求：7 位够吗？
③ 是否可自定义（自定义后缀）？
④ 有效期？过期回收？
⑤ 是否需要统计（点击数）？
```

**第二步：容量估算**

```
写：100 万/天 ≈ 12 QPS（峰值 ×3 = 36）
读：1 亿/天 ≈ 1160 QPS（峰值 ×3 = 3500）
存储：每条 ~100 字节（短码 + 长链 + 元数据）
     100 万 × 365 × 100B ≈ 36GB/年
     → 单库能撑，但 5 年后 180GB，需要考虑归档
```

**第三步：短码怎么生成**

三种方案对比：

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 自增 ID + Base62 | 短、无冲突 | 可被枚举（安全） |
| 随机 7 位 | 不可枚举 | 需查重（冲突概率随量上升） |
| 哈希（MD5 取前 7 位） | 同长链同短码（幂等） | 冲突要处理 |

**推荐**：自增 ID + Base62 + "打散"（每 N 个 ID 加一个随机偏移，或加盐后哈希再截取）。

**Base62 的容量**：

```
62^7 ≈ 3.5 万亿 → 每天 100 万可用 95 年
```

**第四步：读写路径**

```
写：
  client → API → 生成短码 → 写 MySQL → 写 Redis（cache-aside）
读：
  client → API → 查 Redis → 命中返回 302
                 → 未命中查 MySQL → 回填 Redis
```

**为什么用 302 而不是 301**：

```
301（永久）：浏览器缓存 → 后续不再请求 → 无法统计点击
302（临时）：每次都来 → 可统计、可改目标
```

**这是短链的"业务约束决定技术选择"的经典例子**。

**第五步：瓶颈与取舍**

```
① 热点短链（一条被刷 10 万次）→ Redis 单 key 热点
   → 本地缓存（Caffeine）+ 多级缓存
② 短码冲突 → 预生成池（批量生成短码，用完再补）
③ 统计点击 → 异步（写 Kafka，异步聚合）
④ 存储增长 → 按年分表 / 冷数据归档
```

### 推演二：秒杀系统

**第一步：澄清需求**

```
① 商品数量：1000 件
② 参与人数：假设 100 万同时点击
③ 是否允许超卖：绝对不允许（1 件不能卖 2 次）
④ 用户体验：抢到/没抢到要"立即"反馈
```

**第二步：核心矛盾**

```
100 万人抢 1000 件 → 99.9% 的请求注定失败
→ 目标不是"处理所有请求"，而是"快速拒绝绝大多数"
```

**这个认知是秒杀设计的分水岭**。

**第三步：分层过滤（漏斗）**

```
① CDN / 静态页（90% 流量在这里被挡住）
② 网关限流（按 IP/用户，削掉刷子）
③ 前置校验（活动是否开始、库存是否还有）
④ Redis 扣减（Lua 脚本原子扣减）← 真正的"闸门"
⑤ 异步下单（MQ → 消费者落库）
```

**每一层都在"更便宜的地方拒绝更多请求"**。

**第四步：库存扣减（最关键）**

```lua
-- Redis Lua：原子扣减
local stock = tonumber(redis.call('get', KEYS[1]))
if stock <= 0 then return -1 end
redis.call('decr', KEYS[1])
return stock - 1
```

**为什么必须 Lua**：

```
GET + DECR 两条命令之间有并发窗口 → 超卖
Lua 在 Redis 内原子执行 → 无窗口
```

**第五步：不超卖的"双保险"**

```
① Redis 扣减（挡流量）
② 数据库唯一约束 / 乐观锁（最终保证）
CREATE TABLE orders (
  ...
  UNIQUE KEY uk_user_item (user_id, item_id)   -- 一人一件
)
```

**"只靠 Redis"是不够的**：Redis 可能丢数据（主从切换）。

**第六步：用户体验**

```
① 抢到 → 立即返回"排队中"（不阻塞等落库）
② 没抢到 → 立即返回"已抢完"
③ 结果通过轮询/WebSocket 通知
```

**"让用户等 5 秒才知结果"是最差的体验**。

### 推演三：消息推送系统

**第一步：澄清需求**

```
① 规模：1 亿用户，峰值 10 万 QPS
② 类型：通知类（可延迟）/ IM 消息（实时）
③ 在线状态：是否需要感知
④ 多端：手机/PC/网页
```

**第二步：长连接是核心**

```
WebSocket（主流）/ 长轮询（兼容兜底）
```

**连接数与资源**：

```
单机 10 万连接（需调 ulimit、内核参数）
1 亿用户 × 30% 在线 = 3000 万连接 → 300 台机器
```

**这就是"推送系统机器多"的原因**。

**第三步：路由（谁在哪个网关）**

```
① 用户登录 → 分配一个网关 → 写入 Redis（uid → gateway_id）
② 发消息 → 查 Redis → 找到网关 → 网关推给连接
```

**关键问题**：网关重启后，用户重连到别的网关，路由要更新。

**第四步：离线消息**

```
① 在线：直接推
② 离线：存"离线消息表"（或 MQ），上线后拉取
③ 多端同步：每个端一个游标（已读到哪条）
```

**"已读回执"与"多端同步"是 IM 最复杂的部分**。

**第五步：可靠性**

```
① 消息不丢：客户端 ACK + 服务端重推
② 消息不重：客户端用 msg_id 去重
③ 顺序：同一会话用同一队列（保序）
```

**"至少一次 + 去重"是推送系统的标准做法**。

### 三个"通用加分项"

**① 主动说取舍**

```
"这里我用 Redis 做缓存换取延迟，代价是可能读到旧数据，
业务上短链可以接受，如果要强一致我会走数据库。"
```

**② 画"数据流"而不是"组件名"**

```
差的：画一堆框（API、Redis、MQ、DB）
好的：标上"每秒多少请求、数据多大、失败怎么办"
```

**③ 说出"容量从哪来"**

```
"按 100 万/天，均摊 12 QPS，峰值按 3 倍算 36 QPS，
单机 MySQL 能扛，所以先不分库。"
```

**数字能让方案落地，模糊描述无法验证。**

### 一个回答骨架（可直接套）

```
1. 澄清需求（3–5 个问题）
2. 容量估算（QPS、存储、连接数）
3. 核心链路（写路径 / 读路径）
4. 存储选型（为什么）
5. 瓶颈与取舍（至少两个）
6. 失败与降级
7. 如果要扩展（下一步做什么）
```

**"7 步讲完 20 分钟"比"讲 40 分钟细节"得分高**。

### 检查清单

```
□ 先问需求（不直接画图）
□ 会做容量估算（QPS/存储/连接）
□ 核心链路清晰（读/写分开）
□ 能说出"为什么选这个存储"
□ 主动说取舍与代价
□ 有失败处理与降级
□ 数字贯穿（不是模糊形容词）
□ 结构化表达（7 步骨架）
□ 能说出"下一步扩展方向"
□ 不追求完美（够用 + 可演进）
```
