### 面试官真正在听的三层

```
① 定义对不对（基础，及格线）
② 会不会用（能不能对应到排错场景）
③ 有没有边界意识（知道什么时候这套不适用）
```

**只答①就是背书**。答到②③才是"做过"。

### 十二个高频问题

**Q1：TCP 三次握手为什么不是两次**

```
标准：防止已失效的连接请求到达服务端，造成资源浪费。
加分：两次的话，客户端的历史 SYN 到达服务端 → 服务端建连 → 客户端不认 → 服务端挂着一个半开连接等超时。
      三次的核心是"双方都确认对方的接收与发送能力"。
边界：SYN 攻击正是利用"第三次没来"占满半连接队列 → syncookies 缓解。
```

**Q2：TIME_WAIT 为什么是 2MSL**

```
标准：保证最后一个 ACK 能到达，以及让旧连接的报文在网络中消亡。
加分：2MSL = 一来一回的最大生存时间。主动关闭方进入 TIME_WAIT，被动方进入 CLOSE_WAIT。
      大量 TIME_WAIT 是"主动关闭方"，通常来自短连接 → 改用长连接/连接池。
边界：tcp_tw_reuse 只在"客户端主动发起新连接"时安全，服务端别乱开。
```

**Q3：一次 HTTP 请求经历了什么**

```
标准：DNS 解析 → TCP 握手 → TLS 握手 → 发请求 → 服务端处理 → 响应 → 渲染。
加分：分层说。
  应用层：DNS（递归/迭代）、HTTP 报文
  传输层：端口、拥塞控制、重传
  网络层：路由、MTU/分片
  链路层：ARP、交换机
边界：知道哪一层出问题用什么工具查（ping/traceroute/tcpdump/curl -v）。
```

**Q4：TCP 与 UDP 的选择**

```
标准：TCP 可靠有序，UDP 快但不可靠。
加分：具体场景。
  DNS 用 UDP（请求小、要快，超时自己重试）
  音视频用 UDP（丢一帧不影响，重传反而更卡）
  HTTP/3 用 QUIC（UDP 上自己实现可靠传输，避免 TCP 层队头阻塞）
边界：不是"可靠性 vs 速度"，是"谁来做重传与拥塞控制"。
```

**Q5：一次 ping 不通怎么排查**

```
标准：从本机到目标逐层查。
加分（结构化）：
  1) 本机：ip addr / ip route（有没有地址与默认路由）
  2) 网关：ping 网关
  3) DNS：nslookup（如果是域名）
  4) 路径：traceroute / mtr（在哪一跳断）
  5) 目标：目标是否禁 ping（很多云主机默认禁 ICMP）
  6) 端口：ping 通不代表端口通，用 telnet/nc 测端口
边界：ping 不通 ≠ 服务不可用（ICMP 常被禁），要用"端口 + 应用层"验证。
```

**Q6：子网划分怎么做**

```
标准：按主机数算 2^n - 2。
加分：
  - 先算需求（每个子网要多少主机）
  - VLSM：大的先分，小的后分（避免浪费）
  - 例：需要 100/50/30/10 四个子网
      100 → /25（126 可用）
      50  → /26（62）
      30  → /27（30）→ 不够，用 /26
      10  → /28（14）
  - 留出网关与预留地址
边界：云环境的安全组/子网还受"保留地址"影响（如 AWS 每个子网保留 5 个）。
```

**Q7：NAT 的几种类型**

```
标准：SNAT（源地址转换）、DNAT（目标地址转换）、PAT（端口复用）。
加分：具体场景。
  SNAT：内网访问外网（家用路由器、云 NAT 网关）
  DNAT：外部访问内网服务（端口映射、LB）
  PAT：多个内网主机共用一个公网 IP（靠端口区分）
  Full Cone / Restricted / Symmetric：NAT 穿透（P2P、WebRTC）时才有意义
边界：Symmetric NAT 会导致 P2P 打洞失败，需要中继（TURN）。
```

**Q8：负载均衡的四层与七层**

```
标准：四层看 IP+端口，七层看 URL/Header。
加分：
  L4：性能高、透明（不改报文），但无法按 URL 路由；健康检查只能到端口
  L7：可按路径/Header/Cookie 路由、可改写、可做灰度，但要解析报文（性能略低）
  常见组合：L4（LVS/F5）在前做流量分发，L7（Nginx/Ingress）在后做路由
边界：L7 需要保持连接（keepalive），L4 的"透明"在需要客户端真实 IP 时反而省事。
```

**Q9：DNS 解析慢怎么查**

```
标准：换 DNS、清缓存。
加分：
  1) dig +trace 看是哪一级慢
  2) dig @8.8.8.8 对比本地 DNS
  3) 看 resolv.conf 的 timeout/attempts
  4) 有没有用 search domain（导致多次查询）
  5) 应用层有没有缓存（Java 的 JVM DNS 缓存默认无限）
边界：容器里的 DNS（CoreDNS）与宿主不同，/etc/resolv.conf 可能被覆盖。
```

**Q10：跨网段通信为什么需要网关**

```
标准：目的 IP 不在本网段 → 交给网关转发。
加分：
  - 主机判断"是否同网段"靠"IP + 掩码"，不是靠"看起来像"
  - 掩码配错 → 明明同网段却发给网关（或反之）
  - ARP 只在同网段内工作，跨网段是"下一跳的 MAC"
边界：VLAN 隔离后，即使同网段也要经三层设备（因为二层不通）。
```

**Q11：抓包怎么看一个"慢"**

```
标准：tcpdump 抓包，看时间差。
加分：
  1) 看三次握手耗时（网络 RTT）
  2) 看客户端发请求到服务端首字节（服务端处理时间）
  3) 看有没有重传（tcpdump 里出现相同 seq）
  4) 看窗口大小（rwnd 为 0 = 接收方处理不过来）
  5) tcpdump -w 抓下来用 Wireshark 的"专家信息"看
边界：https 抓包只能看到握手与包大小，内容要解密（或看服务端日志/access log）。
```

**Q12：为什么有了 HTTPS 还需要其他安全措施**

```
标准：HTTPS 只保证传输加密。
加分：
  - 它防不了"服务端被攻破"（数据在服务端是明文）
  - 防不了"客户端本身被劫持"（中间人装了根证书）
  - 防不了"业务逻辑漏洞"（越权、注入）
  - 证书校验要开（很多客户端库默认不校验证书 → MITM）
边界：mTLS 可以做人/设备的双向认证，但密钥管理是新的难题。
```

### 三个常见翻车点

**① 上来就背术语，不接场景**

```
❌ "TCP 是面向连接的、可靠的、字节流的传输层协议……"
✅ "我上次遇到连接数上不去，是 TIME_WAIT 太多，改成了连接池"
```

**② 把"配置过"说成"精通"**

面试官会追一问："那你当时为什么选这个参数？"答不上来就露馅。

**③ 不知道边界，什么都说"可以"**

```
问："那是不是所有场景都该用连接池？"
答"是" → 错。长事务/流式场景用连接池会占满。
```

**敢说"这个场景不适合"才是加分项**。

### 答题模板

```
① 一句话定义（20 秒）
② 具体场景 / 我遇到过的例子（30 秒）
③ 边界与坑（20 秒）
```

**控制在 1 分半以内**，太长了面试官会走神。

### 检查清单

```
□ 每个概念能说出"我用它解决过什么问题"
□ 每个参数能说出"为什么是这个值"
□ 每个方案能说出"什么场景不适用"
□ 会用工具验证（ping/traceroute/dig/tcpdump/ss）
□ 不把"配过"说成"精通"
□ 答题控制在 1 分半
```
