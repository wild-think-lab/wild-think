### 面试官在看什么

不是"你知不知道 Redis"，而是这五项：

1. **能不能把模糊需求收敛成明确约束**（QPS、数据量、延迟、一致性）。
2. **能不能做量级估算**（存储、带宽、连接数），而不是凭感觉。
3. **能不能给出分层结构**（入口/应用/缓存/存储/异步）。
4. **知不知道自己的瓶颈在哪**（哪一步最先撑不住）。
5. **有没有失败模式意识**（挂了怎么办、数据会不会丢、如何回滚）。

### 标准流程（照着走就不慌）

```
① 澄清需求（3 分钟）→ ② 估算量级（3 分钟）→ ③ 接口与数据模型（3 分钟）
→ ④ 整体架构（5 分钟）→ ⑤ 关键路径细化（5 分钟）→ ⑥ 瓶颈与失败模式（3 分钟）
```

### 一道例题：短链服务

**① 澄清**（一定要问，问得越具体越显得专业）：

- 读写比例？读远多于写（估计 100:1）。
- 短链有效期？永久 + 可设置过期。
- 是否要自定义后缀？要。
- 是否需要统计点击？需要，异步。
- 一致性要求？跳转必须准确，统计可以最终一致。

**② 估算**：

```
假设每天新增 100 万条短链，读 1 亿次
写 QPS = 100万 / 86400 ≈ 12，峰值 ×5 ≈ 60
读 QPS = 1亿 / 86400 ≈ 1160，峰值 ×5 ≈ 5800
存储：每条 (短码 7B + 长链 100B + 元数据 50B) ≈ 160B
   100万/天 × 365 × 5 年 ≈ 18 亿条 ≈ 290GB
缓存：按 20% 热数据，约 58GB → 两台 32G 的 Redis 够
带宽：5800 QPS × 200B ≈ 1.2MB/s，可忽略
```

估算的重点不是算得准，而是**让每个数字都能推出下一步结论**。

**③ 接口与数据模型**：

```http
POST /api/v1/links        {"url": "...", "expire_at": "..."}  → {"code": "aB3xK9"}
GET  /{code}              → 302 Location: 原链
GET  /api/v1/links/{code}/stats → {"clicks": 1234}
```

表设计：

```sql
CREATE TABLE links (
  code        VARCHAR(10) PRIMARY KEY,
  url         TEXT NOT NULL,
  created_at  DATETIME NOT NULL,
  expire_at   DATETIME NULL,
  owner_id    BIGINT NULL,
  KEY idx_owner (owner_id)
);
```

**④ 整体架构**：

```
Client → CDN/WAF → LB → 应用（无状态，多副本）
                          ├─ Redis（code → url，TTL）
                          ├─ MySQL（持久化）
                          └─ MQ → 统计服务 → ClickHouse
```

**⑤ 关键路径（写短码）**：

- 短码生成两种方案：
  - **自增 ID + Base62**：简单、无冲突，但可被枚举（安全风险）。
  - **随机 7 位 + 唯一索引冲突重试**：不可枚举，冲突率低（62^7 ≈ 3.5 万亿）。
- 推荐随机 + 唯一索引，冲突时重试 3 次，仍失败则加长一位。
- 写入顺序：先写 DB（带唯一索引），成功后再写缓存（或让缓存 miss 回源）。**不要先写缓存**，否则 DB 失败会留下脏缓存。

**⑥ 读路径**：

```
① Redis 命中 → 302
② 未命中 → 查 MySQL → 回填 Redis（TTL 1h，热点更长）
③ 仍无 → 404
```

注意：**缓存穿透**用一个空值标记（`code → "NULL"`，短 TTL）；**缓存击穿**用 singleflight（同一个 code 只允许一个回源）；**雪崩**用 TTL 加随机抖动。

**⑦ 失败模式**（这段最能加分）：

- Redis 挂了：降级为直查 DB，加限流保护 DB。
- DB 主挂了：切换到从库（读多写少，短时间可接受只读）。
- 短码冲突：唯一索引兜底 + 重试。
- 恶意刷量：按 IP + code 维度限流，统计走异步。
- 过期数据：靠 TTL 自然淘汰 + 定时任务清理 DB（分批删，避免大事务）。

### 五个自伤式回答

1. **一上来就画图**，没澄清需求。面试官不知道你在解哪道题。
2. **没有量级估算**，说"用 Redis 就够了"。多少 QPS？内存多少？答不上来。
3. **过度设计**：10 万日活就上分库分表 + 消息队列 + 微服务。面试官会追问"为什么"，答不出就是减分。
4. **只讲正常路径**，不讲失败。真实系统 90% 的复杂度在异常处理。
5. **不说取舍**。任何方案都能挑出毛病，主动说出"这个方案的代价是 X，我接受它因为 Y"才是架构思维。

### 通用答题模板（任何题都能套）

```
需求：核心功能 3 条 + 非功能约束（QPS/延迟/一致性/成本）
量级：读写 QPS、存储、带宽、连接数
结构：入口 → 应用 → 缓存 → 存储 → 异步
关键点：这个系统最特殊的一处（短链是"读多写少 + 短码唯一"，IM 是"长连接 + 消息有序"）
失败：单点、数据丢失、热点、限流
演进：1 万 QPS 怎么做，100 万 QPS 改哪里
```

### 一句话总结

系统设计题不是知识竞赛，而是**在有限信息下做出一致决策并说清代价**。把估算与失败模式讲透，比堆术语有效得多。
