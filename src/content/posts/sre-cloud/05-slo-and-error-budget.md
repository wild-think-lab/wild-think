### 为什么需要它

"系统稳不稳"在会议上永远吵不清：研发说"挺稳的"，运维说"上周出过两次故障"，老板说"客户投诉了"。

SLO 把这个问题换成一句可量化的话：**"99.9% 的请求在 300ms 内成功响应，每月最多允许 43 分钟不达标。"**

有数字，才有讨论基础。

### 三个词的关系

| 词 | 含义 | 例子 |
| --- | --- | --- |
| SLI | 指标，怎么测 | 成功率 = 2xx+3xx / 总请求；延迟 = P95 |
| SLO | 目标，达到多少 | P95 < 300ms，99.9% 成功 |
| SLA | 承诺，对外合同 | 未达标赔钱/降级 |

**先有 SLI，再定 SLO，最后才谈 SLA。** 顺序反了，就是拍脑袋承诺。

### SLI 怎么定义

三个原则：

1. **从用户视角出发**。用户感知的是"下单成功且不太慢"，不是"CPU 使用率"。
2. **可稳定测量**。用服务端指标还是客户端指标要明确（服务端 2xx 率 vs 端到端成功率差别很大）。
3. **少而精**。每个服务 2–3 个核心 SLI 足够，多了没人看。

典型组合：

```
可用性: sum(rate(http_requests_total{code=~"2xx|3xx"}[5m])) / sum(rate(http_requests_total[5m]))
延迟:   histogram_quantile(0.95, sum(rate(http_request_duration_seconds_bucket[5m])) by (le))
```

### SLO 怎么定才不荒唐

三个参考：

- **历史基线**：过去 30 天实际达到多少，在此基础上提高一点。
- **业务影响**：这个服务停了，损失多少？决定投入多少。
- **可达成性**：没有监控、没有冗余的系统，别承诺 99.99%。

常见的分级：

| 服务类型 | 合理 SLO |
| --- | --- |
| 核心交易链路 | 99.95%，P95 < 200ms |
| 一般业务 API | 99.9%，P95 < 500ms |
| 内部管理后台 | 99.5%，P95 < 1s |
| 批处理任务 | 按时完成率 99% |

99.99% 意味着每月只有 4 分钟停机——没有多可用区、没有自动切换的系统基本达不到。

### 错误预算：SLO 真正的用法

以 99.9% / 30 天为例：

```
30 天 × 24 × 60 = 43200 分钟
允许不可用 = 43200 × 0.1% ≈ 43 分钟
```

这 43 分钟就是**预算**。用法：

- 月初预算充足 → 可以安排高风险变更（大版本升级、架构调整）。
- 月中消耗过半 → 变更开始收紧，评审加严。
- 预算耗尽 → **冻结变更**，只做修复。

这条规则的价值在于：它把"要不要上线"从政治博弈变成一次除法。

### 从零落地的四步

**第一步：选一个服务**

选用户量大、有明确痛点的那个，别一开始就覆盖全公司。

**第二步：把 SLI 接上监控**

```yaml
# 记录一个 SLO 视图（示例结构）
- name: api_availability
  sli:
    good: sum(rate(http_requests_total{job="api",code=~"2xx|3xx"}[5m]))
    total: sum(rate(http_requests_total{job="api"}[5m]))
  target: 0.999
  window: 30d
```

**第三步：每周看一次**

只看两个数字：当前达标率、剩余预算。别做复杂报表。

**第四步：写进变更流程**

"预算不足时，非修复类变更需运维负责人签字"——一句话就够，别写成 20 页制度。

### 三个常见误区

1. **把所有指标都当成 SLI**：CPU、内存、QPS 是资源指标，不是用户体验指标。
2. **SLO 定得过高**：99.99% 写在 PPT 里很好看，实际每天都在违规，最后没人再看。
3. **只监控不决策**：预算耗尽了还照常发布，那 SLO 就只是一张图。

### 与告警的关系

SLO 是**趋势**，告警是**事件**。

- 告警告诉你"现在有故障"。
- SLO 告诉你"这个月的稳定度还剩多少"。

两者结合才能回答："我们该先修这个 bug，还是先做容量扩容？"

### 一个能直接抄的模板

```
服务: 订单 API
SLI1: 成功率（2xx+3xx 占比）
SLI2: P95 延迟（服务端）
SLO1: 99.9% / 30 天滚动
SLO2: P95 < 300ms / 30 天
错误预算: 43 分钟/月
预算规则: 消耗 >70% 时变更需评审；耗尽时冻结非修复变更
负责人: xxx
复盘频率: 每周一 15 分钟
```

SLO 的意义不是考核，是**让"要不要上线"这件反复吵的事，有一把共同的尺子**。
