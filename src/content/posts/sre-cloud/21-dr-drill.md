### 三种演练

```
① 桌面推演（Tabletop）：一群人按剧本讨论"如果现在挂了怎么办"
② 组件演练：单独演练"切库/切机房/恢复备份"
③ 全链路演练：真实切流量、真实停服务
```

**"直接从 ③ 开始"** 风险太高，且没人敢做。

### 一个渐进路线

```
第 1 季度：桌面推演（找流程漏洞，成本低）
第 2 季度：单组件演练（切从库/恢复备份）
第 3 季度：半链路演练（摘一个机房流量）
第 4 季度：全链路演练（含用户侧验证）
```

**"先低风险、再高风险"** 才是可持续的。

### 判定标准必须是"用户视角"

```
✗ "数据库切换成功"（技术动作完成）
✓ "切换期间错误率 < 1%，P99 < 500ms，持续 5 分钟"
```

**"技术成功但用户看到 502"** 不算成功。

**建议的四个判据**：

```
① 错误率（不超过基线 × 2）
② 延迟（P99 不超过 SLO）
③ 数据一致性（对账通过）
④ 恢复时长（RTO 达标）
```

### 演练必须有"观察者"

```
一个人执行，一个人记录时间线，一个人看监控
```

**"执行的人看不到全局"**：

```
他在切库时，看不到"用户已经开始报错"
```

### 复盘产出三件东西

```
① 时间线（几点几分做了什么、多久恢复）
② 发现的缺口（配置/权限/文档/告警）
③ 整改项（谁、什么时候、验收标准）
```

**"没有整改项的演练等于没做"**。

### 五个"报告好看但真出事没用"

**① 演练在"演练环境"，与生产差异大**

```
演练环境有小数据量/无真实流量 → 结论不可用
```

**② 只演"顺利路径"**

```
假设"切库一切正常"，没演"切过去发现从库延迟 30 分钟"
```

**③ 没有"时间压力"**

```
演练时慢慢来，真出事时 5 分钟内要决策
→ 演练要计时（按 RTO 倒排）
```

**④ 权限没准备好**

```
演练时发现"没人有权限切 DNS" → 真实场景同样卡住
```

**⑤ 演练完没更新 runbook**

```
文档还是旧的，新人照着做会错
```

### 五个"演练会翻车"的地方

```
① 忘了通知业务方（演练被当成真故障）
② 忘了暂停自动化（自动扩容/自动重启干扰演练）
③ 忘了准备回滚（演到一半真挂了）
④ 忘了记录（事后无法复盘）
⑤ 忘了限时（演练无限延长）
```

**"提前发通知 + 设时间盒"** 是基本纪律。

### 一个"演练剧本"模板

```
名称：核心交易链路机房切换演练
目标：验证 RTO ≤ 15 分钟、错误率 < 1%
范围：订单/支付/库存
前置：从库延迟 < 1s、DNS TTL 已调低、值班到位
步骤：
  T+0   停止写入（进入只读）
  T+2   提升从库为主
  T+5   切换应用配置（指向新主）
  T+8   验证（健康检查 + 抽样下单）
  T+15  宣布完成 / 或回滚
判据：错误率、P99、对账、RTO
分工：执行/记录/观察/决策
回滚：T+15 未达标 → 切回原主
```

**"把剧本写成一页纸"** 演练时才能照着做。

### 检查清单

```
□ 有年度演练计划（渐进路线）
□ 判据是用户视角（错误率/延迟/一致性/RTO）
□ 有执行/记录/观察分工
□ 提前通知业务方
□ 暂停自动化干扰
□ 有回滚条件与决策人
□ 计时（按 RTO 倒排）
□ 复盘产出时间线 + 缺口 + 整改项
□ runbook 随演练更新
□ 整改项有截止日期与验收
```
