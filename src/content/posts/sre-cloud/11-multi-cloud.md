### 三种形态

| 形态 | 含义 | 典型动机 |
| --- | --- | --- |
| 单云 | 一家云厂商 | 简单，生态一致 |
| 多云 | 两家以上云 | 议价、避免锁定、区域覆盖、合规 |
| 混合云 | 自建 IDC + 云 | 核心数据自持、弹性用云 |

**多云的成本不是"钱"，是复杂度**：账号、网络、监控、发布、合规都要 ×N。

### 什么放哪

| 类型 | 建议位置 |
| --- | --- |
| 核心业务数据库（强一致） | 单云或自建 IDC（不要跨云做主从） |
| 前端/无状态应用 | 可以多云（就近部署） |
| 对象存储（静态资源） | 云原生（用 CDN 统一收敛） |
| 大数据/离线计算 | 便宜的云（对延迟不敏感） |
| 灾备 | 另一家云（避免单厂商级故障） |
| AI 训练 | GPU 资源便宜/配额足的地方 |

**关键判断**：**强一致、跨云时延敏感的东西不要跨云**。跨云 RTT 通常 10–30ms，跨云同步复制基本不可行。

### 网络打通

**方案对比**：

| 方案 | 延迟 | 成本 | 适用 |
| --- | --- | --- | --- |
| 公网 + TLS（应用层） | 高（不稳定） | 低 | 非敏感、低频 |
| IPSec VPN（公网加密隧道） | 中 | 低 | 中小流量、测试 |
| 专线（云厂商跨域专线） | 低 | 高 | 生产核心流量 |
| SD-WAN | 低–中 | 中 | 多分支、多云的折中 |

**IPSec VPN 起步**（成本最低，够用）：

```bash
# 一方用 strongSwan
# /etc/ipsec.conf
conn cloud
    left=203.0.113.10
    leftsubnet=10.10.0.0/24
    right=198.51.100.20
    rightsubnet=10.20.0.0/24
    ike=aes256-sha256-modp2048
    esp=aes256-sha256
    auto=start
```

**网段规划必须先做**：两边都用 `192.168.1.0/24` 是最常见的事故（VPN 起来后路由冲突，本地流量跑到云端）。

```
自建 IDC：10.10.0.0/16
云 A：    10.20.0.0/16
云 B：    10.30.0.0/16
```

### 数据主放哪（最关键的决定）

```
① 主数据库放一处（自建或某朵云），其他位置只读副本
② 跨云只读副本用异步复制（接受秒级延迟）
③ 对象存储用"一个主 + CDN 分发"，不要双向同步
④ 缓存（Redis）按区域独立，不做跨云集群
```

**双写是最危险的方案**：两端都写、冲突解决要靠应用层，实际项目里极少成功。

### DNS 与流量调度

```
① 统一 DNS 托管（如 Cloudflare 或自建权威 DNS），不要分散在各云控制台
② 用健康检查 + 故障切换（某云挂了自动切到另一云）
③ 证书统一管理（通配符或自动化签发）
```

健康检查切换的注意点：

```
- TTL 要短（60–120 秒），否则切换生效慢
- 客户端/递归 DNS 会缓存（实际生效时间可能 > TTL）
- 关键业务用"应用层重试 + 多地址"而不是完全依赖 DNS
```

### 账号与权限

```
① 每朵云一个独立账号体系，但统一身份（SSO/联邦登录）
② 用 IaC 管理（Terraform 多 provider），不要手工点控制台
③ 密钥集中管理（Vault / 云厂商 KMS），不要放 Git
④ 有统一的成本标签（cost tag），否则账单对不上
```

Terraform 多 provider 示例：

```hcl
provider "alicloud" { alias = "cn" }
provider "aws"      { alias = "us"; region = "us-east-1" }

module "api_cn" { source = "./modules/api"; providers = { cloud = alicloud.cn } }
module "api_us" { source = "./modules/api"; providers = { cloud = aws.us } }
```

### "多云"变成"多套孤岛"的四个信号

```
① 两个云的控制台各管各的，没人看全局
② 同一个服务在两个云的版本不一致（不同镜像 tag）
③ 监控是两个独立的 Grafana，没人对比
④ 故障时要挨个登录查（没有统一视图）
```

治理：

```
① 统一 CI/CD（一套流水线部署多个目标）
② 统一监控（指标打 cloud= 标签，一个面板看全部）
③ 统一成本看板（按云、按团队）
④ 统一变更流程（多云不降低流程要求）
```

### 灾备：多云最大的价值

```
RTO/RPO 目标 → 决定灾备形态
- RTO 小时级：冷备（备一套环境，不常开）
- RTO 分钟级：温备（备环境常开，异步复制）
- RTO 秒级：热备（双活，成本极高）
```

**冷备最划算**：定期把数据同步到另一朵云的对象存储，故障时启动环境。成本是"存储费 + 少量计算"。

**演练是必须的**：没演练过的灾备等于没有。每半年真跑一次"从另一朵云把业务拉起来"。

### 检查清单

```
□ 网段规划无冲突（三方各一段）
□ 网络打通方式选对（生产核心用专线）
□ 强一致数据不跨云
□ DNS 统一托管 + 健康检查切换
□ IaC 管理（Terraform 多 provider）
□ 密钥集中管理
□ 统一监控（带 cloud 标签）
□ 成本标签规范
□ 灾备有 RTO/RPO 目标且演练过
```
