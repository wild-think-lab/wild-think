### P1 现场最常见的三种混乱

```
① 五个人同时在改配置，互相覆盖
② 没人对外同步，老板/客服/销售各问各的
③ 没人记录时间线，事后复盘全靠回忆
```

**根因**：没有明确"谁指挥"。

### 四个角色

| 角色 | 职责 | 不做什么 |
| --- | --- | --- |
| 事故指挥（IC） | 决策、分配、控节奏 | **不亲手操作** |
| 操作员（Ops） | 执行具体操作 | 不自作主张扩大范围 |
| 沟通员（Comms） | 对内对外同步 | 不承诺恢复时间 |
| 记录员（Scribe） | 记时间线与决策 | 不参与技术判断 |

小团队一人可兼多角，但**"指挥"与"操作"必须分开**：一个人边想边改，容易越改越乱。

### 指挥员的五件事

**① 开场 3 分钟**

```
- 一句话说清现象（用户视角）
- 确认影响范围（多少用户、哪些功能）
- 定分级（P1/P2）与响应节奏
- 分配角色（谁操作、谁沟通、谁记录）
```

**② 建立"单一操作通道"**

```
规则：同一时间只有一个操作员在建言/执行
其他人只提供信息，不直接动手
```

这条规则能避免"多人并发操作"。

**③ 按时间盒推进**

```
每 15 分钟一个回合：
- 现在知道什么？
- 下一步做什么（一个动作）？
- 谁做、多久出结果？
- 要不要升级（叫厂商/叫更多人）？
```

**④ 控制"想根因"的冲动**

```
P1 现场的第一目标是"止血"，不是"找到根因"
根因留给复盘（故障结束后）
```

**⑤ 决定回滚的时机**

```
判据：如果 15 分钟内没有明确好转迹象 → 回滚
不要"再试一个改动" —— 每次尝试都会延长恢复时间
```

### 信息同步的节奏

| 时间 | 内容 | 对象 |
| --- | --- | --- |
| 0–5 分钟 | 已知现象 + 影响范围 | 内部群 |
| 每 15 分钟 | 状态更新（做了什么、结果如何） | 内部群 + 管理层 |
| 30 分钟未恢复 | 升级通知（含已尝试的措施） | 管理层 + 厂商 |
| 恢复后 | 恢复确认 + 影响统计 | 全员 |
| 24 小时内 | 初步复盘 | 相关方 |

**对外口径统一由沟通员发布**，其他人不单独回复客户。

### 一次"操作扩大事故"的复盘

**事故**：某服务 5xx 升高。

**过程**：

```
10:05  告警触发
10:07  A 开始重启 Pod
10:09  B 认为配置有问题，改了 Nginx 超时
10:12  C 认为是数据库，重启了主库
10:15  5xx 从 1% 涨到 40%（数据库重启导致全部失败）
10:40  回滚 + 恢复
```

**问题**：

```
① 三个人同时动手，没人知道谁改了什么
② 重启数据库这种高危操作没有经过确认
③ 没有时间线，复盘时靠猜
```

**改进**：

```
① 设立 IC，明确"只有操作员能动手"
② 高危操作（重启数据库/改网络）必须 IC 批准
③ 记录员实时记时间线（谁、何时、做了什么）
④ 引入"一次只改一个变量"的规则
```

**结果**：下次事故（同类告警）在 6 分钟内定位为缓存问题，只做了一次操作。

### 战时与平时的区别

| | 平时 | 战时（P1） |
| --- | --- | --- |
| 目标 | 正确、可维护 | **尽快恢复** |
| 变更 | 走流程、评审 | 授权即时执行，事后补记录 |
| 排查 | 找根因 | 先止血 |
| 决策 | 讨论共识 | IC 一人拍板 |

**战时的"跳过流程"必须在事后补齐记录**，否则无法复盘。

### 升级路径要写死

```
P1：
  0 分钟  告警 → 值班
  5 分钟  值班确认 → IC
  15 分钟 未定位 → 通知技术负责人
  30 分钟 未恢复 → 通知总监 + 厂商支持
  60 分钟 未恢复 → 启动应急预案（降级/切流）
```

**"该叫谁"要提前写下来**，现场没人有空翻通讯录。

### 检查清单

```
□ 有 IC 角色，且与操作员分离
□ 有"单一操作通道"规则
□ 高危操作需 IC 批准
□ 每 15 分钟同步一次
□ 30 分钟未恢复就升级
□ 有记录员记时间线
□ 先止血后根因
□ 升级路径（谁、何时、怎么联系）已写死
□ 战时跳过的流程事后补齐
```
