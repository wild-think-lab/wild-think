### 从业务指标换算到资源

**核心方法：找到"一个业务动作消耗多少资源"**。

```
例：一次下单请求
  → 3 次 DB 查询（各 2ms）
  → 1 次 Redis（0.5ms）
  → 1 次风控 RPC（20ms）
  → 应用 CPU 约 8ms
```

换算：

```
QPS = 1000 时：
  DB QPS = 3000（要看连接池与 DB 能力）
  应用 CPU = 8 核（1000 × 8ms）
  RPC 并发 = 20（1000 × 20ms / 1000）
```

**关键：找瓶颈项**。上面 RPC 的 20ms 最慢 → 它的并发需求最高。

### 三种扩容策略

| 策略 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 垂直 | 加 CPU/内存 | 简单 | 有上限、单点 |
| 水平 | 加实例 | 近乎无限 | 需要无状态 |
| 分片 | 按 key 拆 | 突破单机瓶颈 | 复杂、跨片查询难 |

**顺序**：先水平（应用层），再分片（数据层），最后才垂直（数据库主库）。

### 容量水位怎么定

**核心水位（必须扩容）**：

```
CPU > 70% 持续 15 分钟
内存 > 80%
磁盘 > 75%（写盘类服务）
连接池使用率 > 80%
```

**为什么是 70% 而不是 90%**：

```
① 留出突发流量空间（促销、爬虫、重试）
② 留出"一台挂掉"的容量（N+1）
③ 高负载下延迟非线性上升（90% 时 P99 可能翻 5 倍）
```

**N+1 原则**：如果一个实例挂了，剩余实例要能承载全部流量。

```
需要 N 个实例承载峰值 → 实际部署 N+1 个
例：峰值需要 4 核 → 部署 5 台 1 核（或 3 台 2 核）
```

### 扩容了还是慢的三个原因

**① 扩容了应用，但瓶颈在数据库**

```
应用从 4 台加到 12 台 → DB 连接数从 400 涨到 1200
→ DB 连接数打满 → 更慢
```

**扩容前必须确认"下一个瓶颈在哪"**。链路式的扩容只会把瓶颈往下推。

**② 扩容了，但流量没打散**

```
负载均衡"最小连接数"策略在新实例刚上线时不起作用（新实例连接数为 0，会被瞬间打满）
→ 新实例被打爆 → 又被摘除 → 抖动
```

对策：新实例上线先"慢启动"（逐步加权）。

**③ 扩容了，但共享资源没扩**

```
所有实例共用同一个 Redis / 同一个 NFS / 同一个网络带宽
→ 应用层扩容反而加重共享资源的压力
```

### 压测怎么做才有意义

**关键：压测要模拟真实流量分布，不是"打满一个接口"**。

```
① 取线上真实流量比例（如 70% 读列表、20% 详情、10% 写）
② 用相同比例压（不是全压最重的那个）
③ 观察"哪个组件先饱和"（这才是有价值的信息）
④ 压到 P99 超过 SLA 就停（不是压到崩溃）
```

**压测的三个产出**：

```
① 单实例的 QPS 上限（这是扩容的基本单位）
② 瓶颈组件的容量（这是真正要关注的）
③ 系统在 X QPS 下的 P99（这是对业务的承诺）
```

### 容量的季节性

**必须提前规划的三个时间点**：

```
① 大促（明确日期，提前 2 周扩容 + 压测）
② 月末/月初（对账、报表类业务暴涨）
③ 节假日（旅游/电商/票务有明显峰值）
```

**"提前多久"**：

```
云上扩容 → 提前 3 天（含验证）
自建机房 → 提前 2–4 周（采购/上架/装机）
```

**自建机房的真实约束**：加一台物理机要采购、上架、装系统、加入集群，1 个月起。

### 容量的成本视角

```
扩容不是免费的：
  云上按量 → 账单线性增长
  自建 → 采购 + 机柜 + 电 + 运维人力
```

**省钱的三个方向**：

```
① 削峰：把非实时任务移到低峰（报表、备份、批量计算）
② 降配：低峰缩容（云的弹性、K8s 的 HPA）
③ 提效：同样的资源做更多事（缓存命中率、查询优化、压缩）
```

**"提效"的收益往往大于"扩容"**：缓存命中率从 60% 提到 90%，可能省掉一半的 DB 容量。

### 一个容量规划表（可直接用）

```markdown
| 组件 | 当前容量 | 当前峰值 | 水位 | 瓶颈项 | 扩容方式 | 提前期 |
| --- | --- | --- | --- | --- | --- | --- |
| 应用 | 6 台 4C8G | 60% CPU | 60% | CPU | 加实例 | 3 天 |
| DB 主库 | 16C64G | 45% CPU, 80% 连接 | 连接 | 连接数 | 读写分离 | 2 周 |
| Redis | 8G 主从 | 70% 内存 | 内存 | 内存 | 加分片 | 1 周 |
| 带宽 | 200Mbps | 150Mbps | 75% | 带宽 | 提带宽 | 3 天 |
```

**"提前期"这一列是这张表的核心价值**：它决定了"什么时候必须开始动手"。

### 检查清单

```
□ 有"一个业务动作 → 资源消耗"的换算
□ 知道当前瓶颈项（不是猜的）
□ 有 N+1 冗余
□ 核心水位线定在 70%（不是 90%）
□ 扩容前确认下一个瓶颈
□ 新实例上线有慢启动
□ 共享资源（DB/Redis/带宽）同步规划
□ 压测按真实流量比例
□ 大促/月末/节假日提前规划
□ 有扩容提前期（云 3 天 / 自建 1 个月）
□ 优先"提效"（缓存/优化）而不是"扩容"
```
