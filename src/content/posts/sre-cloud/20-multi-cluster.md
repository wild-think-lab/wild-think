### 不要为了"看起来高级"上多集群

**四个真实动机**：

```
① 隔离（生产/测试、不同业务、不同租户）
② 地域（异地机房低延迟、容灾）
③ 权限（不同团队/子公司各自自治）
④ 规模（单集群超过 5000 节点难以运维）
```

**"一个集群不够用"的判断标准**：

```
etcd 容量/写入压力、apiserver 延迟、单集群升级风险窗口
```

### 两种架构

**① 联邦（Federation）**

```
一个"控制平面"管理多个成员集群
代表：Karmada、Cluster API、Anthos
优点：统一调度/统一发布
缺点：复杂度高，网络要求高
```

**② 独立集群 + 统一工具链**

```
每个集群自治
统一：GitOps 仓库、策略、监控、镜像仓库
优点：简单、故障隔离好
缺点：跨集群发布/查询需额外工具
```

**"两个集群 + 一个 GitOps 仓库"** 是性价比最高的方案。

### 多集群最容易漏的三件事

**① DNS/服务发现**

```
集群 A 的服务要访问集群 B → 需要跨集群 DNS 或显式 Endpoint
```

**② 镜像分发**

```
每个集群都能拉同一个镜像仓库（或做复制）
→ 否则"某集群拉不到镜像"是常态
```

**③ 证书与身份**

```
多集群 ServiceAccount / OIDC 统一
→ 否则每个集群一套凭据
```

### 发布到多集群（GitOps 做法）

```
repo/
├── base/                 # 公共清单
└── overlays/
    ├── cluster-a/
    └── cluster-b/
```

**用 Kustomize/Helm 做差异**：

```yaml
# overlays/cluster-b/kustomization.yaml
resources:
- ../../base
patches:
- target: {kind: Deployment, name: app}
  patch: |-
    - op: replace
      path: /spec/replicas
      value: 10
```

**"同一份 base + 每个集群一个 overlay"** 是最常见的做法。

**ArgoCD 的做法**：

```
每个集群一个 ArgoCD 实例（或一个实例管多个集群，用 cluster 参数）
→ Application 里指定 destination cluster
```

### 五个"多集群之后运维翻倍"的原因

**① 版本不一致**

```
A 集群 1.28，B 集群 1.26 → API 差异导致清单不兼容
```

**② 策略不一致**

```
A 集群有 Kyverno 策略，B 没有 → 同样的镜像在 B 上跑不起来
```

**③ 监控各自一套**

```
两个 Grafana、两套告警 → 值班要开两个页面
→ 至少"告警统一到一个入口"
```

**④ 备份各自为政**

```
只有 A 集群有 Velero → B 出事没得恢复
```

**⑤ 没有"跨集群视图"**

```
"这个服务在两个集群各几个副本？" 没人答得上来
```

### 一个"可持续"的多集群基线

```
① 版本对齐（同时升级，差不超过一个 minor）
② 策略/基线用同一份仓库
③ 镜像仓库统一（或复制）
④ 监控：Prometheus 联邦或统一 Thanos
⑤ 告警：统一 Alertmanager 入口
⑥ 备份：每个集群都配（不只是主集群）
⑦ 有"集群清单"文档（谁负责、版本、容量）
```

### Thanos/VictoriaMetrics 的用途

```
多集群指标汇总 → 一个查询入口
```

**"统一查询"是多集群最实用的收益**（比"统一调度"更早见效）。

### 检查清单

```
□ 明确多集群的动机（不是为了炫技）
□ 版本对齐策略
□ 策略/基线共用一份
□ 镜像仓库统一或复制
□ 跨集群 DNS/服务发现方案
□ GitOps 仓库按 base + overlay 组织
□ 监控汇总（Thanos/VM）
□ 告警统一入口
□ 每个集群都有备份
□ 有集群清单与责任人
□ 有跨集群的容量视图
```
