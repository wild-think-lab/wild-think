### 值班的四件事

```
① 值守：看告警、确认服务健康
② 响应：接到告警后按 runbook 处置
③ 升级：搞不定/超时时找谁
④ 复盘：事后记录与改进
```

**"只有 ① 没有 ②③④"** → 值班变成"看屏幕"。

### 一条"告警到恢复"的路径

```
告警触发 → 通知到值班人（电话/IM/短信）
→ 值班人 5 分钟内确认（ack）
→ 按 runbook 处置（或升级）
→ 恢复 + 记录时间线
→ 复盘
```

**"通知到人"** 是关键：

```
只发到群里 → 没人认领（三人都以为别人在看）
```

### 轮值与升级

```
① 一周一轮（避免疲劳）
② 主备双人（主值班 + 备份）
③ 升级路径：值班 → 组长 → 领域 owner → 负责人
④ 升级触发条件：15 分钟未定位 / 影响面扩大 / 需要权限
```

**"升级要有明确触发条件"**，否则大家硬扛。

### 五个"值班形同虚设"

**① 告警太多，全部静音**

```
每天 500 条 → 值班人不看 → 真故障也漏
→ 先做告警治理（见另文）
```

**② 没有 runbook**

```
新人值班 → 每个故障都要问人
```

**③ 值班人不被授权**

```
"没权限重启/切流量" → 只能等
→ 值班要预授权（在受控范围内）
```

**④ 没有"值班交接"**

```
换班时"当前有几个隐患"不交接 → 下一个值班重新踩坑
```

**⑤ 复盘不追整改**

```
每次都说"下次注意" → 同类故障反复
```

### runbook 该写什么

```
① 现象（告警长什么样、用户看到什么）
② 影响面（哪些功能受影响）
③ 判据（怎么确认是这个故障）
④ 步骤（1/2/3 具体命令）
⑤ 止损（先恢复，不先查根因）
⑥ 升级（什么情况找谁）
⑦ 回滚（改了怎么退）
```

**"先止损再找根因"** 是值班第一原则。

### 值班的健康度指标

```
① 告警量（每人每晚几条）
② 误报率
③ MTTA（确认时间）/ MTTR（恢复时间）
④ 夜间被叫醒次数
```

**"每人每晚 > 3 次被叫醒"** → 排班或告警治理要改（人会被耗尽）。

### 一个"最小可行"的值班制度

```
① 明确值班表（谁、什么时候）
② 主备双人
③ 告警分级（P0 电话 / P1 IM / P2 日报）
④ 每个 P0/P1 有 runbook
⑤ 有升级路径与触发条件
⑥ 交接清单（未闭环事项）
⑦ 每周回顾告警与故障
```

### 检查清单

```
□ 有值班表与主备
□ 告警分级（不同通知方式）
□ 告警能"通知到人"（不是群消息）
□ 有 ack 机制与超时升级
□ P0/P1 有 runbook
□ 值班有预授权（受控）
□ 有交接清单
□ 有 MTTA/MTTR 指标
□ 关注"夜间叫醒次数"
□ 复盘有整改闭环
```
