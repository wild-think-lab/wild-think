### 第一件事：先判断类型

| 现象 | 类型 | 特征 |
| --- | --- | --- |
| 带宽被打满 | 流量型（UDP/ICMP flood） | 网卡流量飙升，CPU 不高 |
| 连接数打满 | 连接型（SYN flood） | `ss -s` 显示大量 SYN_RECV |
| 应用层慢 | 应用型（CC） | 请求看着正常，但都是慢接口 |
| 只打某个域名 | 反射/DNS 放大 | 大量 DNS/NTP 响应包 |
| 间歇性 | 慢速攻击（Slowloris） | 连接建立但不发完请求 |

**判断命令**：

```bash
# 网卡流量
sar -n DEV 1 5
iftop -i eth0

# 连接状态分布（关键）
ss -s
# TIME-WAIT / SYN-RECV 大量 = 连接型

# 按来源 IP 排序
ss -tn | awk '{print $5}' | cut -d: -f1 | sort | uniq -c | sort -rn | head

# 按目标端口
ss -tn | awk '{print $4}' | awk -F: '{print $NF}' | sort | uniq -c | sort -rn
```

### 止血四步

**① 先保命：限流/降级**

```nginx
# 应用层快速止血
limit_req_zone $binary_remote_addr zone=ddos:10m rate=10r/s;

server {
    location / {
        limit_req zone=ddos burst=20 nodelay;
    }
}
```

（若开启后正常用户也被限，说明攻击来自大量分散 IP，需要上层清洗）

**② 挡住明显异常**

```bash
# 封单个高频 IP（临时，别指望长期有效）
iptables -I INPUT -s 1.2.3.4 -j DROP

# 更有效：按"连接数"限制
iptables -A INPUT -p tcp --syn -m limit --limit 10/s -j ACCEPT
iptables -A INPUT -p tcp --syn -j DROP
```

**③ 上清洗（如果带宽被占满，本机做什么都没用）**

```
流量型攻击的唯一解法：让流量在到达你之前被清洗
→ 云厂商的高防 IP / CDN 的 DDoS 防护
```

**关键认知**：**带宽被打满时，你在服务器上做的任何优化都无效**（包根本到不了应用层）。

**④ 通知与留证**

```
① 通知业务方（可能影响用户）
② 保留证据：抓包、日志、攻击来源
③ 记录时间线（后面要复盘/报案）
```

### 云清洗 vs 自建

| | 云高防/CDN | 自建 |
| --- | --- | --- |
| 带宽 | 几百 G 到 T 级 | 受限于你的出口 |
| 成本 | 按带宽/按次 | 硬件投入大 |
| 切换 | 改 DNS 解析 | 需 BGP/引流 |
| 适合 | 几乎所有业务 | 大型企业/IDC |

**务实做法**：

```
域名解析到 CDN（平时就有加速）
被打时开启 CDN 的"高防模式"
→ 只需要改一个开关
```

**前提是"平时就接在 CDN 上"**：等被打时才切 DNS，切换生效要几分钟到几十分钟（TTL）。

### 应用型（CC）更难防

```
特征：请求看起来完全合法（真实 IP、正常 UA、正常路径）
只是量很大，且集中在"贵"的接口（搜索、详情、下单）
```

**判断**：

```bash
# 哪个路径被打
awk '{print $7}' access.log | sort | uniq -c | sort -rn | head

# 是不是都是同一批 IP
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -5
```

**对策**：

```
① 贵接口加强制缓存（同一个 query 缓存 10 秒）
② 加验证（滑块/JS 挑战）
③ 按"用户维度"限流（登录用户额度更高）
④ 搜索类接口限制结果页数
```

**最有用的防 CC 手段是"缓存"**：

```
1000 QPS 打同一个热门搜索词 → 缓存后只有 1 次回源
```

### 被打时最不该做的三件事

**① 着急重启服务**

```
重启解决不了带宽被打满/连接被打满
反而会让正在处理的请求全部失败
```

**② 无差别封 IP 段**

```
封一个 /16 会误杀大量正常用户（云厂商的 IP 段都是共享的）
```

**③ 在服务器上疯狂抓包**

```
抓包本身消耗 CPU 与磁盘
被打时抓包会让情况更糟（除非只抓少量）
```

### 一个应急 runbook

```markdown
# DDoS 应急

## 判断（5 分钟内）
1. sar -n DEV 1 5        → 带宽是否打满
2. ss -s                 → 连接状态分布
3. awk '{print $7}' access.log | sort | uniq -c | sort -rn | head → 目标路径

## 决策
- 带宽打满 → 立刻上高防/切 CDN 高防
- 连接打满 → 限 SYN + 封高频源
- 应用层   → 限流 + 缓存 + 验证

## 止血（15 分钟内）
1. 开启 CDN 高防模式
2. 应用层限流（limit_req）
3. 贵接口加缓存（临时缩短 TTL）
4. 通知业务方

## 观察（持续）
- 正常用户成功率的恢复情况
- 是否需要进一步降级（关闭非核心功能）

## 记录
- 开始时间、攻击类型、峰值、处理动作、恢复时间
```

### 长期加固

```
① 平时就接 CDN（被打时能一键切）
② 静态资源全走 CDN（不消耗源站带宽）
③ 关键接口有限流（不是等被打才加）
④ 有"贵接口"的缓存层
⑤ 带宽监控告警（提前发现异常）
⑥ 有应急联系人与云厂商工单通道（提前建好）
```

**"平时就有 CDN + 限流 + 缓存"是最有效的预案**：被打时只需要开一个开关。

### 检查清单

```
□ 知道自己的出口带宽上限
□ 接入 CDN/高防（平时就在用）
□ 有应用层限流（关键接口）
□ 贵接口有缓存
□ 有带宽/连接数监控告警
□ 有 runbook（含判断命令与决策分支）
□ 有云厂商应急通道
□ 事后复盘（攻击类型/峰值/改进项）
```
