### Serverless 的三种形态

```
FaaS       ：函数即服务（AWS Lambda / 阿里云 FC / Cloudflare Workers）
PaaS       ：托管运行时（Heroku / App Engine）
SaaS       ：软件即服务（严格说不是"无服务器"）
```

**真正改变架构的是 FaaS**。

### 它的三个真实优势

```
① 无需运维服务器（没有补丁、没有容量规划）
② 按调用计费（闲置不花钱）
③ 天然弹性（并发上来自动扩）
```

**注意"三个"里没有"更便宜"** —— 成本取决于流量形态。

### 冷启动：最被低估的问题

```
冷启动耗时：
  Java  ：1–5 秒（JVM 启动）
  Node  ：100–500ms
  Python：200–800ms（依赖包多则更久）
  Go    ：10–50ms（原生编译最快）
```

**影响**：

```
① 低频接口 → 每次都是冷启动 → P99 很差
② 高并发突发 → 启动一批实例 → 前几秒全部很慢
```

**缓解手段**：

```
① 预置并发（provisioned concurrency，AWS 有）
② 定时"热身"（cron 每 5 分钟打一次）
③ 用 Go/Rust 等启动快的语言
④ 减少依赖体积（包越小启动越快）
```

**"无脑上 Serverless"最常见的后果就是"接口比原来慢了 10 倍"**。

### 并发模型与限制

| 限制项 | 典型值 | 影响 |
| --- | --- | --- |
| 单次执行时长 | 15 分钟（Lambda） | 长任务必须拆分 |
| 内存 | 128MB–10GB | 大数据处理受限 |
| 并发数 | 按账号配额 | 突发会被限流 |
| 临时磁盘 | 512MB–10GB | 不能当地盘用 |
| 连接复用 | 每次调用新环境 | 连接池失效 |

**"连接池失效"是很致命的**：

```
每个调用都是新进程 → 数据库连接无法复用
→ 每次都要建连（几十 ms）+ 可能打满数据库连接数
→ 必须用"外部连接代理"（如 RDS Proxy）
```

### 状态与数据

```
FaaS 是无状态的（调用之间不共享内存）
状态必须外置：数据库 / Redis / 对象存储
```

**这带来两个约束**：

```
① 无法用本地缓存（每次调用都冷）
② 文件系统是临时的（写/tmp 下次就没了）
```

**对策**：

```
① 缓存用 Redis / 托管缓存
② 大文件走对象存储（S3/OSS）
③ 需要本地缓存时考虑"常驻实例"（那就不是 Serverless 了）
```

### 成本结构的真相

```
按调用计费，看起来便宜
但：
① 每次调用有"最低计费时长"（如 100ms 起）
② 内存与时长叠加计费
③ 网络出流量单独计费
④ 并发预置（provisioned concurrency）按月收费
```

**"高频小调用"场景下，Serverless 可能比一台固定服务器贵 10 倍**：

```
假设：每秒 100 次调用，每次 50ms，512MB
→ 每月费用往往远超一台 8C16G 云主机
```

**适合的场景**：

```
① 低频（每分钟几次到每小时几次）
② 突发（平时 0，峰值很高）
③ 事件驱动（webhook、定时任务、图片处理）
```

**不适合**：

```
① 长连接（WebSocket 很难）
② 持续高 QPS
③ 需要常驻后台（定时器/守护进程）
```

### 边缘计算：它是另一个问题

```
边缘 = 把计算放到"离用户近"的地方
形态：CDN 边缘函数、边缘节点上的容器、5G MEC
```

**解决的痛点**：

```
① 延迟（RTT 从 100ms 降到 10ms）
② 回源带宽（在边缘处理/缓存）
③ 地域合规（数据不出境）
```

**现实约束**：

```
① 边缘节点的算力有限（不是数据中心）
② 状态难共享（边缘之间不互通）
③ 调试困难（日志分散、无法 attach）
④ 版本发布是"全网推"，回滚慢
```

### 四个"看起来很美好"的坑

**① 以为能省钱**

```
高频场景反而更贵（先算清楚单次成本 × 调用量）
```

**② 以为不用管运维**

```
仍然要管：依赖版本、冷启动、配额、日志、监控、密钥
只是把"服务器运维"换成"函数配置运维"
```

**③ 以为天然高可用**

```
单函数挂了就是挂了（没有多副本的概念）
要靠"上游重试 + 幂等"
```

**④ 以为能跑长任务**

```
15 分钟上限 → 大任务要拆成"编排 + 多个函数"
→ 编排层（Step Functions / 工作流）成为新的复杂度
```

### 一个决策清单

```
① 请求频率：< 10 QPS 且突发性强 → 适合
② 单次时长：< 1 分钟 → 适合；> 5 分钟 → 不适合
③ 是否需要长连接：需要 → 不适合
④ 是否需要本地状态/缓存：需要 → 谨慎
⑤ 是否有稳定高流量：有 → 用固定服务器更划算
⑥ 团队是否有 Serverless 经验：无 → 从"非核心链路"试
```

**"从非核心链路试"是最稳的落地方式**：图片处理、webhook 接收、报表生成这类。

### 混合架构（最现实的方案）

```
核心 API       → 常驻服务（K8s）
低频/突发任务  → Serverless
静态与热点内容 → 边缘（CDN + 边缘函数）
```

**这才是绝大多数团队的最终形态**，"全 Serverless"很少见。

### 检查清单

```
□ 评估冷启动对 P99 的影响
□ 用启动快的语言或预置并发
□ 数据库连接用外部代理
□ 状态全部外置（不用本地缓存）
□ 长任务拆分成编排 + 函数
□ 算清单次成本 × 调用量（别凭感觉）
□ 有日志/监控/密钥管理方案
□ 核心链路不上 Serverless（先试非核心）
□ 边缘场景评估调试与回滚成本
□ 混合架构（不追求"全无服务器"）
```
