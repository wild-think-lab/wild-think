### 事情的开始

```
17:40 同事 A 上线一个"小改动"：Nginx 加了一行 client_max_body_size 20m
17:41 全站 413（上传接口全挂）
17:43 回滚，17:46 恢复
```

**"一行配置"也很危险**，因为它改的是**全局行为**。

### 变更的四条铁律

**① 任何变更都要能"一步回滚"**

```
改配置前先备份：cp nginx.conf nginx.conf.bak.$(date +%F-%H%M)
或更好：配置进 Git，回滚 = git checkout + reload
```

**"没有回滚方案的变更，等于赌博"**。

**② 双人复核（Four Eyes）**

```
改的人 ≠ 看的人
复核看三件事：
  ① 改动是否符合预期
  ② 是否影响其他模块
  ③ 回滚命令是什么
```

**为什么有效**：自己看自己的错最容易漏。

**③ 变更窗口与低峰**

```
高风险变更：业务低峰（凌晨/周末）
中风险：提前通知，有人值守
低风险：随时可改但要有记录
```

**分级不是官僚，是让"注意力"用在正确的地方**。

**④ 改完必须验证（不是"看起来对"）**

```
配置类：nginx -t / httpd -t 先测语法
        然后 reload（不是 restart）
业务类：跑一遍核心链路（登录→下单→支付）
监控类：确认指标确实上报
```

**`nginx -t` 通过不代表配置"语义正确"**，只是语法合法。

### 灰度发布的三种粒度

**① 按流量比例**

```
10% → 观察 30 分钟 → 50% → 观察 → 100%
```

**② 按机器/实例**

```
先 1 台 → 观察 → 一批 → 全量
```

**③ 按用户/租户（功能开关）**

```javascript
if (featureFlag.isEnabled('new-checkout', userId)) {
  // 新逻辑
} else {
  // 老逻辑
}
```

**功能开关的价值**：

```
出问题不用回滚代码（重启很慢）→ 改开关即可（秒级）
```

**代价**：代码里要维护两套逻辑，需要定期清理。

### 变更单模板（可直接用）

```markdown
## 变更基本信息
- 变更标题：Nginx 上传大小调整 20m
- 变更负责人：
- 复核人：
- 计划时间：2026-11-27 22:00–22:30
- 影响范围：全部上传接口

## 变更内容
- 文件：/etc/nginx/conf.d/app.conf
- 改动：新增 client_max_body_size 20m;
- 原因：用户反馈 > 10MB 的附件上传失败（工单 #1234）

## 风险评估
- 影响面：上传接口（约占总请求 2%）
- 是否影响其他模块：否
- 最坏情况：上传仍失败 / 或大文件写入磁盘压力上升

## 执行步骤
1. cp app.conf app.conf.20261127
2. 修改 app.conf
3. nginx -t
4. systemctl reload nginx
5. 用 15MB 文件测试上传

## 验证方法
- curl -F "file=@test15m.bin" https://api/upload → 200
- 观察磁盘 IO 5 分钟

## 回滚方案
- cp app.conf.20261127 app.conf && nginx -t && systemctl reload nginx
- 预计耗时：10 秒

## 观察指标
- 5xx 率、上传成功率、磁盘 IO
```

**这份模板的价值**：逼你回答"最坏是什么、怎么退回去"。

### 变更后的观察窗口

**不同变更的观察期**：

| 变更类型 | 观察期 | 关注 |
| --- | --- | --- |
| 配置/参数 | 15–30 分钟 | 错误率、延迟 |
| 应用发布 | 1–2 小时 | 业务指标、日志异常 |
| 数据库结构 | 24 小时+ | 慢查询、复制延迟 |
| 基础设施 | 数天 | 容量、稳定性 |

**"改完就走"是事故的温床**。

### 一个反例：为什么"热修复"最危险

```
18:00 线上报错
18:05 直接在服务器上 vim 改代码（没走发布流程）
18:06 重启服务
18:20 又报错，再改一次
18:40 第三次改
19:30 发现三次改动互相冲突，且没有记录
```

**热修复的三个恶果**：

```
① 服务器状态与代码库不一致（下次发布覆盖掉修复）
② 没人知道改了什么（无审计）
③ 多次改动互相打架
```

**正确做法**：

```
紧急修复也必须：改代码库 → 走最快发布通道（哪怕是一条命令）
哪怕只用一个 commit + 一条部署命令
```

**"快"和"有记录"不冲突**。

### 变更冻结期

```
大促、重要活动、季度结账期间：禁止非必要变更
```

**冻结不等于"什么都不做"**：

```
① 紧急修复仍可做（但要走双重审批）
② 提前把风险变更做完（别堆在冻结前一天）
```

### 检查清单

```
□ 每个变更都有回滚方案（且演练过命令）
□ 配置进 Git，改动用 PR
□ 双人复核（改的人 ≠ 复核的人）
□ 配置先 nginx -t / 语法检查，再 reload
□ 高危变更走低峰窗口
□ 有灰度手段（比例/机器/开关）
□ 变更单含"最坏情况 + 回滚 + 验证"
□ 变更后有观察窗口（不到时间不宣布完成）
□ 紧急修复也进代码库
□ 有变更冻结期与例外审批
□ 所有变更留审计记录
```
