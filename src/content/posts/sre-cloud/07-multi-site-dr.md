### 两个数字决定一切

- **RTO（Recovery Time Objective）**：故障后多久必须恢复。
- **RPO（Recovery Point Objective）**：最多能丢多少数据（按时间算）。

它们不是拍脑袋定的，而是从业务推出来的：

```
RTO：财务结算系统 30 分钟 → 必须能快速切流
RPO：订单数据不能丢一条 → 必须是同步复制
RTO：内部报表 4 小时 → 可以冷备 + 手工恢复
```

**先定数字，再选架构。** 反过来做（先买两套机房再想为什么）是浪费钱。

### 四个容灾等级

| 等级 | 描述 | RTO | RPO | 成本 |
| --- | --- | --- | --- | --- |
| L1 本地备份 | 同机房备份，机器故障可恢复 | 小时级 | 小时级 | 低 |
| L2 异地备份 | 数据定期传到异地 | 小时–天 | 小时级 | 低 |
| L3 温备 | 异地有环境，需启动与切流 | 30 分钟–2 小时 | 分钟级 | 中 |
| L4 双活/多活 | 两边同时提供服务 | 秒–分钟 | 接近 0 | 高 |

大部分企业的核心系统在 L3，非核心在 L1/L2。**全上 L4 是奢侈，也没必要**。

### 同城双活 vs 两地三中心

**同城双活**（两个机房，相距 30–50km）：

- 延迟低（< 2ms），可以做同步复制，RPO≈0。
- 但同城灾害（地震、大面积停电、城市级网络故障）会同时影响两边。
- 关键点：**同城双活解决的是"机房级故障"，不是"城市级故障"**。

**两地三中心**（同城两中心 + 异地一中心）：

- 同城两中心做双活（RPO≈0，RTO 分钟级）。
- 异地中心做异步复制（RPO 分钟级，RTO 小时级）。
- 成本约是同城双活的 2–3 倍。

选型判断：

```
只要求机房故障不停 → 同城双活
要求城市级灾害也能恢复 → 两地三中心
只要求"数据不丢" → 异地异步备份 + 定期演练即可
```

### 数据层的三种复制方式

| 方式 | RPO | 代价 |
| --- | --- | --- |
| 同步复制 | 0 | 写延迟增加（跨机房 RTT × 2） |
| 半同步 | 接近 0 | 一台副本确认即返回，兼顾 |
| 异步复制 | 秒–分钟 | 延迟低，但可能丢最后一段 |

MySQL 半同步：

```ini
rpl_semi_sync_source_enabled = 1
rpl_semi_sync_source_timeout = 1000     # 1 秒等不到就从异步继续（可用性优先）
rpl_semi_sync_source_wait_point = AFTER_SYNC
```

`AFTER_SYNC` 比 `AFTER_COMMIT` 更安全（提交前确认），代价是延迟更高。

PostgreSQL：

```ini
synchronous_commit = remote_write     # 或 on / remote_apply
synchronous_standby_names = 'sync1'
```

`remote_apply` 最严格（备库已应用），延迟也最大。

### 流量层怎么切

三种切流手段：

1. **DNS 切换**：TTL 要提前调小（60s），但客户端缓存不可控，实际生效可能几分钟到几十分钟。
2. **全局负载（GSLB）+ 健康检查**：自动摘除故障机房，最常用。
3. **应用层路由**：客户端/SDK 按配置选择入口，最可控但要改代码。

**关键：切流之前必须确认"另一边真的能承接"**。很多事故是"切过去了，但另一边容量只有 30%"。

所以容量要按"单边承接全部流量"来设计——双活不是"各承担 50%"，而是"平时各 50%，故障时一边能吃下 100%"。

### 演练：不演练的容灾等于没有

演练要分层次，从轻到重：

| 层级 | 做什么 | 频率 |
| --- | --- | --- |
| 桌面演练 | 开会走流程，确认谁做什么 | 每季度 |
| 组件切换 | 切一个中间件/一个库 | 每月 |
| 单机房切流 | 全部流量切到另一边，跑 2 小时 | 每半年 |
| 真实断网演练 | 直接断开一边机房网络 | 每年 |

演练必须记录三件事：

1. **实际 RTO**（从决定切到服务恢复用了多久）。
2. **实际 RPO**（丢了多少数据，能不能对上账）。
3. **卡在哪**（哪个步骤没人会、哪个系统切不过去）。

第一次演练通常会发现"RTO 是设计值的 5 倍"——这不是失败，这正是演练的价值。

### 五个常见认知错误

1. **"我们做了主从，所以有容灾"**：主从只解决数据副本，不解决"流量怎么切、应用怎么起"。
2. **"备份在异地，所以安全"**：没验证过恢复的备份不算备份。
3. **"双活就是两套一样的系统"**：数据一致性、会话一致性、定时任务冲突都要处理。
4. **"RTO 30 分钟"**：不算上"发现故障 + 决策 + 通知"的时间。真实 RTO 要加上人的反应时间。
5. **"容灾系统平时不用管"**：半年不用的系统，切换时一定出问题（证书过期、配置漂移、容量不足）。

### 一份容灾方案该写清的七件事

```
1. 业务分级与对应 RTO/RPO
2. 架构图（含数据流向与复制方式）
3. 切换触发条件（谁有权决定切）
4. 切换步骤（可执行的命令与检查点）
5. 切换后验证清单（业务侧怎么确认"真的好了"）
6. 回切步骤（故障恢复后怎么切回来）
7. 演练计划与最近一次演练结论
```

第 6 项最常被漏掉——切过去容易，切回来才发现"反向复制没配"。

### 一句话总结

容灾的本质是**用钱买时间**。先定 RTO/RPO，再选等级与架构，最后靠演练把"纸面方案"变成"真能切"。
