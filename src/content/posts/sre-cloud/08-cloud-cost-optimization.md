### 先能归因，才能优化

看不到"谁花了钱"，任何优化都是猜。

归因的最小粒度：

```
业务线 → 环境（prod/staging/dev） → 服务 → 资源类型（计算/存储/网络）
```

落地动作：

1. **所有资源必须打标签**（`team`、`service`、`env`、`cost-center`）。
2. 账单按标签聚合出报表，每周发给负责人。
3. 未打标签的资源单独列一张表，周会通报。

```bash
# 阿里云 CLI 示例：按标签查实例
aliyun ecs DescribeInstances --Tag.1.Key=team --Tag.1.Value=order
```

没有标签的资源是成本黑洞——通常是测试环境、临时机器、忘了关的实验。

### 四类浪费

**① 闲置资源**

- 长期 CPU < 5% 的实例。
- 无人访问的测试环境（夜间与周末）。
- 已下线但没释放的磁盘、快照、负载均衡。

**② 规格过大**

CPU 与内存利用率长期低于 20%，说明规格是拍脑袋定的。

```promql
# 每实例 CPU 利用率（7 天平均）
avg by (instance) (rate(node_cpu_seconds_total{mode!="idle"}[7d]))
```

**③ 架构性浪费**

- 大量小实例而不是少数大实例（管理开销 + 单价更高）。
- 跨可用区免费流量没利用，反而走公网。
- 缓存没做，把重复查询打到最贵的数据库。

**④ 计费模式不匹配**

- 长期稳定的负载用按量付费（比包年贵 30–50%）。
- 短时突发任务用预留实例（浪费）。

### 三种计费模式的边界

| 模式 | 适合 | 风险 |
| --- | --- | --- |
| 按量付费 | 不确定时长、临时、实验 | 长期用会显著更贵 |
| 预留/包年包月 | 稳定负载（>70% 时间在用） | 业务变化时退不掉 |
| 竞价/抢占式 | 可中断任务（批处理、CI、训练） | 随时被回收，必须能续跑 |

判断公式：

```
若资源年利用率 > 60% → 预留
若 30%–60% → 按量 + 部分预留
若 < 30% → 要么按量，要么直接关掉
```

**竞价实例的硬要求**：任务必须幂等且能断点续跑。没有 checkpoint 的任务不要放竞价机器。

### 优化的六个动作（按性价比排序）

1. **关掉没用的**（零成本，收益最大）：测试环境夜间停机、删除无主磁盘与旧快照。
2. **右移规格**（Right-sizing）：按 P95 利用率下调 1–2 档。
3. **合并小实例**：10 台 2C4G 换成 3 台 8C16G，单价与管理成本双降。
4. **存储分层**：热数据 SSD、冷数据对象存储、归档走低频。
5. **CDN 与缓存**：把回源流量降下来，带宽费通常是最容易失控的一项。
6. **计费模式切换**：稳定负载转预留，可中断转竞价。

前三项通常能拿到 15–25%，全部做完常见 30%。

### 三个"省成本伤到自己"的坑

**① 砍监控与备份**

省几百块的监控费用，换来故障时多花几小时的定位时间。**监控与备份是保险，不是开销**。

**② 把生产与测试混在一台机器上**

省一台机器的钱，换来测试把生产打挂的风险。

**③ 过度右移**

按平均利用率下调规格，忽略峰值。结果是大促当天 CPU 打满、请求排队。

正确做法：右移按 **P95 而非平均值**，并保留 30% 余量。

### 一个可执行的月度流程

```
月初：拉上月账单 → 按服务归因 → 排出 Top 10 花费
月中：对 Top 10 做三项检查（利用率、规格、计费模式）
月末：执行变更 → 记录预期节省 → 下月核对实际账单
```

关键是**闭环核对**：优化后账单真的降了吗？没有核对，优化就变成"每年说一遍但没人做"。

### 一句话总结

云成本优化的顺序是「**先归因、再关停、再右移、最后换计费**」。跳过归因直接砍资源，通常砍掉的是最不该砍的那部分。
