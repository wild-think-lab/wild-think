### 容量规划要回答三个问题

1. **现在能撑多少**（当前上限）。
2. **什么时候会到上限**（增长曲线）。
3. **到了要加什么**（加哪一层最有效）。

大部分团队只做第 1 个，然后每年被动扩容。

### 五层拆解

| 层 | 指标 | 典型瓶颈 |
| --- | --- | --- |
| 入口 | 带宽、新建连接数、TLS 握手 | 带宽打满、Nginx worker 不够 |
| 应用 | QPS、并发数、线程/协程、GC | CPU、连接池、锁 |
| 缓存 | 命中率、内存、eviction | 命中率骤降导致打穿 |
| 数据库 | 连接数、QPS、写入、慢查询、磁盘 IOPS | 连接池耗尽、锁等待 |
| 存储 | 容量增长、IOPS | 日志与备份吃掉空间 |

**先定位"最先到顶"的一层**，其余的努力都是浪费。

### 单机上限的估算方法

经验值（4 核 8G、普通 SSD）：

| 服务 | 单实例承载 | 备注 |
| --- | --- | --- |
| Nginx 静态 | 数千 QPS，取决于文件大小 | 小文件受 IOPS 限制 |
| Nginx 反代 | 1–2 万连接 | 受内存与 fd 限制 |
| Java 应用 | 200–800 QPS（有 DB 访问） | 视业务复杂度 |
| Go 应用 | 1000–5000 QPS | 简单 JSON 接口 |
| MySQL（单机） | 2000–5000 简单读 QPS | 写更低，受 redo/磁盘限制 |
| Redis | 单线程 8–12 万 ops | 大 key 与 pipeline 会掉 |

这些数字只能当起点，**必须用自己的压测结果替换**。

### 峰值与放大系数

```
日活 × 每人请求数 / 86400 × 峰值系数 = 峰值 QPS
```

峰值系数（峰值 QPS / 平均 QPS）实际值：

- 内部管理系统：3–5
- 面向公众的电商：10–20（大促前另算）
- 有定时任务集中触发的系统：可能到 100

**定时任务集中触发是很多"莫名其妙挂了"的原因**：半夜 2 点几十台机器同时备份，把存储打满。

### 一套可以照着填的表

```
服务：order-api
当前实例：4 × (4C8G)
单实例实测：320 QPS @ P99 180ms（CPU 65%）
目标：峰值 1200 QPS，允许挂 1 台
需要的实例数：1200 / 320 = 3.75 → 取 4（可容 1 台故障）
数据库：峰值 1200 QPS 读，连接池 20/实例 × 4 = 80 连接
   MySQL max_connections=200，安全
   若加实例到 8：连接 160，接近上限 → 需要连接池中间件或读写分离
结论：应用层够，数据库连接数是下一条天花板
```

这张表的价值是**把"加机器"变成"加到哪里、加了之后下一步卡在哪"**。

### 压测该测什么

1. **不是测极限，而是测拐点**：找到"QPS 上升但 P99 开始非线性上涨"的那个点。
2. **测稳态 30 分钟**，不要只跑 1 分钟。内存泄漏与连接泄漏要时间才暴露。
3. **混合场景**：读写比按真实比例（8:2 或 9:1），不要全读。
4. **带真实数据量**：空表上跑出来的 QPS 没有意义，索引选择性完全不同。
5. **观察依赖**：压测时同时看 DB 的 `Threads_running`、Redis 命中率、GC 暂停。

工具选择：

```bash
# 简单接口用 wrk，够快够省
wrk -t8 -c200 -d30s --latency http://localhost:8080/api/v1/orders

# 需要脚本与场景用 k6
k6 run -e BASE_URL=http://localhost:8080 script.js

# 看系统侧
sar -u 5 10; pidstat -d 5 10
```

### 增长预测：三条曲线

- **线性增长**：按过去 6 个月月均增速外推。
- **阶跃增长**：新业务上线、新客户接入——**这类必须提前预留**。
- **季节性**：电商双 11、教育开学季，按去年同期峰值 × 1.5。

把三条画在同一张图上，标出"当前容量线"和"扩容采购周期"，就知道最晚什么时候必须下单。

### 别忘了这些"非计算资源"

- **公网 IP / 域名 / 证书数量**：证书到期是经典事故，做自动续期与到期告警。
- **连接数上限**：云厂商 NAT 网关、SLB 都有连接数限制（常常是隐藏天花板）。
- **文件描述符**：`ulimit -n` 与 systemd 的 `LimitNOFILE`，默认 1024 会在几千并发时直接报 `too many open files`。
- **端口范围**：`net.ipv4.ip_local_port_range` 默认 32768–60999，短连接多时会被耗尽。
- **备份窗口**：数据涨到一定量后，夜间备份跑不完，第二天开始堆积。

### 监控上必须有的四个容量指标

```promql
# 1. 距离资源上限的余量（用 80% 作为预警线）
node_filesystem_avail_bytes / node_filesystem_size_bytes < 0.2
# 2. 连接数使用率
mysql_global_status_threads_connected / mysql_global_variables_max_connections > 0.7
# 3. 实例冗余度
count(up{job="order-api"} == 1) / count(up{job="order-api"})
# 4. 增长速率（周同比）
delta(node_filesystem_used_bytes[7d])
```

容量告警应该比"资源打满"早两周，而不是早两分钟。

### 一句话总结

容量规划不是算命，而是**把自己的上限、增长的斜率、扩容的周期三者画在一张图上**，然后提前一个采购周期动手。
