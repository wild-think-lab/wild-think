### 反直觉一：SLI 选"用户能感知的"，不是"服务器能报的"

```
❌ SLI = 服务的 CPU 使用率
✅ SLI = 成功请求的比例 / 请求延迟在阈值内的比例
```

**四种 SLI 类型**：

| 类型 | 例子 |
| --- | --- |
| 可用性 | 非 5xx 请求 / 总请求 |
| 延迟 | P99 < 200ms 的请求比例 |
| 吞吐 | 每秒成功处理的请求数 |
| 正确性 | 返回结果正确（如对账一致） |

**"正确性"最容易被忽略**：接口 200 但返回错数据，用户感知是"坏的"，而可用性指标看起来是 100%。

### 反直觉二：99.9% 只有 43 分钟，99.99% 只有 4 分钟

```
每月允许不可用时间：
  99%     → 7.2 小时
  99.9%   → 43.2 分钟
  99.99%  → 4.3 分钟
  99.999% → 26 秒
```

**关键理解**：

```
① 99.9% 意味着"每月只能挂 43 分钟"
② 一次计划外的重启（2 分钟）+ 一次故障（10 分钟）+ 一次发布问题（30 分钟）= 就用完了
③ 所以 99.9% 需要"分钟级"的故障恢复能力，而不只是"不出事"
```

**这就是为什么"发布"是可用性的主要威胁**：每次发布都有风险窗口。

### 反直觉三：多依赖的可用性是乘起来的

```
服务 A 依赖 B（99.9%）和 C（99.9%）
A 的可用性上限 = 99.9% × 99.9% = 99.8%
```

**一旦有一条串行依赖链有 5 个 99.9% 的服务**：

```
0.999^5 ≈ 99.5%  → 每月 3.6 小时不可用
```

**对策**：

```
① 减少串行依赖（异步化、缓存、降级）
② 依赖不可用时能降级（不返回错误，返回部分结果）
③ 别宣传"我们的 A 服务是 99.99%"，如果它依赖 5 个 99.9%
```

### 反直觉四：100% 可用是有害目标

```
理由：
① 成本指数增长（最后 0.01% 的成本可能超过前面所有）
② 抑制变更（不敢发布 → 业务停滞）
③ 掩盖真实风险（为了"不挂"而"不部署"，问题只会更大）
```

**正确做法：设定"错误预算"**

```
SLO = 99.9% → 错误预算 = 0.1% 的请求（或 43 分钟/月）
预算没用完 → 可以放心发布
预算用完 → 冻结变更，专注稳定性
```

**错误预算把"稳定性 vs 速度"的争论变成"数字问题"**，这是 SLO 最有价值的地方。

### 怎么定第一个 SLO

**三步**：

```
① 先测现状（过去 30 天的实际可用性是多少？）
② 定一个"略高于现状"的目标（如现状 99.5%，先定 99.7%）
③ 逐步提升（每季度评估一次）
```

**不要一开始就定 99.99%**：达不到就变成"永远在救火"。

### SLO 与告警的关系

**错误预算燃烧速率（burn rate）告警法**：

```
1 小时窗口内燃烧速率 > 14.4  → 紧急告警（约 2% 预算在 1 小时内烧掉）
6 小时窗口内燃烧速率 > 6     → 工单告警
3 天窗口内燃烧速率 > 1       → 记录/观察
```

**为什么比"阈值告警"好**：

```
阈值告警：CPU > 90% 就告警（可能对业务毫无影响）
燃烧率告警：直接告警"可用性正在快速变差"（与用户感知一致）
```

**这是 Google SRE 推荐的"多窗口多燃烧率"告警法**，能同时做到"快"与"少误报"。

### 一份可用的 SLI/SLO 定义

```yaml
service: order-api
slis:
- name: availability
  description: 非 5xx 的请求比例
  good: 'sum(rate(http_requests_total{job="order-api",code!~"5.."}[5m])'
        ' / sum(rate(http_requests_total{job="order-api"}[5m])'
- name: latency
  description: 95% 的请求在 300ms 内
  good: 'sum(rate(http_request_duration_seconds_bucket{job="order-api",le="0.3"}[5m])'
        ' / sum(rate(http_request_duration_seconds_count{job="order-api"}[5m])'

slos:
- sli: availability
  target: 99.9
  window: 30d
- sli: latency
  target: 99.0
  window: 30d

error_budget_policy:
  burn_rate_alerts:
  - window: 1h
    threshold: 14.4
    severity: page
  - window: 6h
    threshold: 6
    severity: ticket
```

### 常见错误

```
❌ SLI 用"平均值"（平均延迟 100ms 掩盖了 P99 是 5 秒）
❌ SLO 目标与业务没对齐（技术定 99.99%，业务其实只要 99.5%）
❌ 有 SLO 但没有错误预算策略（等于没定）
❌ 用"月度"窗口而不滚动（月末最后一天挂 40 分钟就破线）
❌ 只看"我们的 SLI"，不看"用户的 SLI"（用户从他们那边测，可能更差）
```

### 检查清单

```
□ SLI 是用户可感知的（不是 CPU）
□ 包含延迟 SLI（不只看是否 5xx）
□ 有正确性 SLI（关键业务）
□ SLO 从现状出发（不是拍脑袋）
□ 有错误预算（多少分钟/多少请求）
□ 有燃烧率告警（多窗口）
□ 预算用完冻结变更
□ 计算过复合可用性（不是"宣称 99.99%"）
□ 不追求 100%
```
