### 先问"这张图能回答什么问题"

```
没用的图：CPU 使用率（一直 30%，看不出异常）
有用的图：CPU 使用率的 P99 + 饱和度（"排队长度"）
```

**"漂亮但没用"是最常见的监控浪费**。

### 四个黄金信号

```
延迟（Latency）  ：请求多久完成
流量（Traffic）  ：多少请求/多少数据
错误（Errors）   ：失败比例
饱和度（Saturation）：资源排队程度（最关键但最常被忽略）
```

**为什么"饱和度"重要**：

```
CPU 30% 但磁盘队列长度 20 → 已经很慢
CPU 95% 但没有队列 → 说明刚好打满（还能扛）
```

**"使用率高"不等于"快满了"，"排队"才是**。

### USE（资源视角）

```
Utilization（使用率）：资源被使用的时间比例
Saturation（饱和度）：排队长度（进程/请求在等这个资源）
Errors（错误）      ：错误计数
```

**适合"排查瓶颈"**：CPU、内存、磁盘、网络、连接池，每个都问这三个。

### RED（请求视角）

```
Rate（速率）    ：每秒请求数
Errors（错误）  ：每秒失败数 / 失败比例
Duration（耗时）：延迟分布（P50/P95/P99）
```

**适合"看服务健康"**：API、数据库查询、下游调用。

**"USE 看资源，RED 看请求"**，两张都要有。

### 五个"图表漂亮但没用"的原因

**① 只有平均值**

```
平均延迟 50ms 看起来很好，但可能有 1% 请求 3 秒
→ 必须看分位数（P95/P99）
```

**"平均值会掩盖长尾"是监控的第一课**。

**② 没有基线**

```
图中只有一条"当前值"曲线
→ 看不出"今天和上周比如何"
→ 应该叠加"上周同时段"或"7 天前"
```

**③ 指标命名模糊**

```
差的：requests_total、latency
好的：http_requests_total{code="500"}、http_request_duration_seconds{quantile="0.99"}
```

**规范**：

```
<namespace>_<subject>_<unit>
单位必带（_seconds / _bytes / _total）
```

**④ 标签基数爆炸**

```
{url="/api/user/12345"} → 每个用户一个序列
→ Prometheus 内存爆炸
```

**处理**：

```
① URL 用模板化（/api/user/{id}）
② 高基数信息不做标签（放日志）
③ 必要的维度控制基数（如 status_code 而非 error_message）
```

**⑤ 缺少"业务指标"**

```
只有技术指标（CPU/QPS），没有业务指标（下单量/支付成功率）
→ 技术全绿但业务已经挂了
```

**必须有"业务侧"的黄金指标**：

```
核心转化率、订单量、支付成功率、登录成功率
```

### 一个"分层"的指标体系

```
① 业务层：订单量、支付成功率、DAU
② 应用层：QPS、错误率、P99 延迟
③ 依赖层：数据库慢查询数、连接池占用、缓存命中率、MQ 积压
④ 资源层：CPU/内存/磁盘/网络（USE）
⑤ 基础设施：节点存活、证书到期、磁盘水位
```

**排查路径通常是"从业务层往下钻"**：

```
用户投诉支付失败 → 应用层错误率 ↑ → 依赖层发现数据库连接池满 → 资源层发现数据库 IO 饱和
```

**"分层"让排查有方向**。

### 告警的"质量"比"数量"重要

```
好的告警：能回答"什么问题、影响谁、怎么处理"
差的告警：只有一句"CPU 高"
```

**每条告警应有**：

```
① 判据（阈值 + 持续时间）
② 影响面（哪个服务/多少用户）
③ 处理动作（runbook 链接）
④ 分级（P0–P3）
```

**"告警预算"**：

```
团队 5 人 → 每天告警 < 20 条
超过 → 要么阈値不合理，要么关联没做
```

### 四个"必须有"的仪表盘

```
① 服务总览：可用性 + QPS + 错误率 + P99（每服务一行）
② 依赖健康：DB/缓存/MQ/下游 API 的延迟与错误
③ 资源水位：CPU/内存/磁盘（含"趋势与预测"）
④ 变更与告警：最近发布 + 最近告警（把"变更"和"异常"放一起）
```

**"把变更和告警放一起"能直接关联"是不是刚发布导致的"**。

### SLO 与指标的关系

```
SLI（指标）：如"请求成功率"
SLO（目标）：如"99.9% 成功率 / 30 天"
错误预算   ：允许的失败次数
```

**SLO 的价值在于"决定什么时候该停手"**：

```
错误预算耗尽 → 停止发布新功能，先修稳定性
```

**"没有 SLO 的监控"只能事后救火**。

### 检查清单

```
□ 四个黄金信号都有（含饱和度）
□ 延迟看分位数（不只看平均）
□ 图有基线对比（上周同时段）
□ 指标命名规范（带单位）
□ 标签基数可控（URL 模板化）
□ 有业务指标（不只技术指标）
□ 分五层指标体系（业务→资源）
□ 每条告警有判据/影响/runbook
□ 有告警预算（每天 < 20 条）
□ 四个必备仪表盘
□ 有 SLI/SLO 与错误预算
```
