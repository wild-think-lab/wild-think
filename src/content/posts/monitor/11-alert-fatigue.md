### 300 条告警的后果

```
第 1 周：认真看
第 2 周：只看标红的
第 3 周：全部静音
第 4 周：真故障没人看 → 事故
```

**告警太多 = 没有告警**。这是运维里最常见的隐性故障。

### 四个成因

| 成因 | 例子 |
| --- | --- |
| 阈值太敏感 | CPU > 60% 就告警（业务高峰必触发） |
| 同一根因多次告警 | 一个节点挂了，20 个 Pod 都报"不可达" |
| 没有分级 | 磁盘 70% 和 数据库挂了都发同一个渠道 |
| 告警没有"下一步" | "XXX 异常"，收到后不知道该做什么 |

### 分级：三个渠道，不要混

| 级别 | 触发条件 | 通知方式 | 响应要求 |
| --- | --- | --- | --- |
| P1 严重 | 用户可感知的业务中断 | 电话/短信 + 值班群 | 5 分钟响应 |
| P2 警告 | 冗余下降、容量水位、性能退化 | IM 群 | 30 分钟处理 |
| P3 关注 | 趋势性问题、待优化项 | 邮件/工单 | 每周处理 |

**规则**：P1 一个月不超过 2–3 次。如果每周都有 P1，说明分级错了。

### 聚合：把"一因多果"合并

Prometheus Alertmanager 的做法：

```yaml
route:
  group_by: [alertname, cluster, service]     # 按这三项聚合
  group_wait: 30s                             # 首次等待，攒一攒
  group_interval: 5m                          # 同组新增的间隔
  repeat_interval: 4h                         # 持续告警的重复间隔
```

效果：一个服务 10 个 Pod 同时异常 → **1 条告警**而不是 10 条。

按 `alertname` 聚合还有一层意义：**同一个指标在多台机器上触发，合并成一条"3 台机器磁盘 > 85%"**。

### 抑制：根因告警压住派生告警

```yaml
inhibit_rules:
- source_match: { alertname: NodeDown }
  target_match_re: { alertname: "PodNotReady|ServiceUnavailable" }
  equal: [node]                  # 同一个节点上
```

含义：节点宕机时，**压住该节点上的所有 Pod 告警**——因为根因已经很明确。

没有抑制规则的后果：

```
一台节点宕机 → 节点告警 1 条 + 该节点上 30 个 Pod 各 1 条 = 31 条
```

### 静默：计划内的变更

```bash
# 命令行创建静默
amtool silence add alertname="HighCPU" --duration=2h \
  --comment="计划内压测" --author="ops"
```

要点：

- **必须写原因和结束时间**（不留永久静默）。
- 静默到期自动恢复。
- 静默期间如果真出别的问题，**不能也静默掉**（静默要精确匹配）。

### 每条告警都该有"下一步"

告警内容模板：

```
标题：prod-api 节点内存使用率 92%
分级：P2
影响：该节点上 8 个 Pod，可能触发驱逐
第一步：kubectl top pod -n prod --sort-by=memory | head
第二步：检查是否有内存泄漏（对比 24 小时趋势）
文档：https://runbook.example.com/memory-high
```

**没有"第一步"的告警，等于制造焦虑**。

### 用数字衡量告警质量

| 指标 | 健康值 |
| --- | --- |
| 每周告警总数 | < 30 条（P1+P2） |
| 告警中"有动作"的比例 | > 80%（收到后有人做了什么） |
| P1 误报率 | < 10% |
| 平均确认时间（MTTA） | < 10 分钟 |
| 重复告警占比 | < 20% |

**"有动作的比例"最关键**：如果 90% 的告警收到后没人做任何事，那些告警就该删。

### 一次告警精简的过程

初始：每天 280 条，来自 47 条规则。

**第一步：统计**

```
按规则统计触发次数 Top 10 → 占总量 85%
```

**第二步：逐条判断**

| 规则 | 判断 | 动作 |
| --- | --- | --- |
| CPU > 60% | 业务高峰常态 | 改成 > 85% 且持续 10 分钟 |
| 磁盘 > 70% | 长期在 75% | 改成 > 85% |
| Pod 重启 | 每次发布都触发 | 加"排除滚动更新窗口"的条件 |
| 节点 NotReady | 有意义 | 保留，加抑制规则 |
| 证书剩余 < 30 天 | 有意义 | 保留，降为 P3 邮件 |

**第三步：结果**

```
280 条/天 → 12 条/天，其中 P1 每月 1–2 次
值班人员开始真的看告警了
```

### 检查清单

```
□ 告警有三级，P1 少而准
□ 有 group_by（按 alertname + service）
□ 有 inhibit_rules（根因压制派生）
□ 静默有原因与到期时间
□ 每条告警有"下一步"与 runbook 链接
□ 每周统计告警数量与"有动作比例"
□ 定期删掉"没人处理"的规则
```
