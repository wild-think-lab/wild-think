### 告警疲劳是怎么形成的

典型过程：上监控 → 规则全设 80% 阈值 → 一天 300 条 → 大家静音 → 真故障没人看。

根因不是"规则太多"，而是**规则没有分级、没有上下文、没有责任归属**。

### 四条收敛策略

1. **分级**：只有 P0 打扰人，P1 进群，P2/P3 进日报。
2. **去重合并**：同一实例同一类型合并（Alertmanager 的 `group_by`）。
3. **抑制（inhibit）**：`InstanceDown` 触发时，抑制该实例上的 CPU/磁盘告警——机器都连不上了，报磁盘没意义。
4. **依赖关系**：核心交换机挂了，下游 200 条告警都应该被抑制。

```yaml
# Alertmanager 抑制示例
inhibit_rules:
  - source_match: { alertname: "InstanceDown" }
    target_match_re: { alertname: "DiskWillFillIn4Hours|HighCPU" }
    equal: ["instance"]
```

### 告警内容要能直接指导动作

差的告警：

```text
CPU usage > 90% on web01
```

好的告警：

```text
[P1] web01 CPU 持续 92%（15 分钟）
可能原因：批量任务 / 死循环 / 流量突增
先看：top -b -n1 | head -20; 查 /var/log/app 最近错误
面板：https://grafana/...
```

告警的价值是**把判断成本降到最低**，不是把数字发出来。

### 值班交接的三件事

1. **当前状态**：哪些告警未恢复、已做了什么。
2. **待观察项**：刚发的版本、刚到阈值的磁盘。
3. **已知问题**：这台机器本来就慢、那个告警是误报（并附原因）。

口头交接必漏，写进值班记录里。

### 故障复盘模板

```markdown
## 事故概要
- 影响：<谁受影响、多久、多大范围>
- 级别：P0 / P1
- 时间：发现 10:12 / 恢复 10:48（36 分钟）

## 时间线
10:12 监控报警：5xx 率上升
10:15 确认后端连接池耗尽
10:20 回滚版本 v2.3.1
10:48 错误率恢复正常

## 根因
新版本把连接池上限从 50 改成 5（配置模板变量未生效）

## 修复
- 立即：回滚
- 短期：加配置校验与启动自检
- 长期：发布前 diff 配置、灰度 10% 观察 10 分钟

## 待办（负责人 / 截止）
- [ ] 配置校验脚本 @张三 11-30
- [ ] 灰度流程写入发布手册 @李四 12-05
```

三条原则：**对事不对人**、**每个待办有主**、**区分"立即/短期/长期"**。没有责任人和截止时间的复盘等于没做。

### 从告警到 SLO

复盘多了会发现规律：大部分 P0 来自少数几个环节。把这些环节写成 SLO：

```text
发布成功率 ≥ 99%
数据库主从延迟 P95 < 1s
核心接口 P95 < 300ms
```

然后用错误预算决定"这周能不能发版"。这就是从"救火"走向"防火"的转折点。

### 本章要点

- 告警疲劳根源是没分级、没上下文、没归属。
- 抑制规则能消掉大量连带告警。
- 告警正文要写"先看什么"，而不只是数字。
- 复盘必须有时间线、根因、待办（带人和日期）。
