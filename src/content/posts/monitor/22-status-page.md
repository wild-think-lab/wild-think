### 四个等级（对外统一口径）

```
① Investigating  已发现，正在定位
② Identified     已定位原因，正在处理
③ Monitoring     已恢复，观察中
④ Resolved       已彻底解决
```

**"没有等级，只有'稍后通知'"** → 用户更焦虑。

### 更新节奏

```
P0：每 15–30 分钟一条（即使"无进展"也要发）
P1：每 30–60 分钟
P2：开始与结束各一条
```

**"无进展也发"** 的意义：让用户知道"有人在处理"。

### 第一条该写什么

```
① 影响什么（功能/区域/比例）
② 什么时候开始
③ 现在在做什么
④ 下次更新时间
```

**示例**：

```
[Investigating] 14:05 起，部分用户登录失败（约 30%）。
已定位到认证服务异常，正在切换备用节点。
下次更新 14:35。
```

**"我们正在紧急处理中"** 不提供任何信息。

### 五个"越解释越糟"

**① 甩锅外部**

```
"云厂商网络问题"（如果没证据，会被追问）
```

**② 过度技术细节**

```
用户不关心 "etcd 集群 leader 选举"
```

**③ 承诺时间**

```
"20 分钟内恢复"（没恢复就失信）
→ 说"下次更新时间"，不说"恢复时间"
```

**④ 隐瞒范围**

```
明明影响 50%，写"少数用户"
→ 被发现后信任崩塌
```

**⑤ 结束后不写复盘**

```
Resolved 之后就没了 → 同一个问题会再来
```

### 状态页的技术实现

```
① 独立域名/子域（不依赖主站，主站挂了它还能用）
② 静态页 + 外部监控写入（API 驱动）
③ 组件化（登录/支付/API 分别显示）
④ 历史事件保留（可追溯）
```

**"状态页和业务同集群"** → 业务挂了状态页也挂了（最尴尬）。

### 组件粒度

```
- API
- 登录/认证
- 支付
- 控制台
- 第三方依赖（短信/对象存储）
```

**"全站一个绿灯"** 无法表达"部分可用"。

### 与内部流程的配合

```
① 事件指挥官（IC）负责对外口径
② 沟通负责人（CLO）负责写状态页
③ 技术负责人（TL）负责定位
④ 三者分离，避免"一个人又要修又要写"
```

### 事后

```
① Resolved 后 24h 内发简短说明（影响 + 原因 + 措施）
② 5 个工作日内出完整复盘
③ 状态页保留历史（可查）
```

### 检查清单

```
□ 状态页独立于主站
□ 有四个等级口径
□ 有固定更新节奏（含"无进展"）
□ 组件粒度合理
□ 第一条含"影响/开始时间/下一步/下次更新"
□ 不承诺恢复时间
□ 不甩锅、不隐瞒范围
□ 有 IC/CLO/TL 分工
□ Resolved 后有说明与复盘
□ 历史事件可追溯
□ 有演练（模拟一次故障发状态页）
```
