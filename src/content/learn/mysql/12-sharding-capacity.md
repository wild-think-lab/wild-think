### 先别急着分

```
优化顺序：索引 → SQL 改写 → 缓存 → 读写分离 → 归档 → 才考虑拆分
```

**判据（不是绝对）**：

```
单表 > 千万行且频繁范围扫描
单库 QPS 接近单机上限
单库磁盘/备份窗口不可接受
```

**"上来就分 16 库"** → 事务、join、报表全崩，收益却没到。

### 三种拆分

```
① 垂直分库：按业务（订单库/用户库）
② 垂直分表：冷热字段分离（大字段单独表）
③ 水平分表：按分片键把行打散
```

### 分片键怎么选

```
好：查询条件里高频出现、分布均匀（user_id、tenant_id）
差：时间（热点全在最新分片）、随机 UUID（范围查询全扫）
```

**"按时间分片"** → 写入全压在一个分片。

### 跨片代价

```
① 跨片 join：基本不可用
② 跨片事务：需 2PC/最终一致
③ 跨片排序分页：要各片取 N 条再归并
④ 聚合统计：要预聚合或离线算
```

**"分完还想做实时报表"** → 需要额外的汇总链路。

### 路由方式

```
① 应用层分片（算 sharding key）
② 中间件（ShardingSphere / ProxySQL 分片）
③ 数据库原生分区（partition，不是分片）
```

```sql
-- 原生分区（单机内，能减小单表扫描）
CREATE TABLE orders (...) PARTITION BY RANGE (YEAR(created_at)) (
  PARTITION p2024 VALUES LESS THAN (2025),
  PARTITION p2025 VALUES LESS THAN (2026)
);
```

**注意**：分区不解决单机 QPS 上限。

### 扩容（最难的部分）

```
① 预分片（一开始就分够，如 64 片，后期只搬不重算）
② 一致性哈希（减少搬迁）
③ 双写迁移（新老并存 → 校验 → 切读 → 下线老）
```

**"取模 16 改成取模 32"** → 几乎全部数据要搬。

### 五个"分了更慢"

**① 分片键选错**

```
按用户分片，但查询按订单号 → 每次扫全片
```

**② 片太多**

```
连接数 × 片数 → 连接池打满
```

**③ 跨片分页**

```
每片取 1000 条再归并 → 深翻页爆炸
```

**④ 忘记全局唯一 ID**

```
自增 ID 在各片重复 → 主键冲突
```

**⑤ 报表直接查分片库**

```
全片扫描 → 拖垮线上
```

### 全局 ID 方案

```
① 号段模式（DB 分配区间，应用本地发号）
② Snowflake（时间 + 机器 + 序列）
③ UUID（简单但索引不友好）
```

### 检查清单

```
□ 先优化再拆分（有数据支撑）
□ 分片键分布均匀且高频
□ 预分片（留扩容空间）
□ 全局唯一 ID 方案
□ 跨片查询有明确替代（汇总表/ES）
□ 分页有上限（禁深翻页）
□ 连接池按片数评估
□ 有双写迁移与校验
□ 报表走独立链路
□ 有分片监控（热点片）
```
