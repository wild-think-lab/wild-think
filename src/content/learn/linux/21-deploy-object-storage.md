## 一、先弄懂它是什么

**对象存储不是"另一种网盘"，它是三种存储形态里的一种。**

| 形态 | 访问方式 | 数据单位 | 典型用途 |
| --- | --- | --- | --- |
| 块存储 | iSCSI / 云盘 /dev/sdb | 扇区（无文件语义） | 数据库、虚拟机磁盘 |
| 文件存储 | NFS / SMB，POSIX 语义 | 文件 + 目录树 | 共享目录、代码、文档协作 |
| 对象存储 | HTTP API（S3 协议） | 对象（键 + 数据 + 元数据） | 附件、备份、日志归档、模型文件 |

**为什么是"扁平"的**：对象存储里没有目录，只有桶（Bucket）和键（Key）。你在控制台看到的"文件夹"，其实是键名的前缀（`photos/2026/11/a.jpg` 里的 `photos/2026/11/`）。这样做的好处是没有目录锁、没有 inode 竞争，元数据极小，才能横向扩到几十 PB。

**它解决的问题**：一次写入、多次读取、按对象整取的海量数据。备份包、图片、视频、日志归档、模型权重都符合这个模式。

**它不能解决的问题**：数据库文件、需要频繁随机改写的文件、需要文件锁/追加写/重命名的场景。对象存储的"更新"本质是"整对象重写"，`rename` 也是复制 + 删除。

### 原理：纠删码 vs 多副本

```
多副本：一份数据存 3 份，空间利用率 33%，恢复最快
纠删码：把对象切成 k 块 + m 块校验（如 4+2），
        任意 2 块丢失仍可恢复，空间利用率 4/6 ≈ 67%
```

MinIO 默认走纠删码（Erasure Code），这就是它"4 节点起"的原因：校验块要分散到不同节点/盘上，节点太少无法形成有效的纠删组。

### 必须先分清的概念

| 概念 | 含义 | 容易搞错的地方 |
| --- | --- | --- |
| Bucket | 桶，命名空间 + 策略边界 | 桶策略是"私有/公开"，不是账号权限 |
| Object | 键 + 数据 + 元数据 | 键可以带斜杠，但没有真正的目录 |
| Prefix | 键的前缀，用来"模拟目录"和批量列举 | 列举是前缀匹配，不是目录遍历 |
| Access Key / Secret Key | 调用 API 的凭据 | 应用要用独立密钥，不要用 root |
| Presigned URL | 带签名的临时下载/上传链接 | 有时效，别长期贴在前端 |
| Versioning | 对象版本，防覆盖与误删 | 会占双倍空间，要配生命周期 |
| ILM | 生命周期规则（过期删除/转储） | 不配就永远增长 |

### 什么情况该自建，什么情况不该

```
该自建：内网备份归档、数据不能出内网、需要 S3 兼容但不想被云厂商绑死
不该自建：数据量小（用云对象存储更省心）、要求强一致事务、需要 POSIX 挂载语义
```

**判据**：先问"数据是整取还是随机改"。整取 → 对象存储合适；随机改 → 文件系统或数据库。

### 为什么自建对象存储

```
① 备份/日志归档需要便宜的大容量
② 应用要 S3 接口（不想被云厂商绑死）
③ 图片/附件/模型文件独立于数据库
```

**"文件存数据库"** → 库变大、备份变慢、并发差。

### 单机部署（容器）

```bash
docker run -d --name minio \
  -p 9000:9000 -p 9001:9001 \
  -e MINIO_ROOT_USER=admin \
  -e MINIO_ROOT_PASSWORD='<强密码>' \
  -v /data/minio:/data \
  -v /etc/localtime:/etc/localtime:ro \
  quay.io/minio/minio server /data --console-address ":9001"
```

**要点**：

```
① 数据目录必须挂出来
② 9000 是 API，9001 是控制台
③ 单机就是单点，重要数据要异地
```

### 分布式（纠删码）

```bash
minio server http://node{1...4}/data{1...2}
```

```
① 至少 4 节点（纠删码需要）
② 各节点盘数一致，容量一致
③ 用 DNS/主机名，不要用会变的 IP
```

**判据**：N 节点可容忍 N/2 节点故障（视配置）。

### 桶与策略

```bash
mc alias set local http://127.0.0.1:9000 admin '<pwd>'
mc mb local/backup
mc anonymous set none local/backup      # 禁止匿名
```

```bash
# 生命周期：30 天后自动删除
mc ilm rule add local/backup --expire-days 30
mc ilm rule ls local/backup
```

**"桶设成 public"** → 全网可下载，是最常见的泄密原因。

### 应用接入（S3 兼容）

```python
import boto3
s3 = boto3.client("s3", endpoint_url="http://10.0.0.30:9000",
                  aws_access_key_id="app", aws_secret_access_key="***")
s3.upload_file("a.zip", "backup", "a.zip")
```

**注意**：

```
① 用独立 access key（不用 root 账号）
② 权限按桶/前缀限定
③ 预签名 URL 给前端直传（别让文件过应用）
```

### 五个"存进去取不出来"

**① 路径/桶名写错**

```
list 看不到对象（前缀不匹配）
```

**② 权限只给了 ListBucket 没给 GetObject**

```
能看列表，下载 403
```

**③ 时钟偏差导致签名失效**

```
S3 签名对时间敏感（NTP 必须准）
```

**④ 大文件超时**

```
分片上传（multipart）或直传
```

**⑤ 磁盘满 → 写入失败但读还在**

```
监控容量水位（80% 告警）
```

### 容量与备份

```
① 逻辑备份：mc mirror 到另一个集群/云
② 版本控制：开启 object versioning（防误删）
③ 保留期与生命周期规则
```

```bash
mc mirror --overwrite local/backup remote-site/backup
```

### 检查清单

```
□ 数据目录独立挂盘
□ 控制台端口不暴露公网
□ 桶默认私有
□ 应用用独立 key + 最小权限
□ 前端用预签名直传
□ NTP 准（签名依赖时间）
□ 有容量水位告警
□ 有版本控制/防误删
□ 有异地 mirror
□ 有生命周期清理规则
```
