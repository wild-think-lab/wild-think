### 成本花在哪

```
① 计算（CPU/内存 request 预留）
② 存储（PV + 备份 + 快照）
③ 网络（跨区流量/公网带宽）
④ 人力（运维与救火）
```

**"request 预留"** 是最容易被忽视的成本：预留了但没用到，也算钱。

### 三个利用率指标

```
① CPU 实际使用 / request
② 内存实际使用 / request
③ 卷实际使用 / 声明容量
```

```bash
kubectl top pods -A --sort-by=cpu | head
kubectl describe node | grep -A6 "Allocated resources"
```

**判据**：

```
平均利用率 < 20% 且稳定 → 可下调 request
request 总和 > 节点容量 80% → 该扩容或调小
```

### 六个"看起来忙其实浪费"

**① request 拍脑袋给大**

```
每个服务都给 2C4G，实际 0.2C
```

**② 副本数固定不弹**

```
低峰仍 10 副本（HPA 的 minReplicas 太高）
```

**③ 镜像太大**

```
拉取耗带宽 + 存储（每节点缓存多份）
```

**④ 日志无限保留**

```
Loki/ES 存了 180 天但没人查 7 天前的
```

**⑤ 快照堆叠**

```
每次变更打快照，从不清理
```

**⑥ 多套环境共用生产规格**

```
测试环境也 8C16G × 20 副本
```

### 治理的四个动作

```
① 基线：每个服务记录 request/实际使用
② 调整：按 P95 使用 + 20% 余量定 request
③ 弹性：低峰缩容（HPA minReplicas 合理）
④ 清理：镜像/日志/快照有保留策略
```

**"一次全调小"** 会在高峰翻车（要分批 + 观察）。

### 一个季度节奏

```
Q 初：出"成本与利用率"报表（按团队/服务）
Q 中：挑 Top 10 浪费项，逐项改
Q 末：复测 + 更新基线
```

**"只出报表不改"** = 没人看。

### 本章检查清单

```
□ 有按服务/团队的资源台账
□ 有 request vs 实际使用对比
□ 低利用率服务有下调计划
□ HPA min/max 合理
□ 镜像瘦身有标准
□ 日志/快照有保留策略
□ 测试环境规格与生产分离
□ 有季度成本报表
□ 调整分批且有观察
□ 成本变化有记录（可追溯）
```
