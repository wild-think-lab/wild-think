### 规划的三个决定

```
① 前缀来源（运营商 /56 或 /48，或 ULA 内部使用）
② 每个网段一个 /64（SLAAC 要求）
③ 是否需要 v4（双栈 vs v6-only）
```

**"切 /80 子网"** 会破坏 SLAAC（接口 ID 需要 64 位）。

### 一个办公网的地址表

| 网段 | v4 | v6 |
| --- | --- | --- |
| 办公 | 192.168.10.0/24 | 2001:db8:10::/64 |
| 访客 | 192.168.20.0/24 | 2001:db8:20::/64 |
| 服务器 | 192.168.40.0/24 | 2001:db8:40::/64 |

**编号与 VLAN 对齐**（VLAN 10 ↔ 第 10 个 /64）便于记忆与排障。

### RA 与 DHCPv6 分工

```
RA：下发前缀 + 默认路由（必需）
DHCPv6：下发 DNS（可选，或用 RA 的 RDNSS）
```

**关键参数**：

```
RA 的 A 位 = 1 → 允许 SLAAC
RA 的 M 位 = 1 → 用 DHCPv6 获取地址（而非 SLAAC）
```

### v6 防火墙（必须独立配）

```bash
# nftables 示例
nft add rule inet filter input ip6 nexthdr icmpv6 accept
nft add rule inet filter input tcp dport { 22, 80, 443 } accept
nft add rule inet filter input counter drop
```

**"v4 配了 v6 没配"** → v6 默认可能更宽松（暴露面反而变大）。

**必须放行 ICMPv6**（尤其是 `packet too big`），否则 PMTU 会卡死大包。

### PMTU：v6 最容易踩的坑

```
v6 中间路由器不分片
→ 依赖 ICMPv6 "Packet Too Big" 通知源端
→ 该消息被拦 → 小包通、大包卡
```

**验证**：

```bash
ping6 -s 1400 -M do 2001:db8::1
```

### 迁移的分阶段路径

```
阶段 1：内部双栈（设备有 v6 地址，但 DNS 只发 A）
阶段 2：内部服务用 v6 访问（验证路径与防火墙）
阶段 3：对外发 AAAA（先低权重灰度）
阶段 4：观察回退率（有 v6 不通的用户要能降级）
```

**"一次性全发 AAAA"** 会让"v6 不通"的用户直接打不开。

### 五个风险点

```
① 前缀变更（运营商换 /56）→ 规则/白名单全失效
② 只有 AAAA 没有连通 → 首包超时才回落
③ 监控只测 v4 → v6 故障不可见
④ 日志里 v6 地址没规范化（:: 压缩）
⑤ NAT64/DNS64 让"以为支持 v6"但其实转发
```

### 一个"能上线"的检查表

```
□ 前缀与 /64 规划完成
□ RA/DHCPv6 参数一致
□ v6 防火墙与 v4 对齐
□ ICMPv6 放行（含 PMTU）
□ DNS AAAA 灰度
□ 监控采集 v6 可用性
□ 有"v6 不可用"的回退验证
□ 前缀变更流程明确
□ 文档记录每个网段的 v6 段
```

### 检查清单

```
□ 每网段一个 /64
□ 编号与 VLAN 对齐
□ RA 允许 SLAAC（或明确 DHCPv6）
□ v6 防火墙独立配置
□ ICMPv6 放行
□ PMTU 测试过
□ AAAA 灰度发布
□ 双栈监控
□ 有回退方案
```
