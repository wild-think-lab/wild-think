### 复盘的目的不是"找责任人"

```
坏的复盘：谁操作失误 → 批评 → 大家以后不敢上报
好的复盘：为什么会失误 → 系统怎么改 → 下次不会再发生
```

**核心原则**：**对事不对人，找系统缺陷而不是人的过错**。

### 复盘模板

```markdown
# 故障复盘：订单接口 5xx（2026-11-27）

## 一、基本信息
- 影响时间：10:05 – 10:38（33 分钟）
- 影响范围：下单接口，约 12% 请求失败
- 影响用户：约 3400 人
- 级别：P2

## 二、时间线（精确到分钟）
| 时间 | 事件 | 来源 |
| --- | --- | --- |
| 09:10 | 配置中心调整连接池 50→80 | 变更记录 |
| 10:05 | 5xx 率突增到 12% | 监控告警 |
| 10:07 | 值班确认，开始排查 | 值班记录 |
| 10:15 | 发现 DB 连接数打满 | 排查记录 |
| 10:22 | 回滚池大小到 50 | 变更记录 |
| 10:30 | 5xx 率回落 | 监控 |
| 10:38 | 确认恢复，结束 | 值班记录 |

## 三、根因
配置调整使 20 个实例 × 80 = 1600 连接，超过 DB max_connections(1000)。
超出部分连接失败 → 应用报 5xx。

## 四、为什么没有被提前发现
1. 配置变更没有"连接数总量"的校验
2. 监控只看 5xx 率，没有"连接池使用率"告警
3. 变更流程里没有"DBA 会签"

## 五、做对了什么
1. 告警在 2 分钟内触发
2. 值班按 runbook 定位到 DB
3. 回滚 8 分钟完成

## 六、改进项（必须有人有期限）
| 改进 | 负责人 | 期限 | 验证方式 |
| --- | --- | --- | --- |
| 配置变更加连接数总量校验 | @A | 12-05 | 试改一次，被拦截 |
| 加连接池使用率告警（>80%） | @B | 12-03 | 人为压测触发 |
| 变更流程加 DBA 会签 | @C | 12-10 | 下个变更走一遍 |
| runbook 补"连接数打满"处置 | @A | 12-02 | 演练验证 |

## 七、不会做的事（明确边界）
- 不改连接池默认值（50 是经过压测的合理值）
```

**"不会做的事"这一段很重要**：它防止复盘变成"加一堆限制"。

### 把"人的失误"翻译成系统改进

| 表面原因 | 系统原因 | 改进 |
| --- | --- | --- |
| 运维改错了参数 | 变更没有校验与审批 | 加自动校验 + 会签 |
| 忘了续证书 | 没有到期提醒 | 加监控告警（剩余 < 14 天） |
| 没看告警 | 告警噪音太多 | 收敛告警，只留可行动的 |
| 排查太慢 | 没有 runbook | 写 runbook + 演练 |
| 单点故障 | 架构没有冗余 | 加副本/多可用区 |

**"再培训一次"通常不是有效改进**：人会疲劳、会换岗。

### 防再发的三个层次

```
① 让问题不再发生（消除根因）
② 让问题发生时能自动恢复（冗余/自愈）
③ 让问题发生时能快速发现与处理（监控/runbook）
```

**大多数团队只做③，少数做②，很少做①**。

**优先级建议**：

```
① 影响可用性的 → 必须做②（冗余）
① 根因能低成本消除的 → 做①
③ 一定要做（这是止损底线）
```

### 知识沉淀的三件事

**① Runbook（可执行的处置手册）**

```markdown
# Runbook：订单接口 5xx 率升高

## 判断
- 5xx 率 > 1% 持续 2 分钟

## 第一步：确认范围
kubectl -n prod get pods -l app=order
curl -s https://api.example.com/healthz

## 第二步：看依赖
mysql -e "show status like 'Threads_connected'"
redis-cli info clients

## 第三步：常见原因与处置
| 原因 | 判断 | 处置 |
| --- | --- | --- |
| DB 连接打满 | Threads_connected ≈ max | 回滚池配置/重启部分实例 |
| 依赖超时 | 日志 context deadline | 降级/限流 |
| 发布问题 | 最近有发布 | 回滚版本 |

## 最后验证
5xx 率 < 0.1% 持续 5 分钟

## 最后更新
2026-11-27 by @A（演练验证过）
```

**Runbook 必须有"最后验证日期"**，否则会变成过期文档。

**② 演练（让 runbook 真的能用）**

```
每月一次：按 runbook 走一遍（在预发环境注入故障）
→ 会发现命令过时、权限不够、联系人变了
```

**③ 案例库（把一次教训变成团队资产）**

```
每个 P1/P2 故障写一篇"案例卡片"：
- 现象（一句话）
- 判断路径（怎么定位的）
- 根因
- 通用教训（下次遇到类似现象怎么想）
```

**"通用教训"比"具体细节"更有价值**：

```
例：连接复用场景下"随机断开"多半是 keepalive 时间不匹配
    这条经验能用在所有反代/网关场景
```

### 复盘会的组织

```
① 提前发材料（时间线 + 数据），不要现场回忆
② 主持人不是当事人（避免自我辩护）
③ 先讲事实，再讲判断
④ 改进项必须有人有期限
⑤ 控制在 60 分钟内
```

**"改进项必须有验证方式"**：

```
❌ "加强监控"
✅ "加连接池使用率告警，阈值 80%，12-03 前上线，用压测验证能触发"
```

### 检查清单

```
□ 复盘对事不对人
□ 时间线精确到分钟（含来源）
□ 根因是一句话（不是一堆现象）
□ 分析"为什么没提前发现"
□ 记录"做对了什么"（正向激励）
□ 改进项有人有期限有验证方式
□ 有"不会做的事"（防过度反应）
□ 更新了 runbook 并填了验证日期
□ P1/P2 写了案例卡片
□ 定期演练 runbook
```
