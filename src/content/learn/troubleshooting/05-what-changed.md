### 一句经验

```
"什么都没改"是故障排查里最危险的一句话
```

**因为**：

```
你没改 ≠ 别人没改 ≠ 环境没变 ≠ 数据没变 ≠ 依赖没变
```

### 五个变更来源

**① 你的发布**

```bash
git log --since="1 day ago" --oneline
# 容器
kubectl rollout history deploy/app
kubectl get events --sort-by=.lastTimestamp | head -30
```

**② 别人的发布（依赖/平台）**

```
上游服务的发布窗口
中间件升级（DB/PG/Redis 小版本）
K8s 平台升级
```

**③ 配置与数据**

```
配置中心改了参数
数据库数据量增长（今天破 1 亿行 → 某个查询从 200ms 变 2s）
证书过期
License 到期
```

**④ 环境与容量**

```
流量增长（活动、爬虫、被转载）
某个节点下线（容量少一份）
上游限流阈值变了
```

**⑤ 时间与外部**

```
定时任务叠加（每小时任务都在整点跑）
月末/季末对账
第三方接口变更（限流/字段/证书）
```

### 把时间轴对齐

**做法：把所有"变更记录"和"故障开始时间"放在一张时间轴上**。

```markdown
09:00  发布 v2.3.1（订单服务）
09:10  配置中心调整 pool size 50→80
09:30  某节点磁盘告警 85%
10:05  用户反馈下单失败
10:08  告警：订单接口 5xx 率 12%
```

**判断**：

```
故障在 10:05 开始，最近一次变更是 09:10
→ 09:10 的配置改动优先怀疑（50→80 让 DB 连接打满）
```

**"最后一次变更"通常就是根因**，但要注意：

```
有"延迟显现"的变更（如内存泄漏、磁盘增长、连接数累积）
→ 变更发生在几小时前，故障现在才出现
```

**容器与 K8s 的事件查询**：

```bash
kubectl get events -A --sort-by=.lastTimestamp \
  --field-selector type=Warning | tail -30
```

### "没变也能坏"的四种情况

**① 累积型**

```
连接不释放 → 几天后打满
日志不切分 → 磁盘慢慢满
内存泄漏 → 一周后 OOM
```

**处理**：看趋势，不看单点。

```bash
# 连接数趋势
for i in 1 2 3; do mysql -e "show status like 'Threads_connected'"; sleep 60; done
```

**② 阈值型**

```
数据量跨过某个点 → 查询计划从走索引变成全表扫
QPS 跨过某个点 → 缓存命中率骤降
```

**处理**：看"刚好跨过阈值"的证据（如 `EXPLAIN` 对比）。

**③ 外部依赖型**

```
第三方证书过期
上游改了限流
DNS 记录被改
```

**处理**：把外部依赖的"到期时间"做成日历提醒。

**④ 周期性型**

```
每小时整点任务 → 整点必慢
周一早上 → 登录峰值
每月 1 号 → 账单任务
```

**处理**：看"是否周期性"（对比昨天/上周同一时刻）。

```bash
# 看昨天同一时间是否也异常
# 监控系统里对比 7 天前的同一时间窗
```

### 一个实用的排查顺序

```
① 故障什么时候开始（精确到分钟）
② 之前 24 小时有什么变更（自己的/别人的/配置的）
③ 是否有周期性（对比昨天/上周）
④ 是否有累积趋势（看指标曲线，不看当前值）
⑤ 是否跨过阈值（数据量/连接数/QPS）
```

**这个顺序能在 15 分钟内回答"是不是变更导致的"**。

### 回滚的决策

**当怀疑某次变更时**：

```
① 能回滚 → 立即回滚（先恢复，后分析）
② 不能回滚 → 先降级/关功能（止损）
③ 完全无法止损 → 明确影响面，通知相关方
```

**"先恢复后分析"** 是原则，但要注意：

```
如果回滚会丢数据/破坏状态，那要先评估
（如数据库迁移的回滚可能需要反向脚本）
```

### 记录变更的机制

**有效的做法**：

```
① 所有发布走流水线（有记录、有时间戳、有版本号）
② 配置变更也走流水线（配置中心有变更历史与审批）
③ 数据库变更走迁移脚本（有版本、有记录）
④ 平台/中间件升级发布公告（写进运维日历）
```

**"变更台账"的价值**：

```
故障时 5 分钟能查到"最近改了什么"
没有台账 → 只能靠回忆与聊天记录
```

### 检查清单

```
□ 故障开始时间精确到分钟
□ 查过最近 24 小时的发布记录
□ 查过配置变更记录
□ 查过平台/中间件升级公告
□ 对比昨天/上周同一时刻（是否周期性）
□ 看指标趋势（不只当前值）
□ 检查证书/License/配额到期
□ 有变更台账（发布/配置/DB 迁移都记录）
□ 决策顺序：先恢复后分析
□ 回滚前评估是否丢数据
```
