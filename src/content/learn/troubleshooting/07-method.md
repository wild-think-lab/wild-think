### 四步固定流程

```
① 确认现象（谁、什么时候、多大范围、能复现吗）
② 缩小范围（是全局还是单实例？是入口还是后端？）
③ 验证假设（改一个变量，看结果）
④ 记录与固化（结论进知识库）
```

**"先动手重启"** → 症状消失但根因留下。

### 分层排除（从外到内）

```
DNS → 网络（连通/端口）→ 网关/代理 → 应用 → 依赖（DB/缓存/MQ）→ 资源
```

```bash
dig app.example.com
curl -v --max-time 5 http://10.0.0.11:8080/health
ss -lntp | grep 8080
```

**判据**：每一层都有"通过/不通过"，不要跳层猜。

### 二分定位（最快的办法）

```
单实例问题 → 其他实例正常？→ 对比配置/版本/机器
单接口问题 → 其他接口正常？→ 对比代码路径/依赖
单时段问题 → 高峰期？→ 看资源与队列
```

**"全部实例都慢"** 通常不是应用代码，而是共享依赖（DB/网络/DNS）。

### 变更对照（80% 的故障来自变更）

```
① 最近 24 小时改了什么（发布/配置/证书/网络/权限）
② 有没有同时发生的其他事件（扩容、迁移、上游变更）
③ 能否回滚验证
```

**"先回滚再分析"** 在影响面大时是正确的选择。

### 常见现象的快速判据表

| 现象 | 先看 | 常见根因 |
| --- | --- | --- |
| 502/504 | 网关 error.log、后端端口 | 后端挂/超时 |
| 连接超时 | 防火墙、安全组、路由 | 端口不通 |
| 能 ping 不能访问 | 端口、监听地址 | 只监听 127.0.0.1 |
| 间歇 500 | 错误日志、依赖超时 | 连接池/DB 抖动 |
| 变慢 | P99、慢查询、GC | 索引/内存/连接数 |
| 磁盘满 | df、日志、binlog | 未轮转 |

### 五个"越查越乱"

**① 同时改多个变量**

```
不知道是哪个改动生效
```

**② 在生产上试**

```
排障变成二次故障
```

**③ 不看时间线**

```
把"先后发生"当成"因果"
```

**④ 只信一个指标**

```
CPU 不高但服务挂了（连接池耗尽）
```

**⑤ 不记录**

```
同样的问题下次还要重查一遍
```

### 记录模板

```
现象：14:03 起 order-api 5xx 从 0.2% 升至 12%
范围：3 个实例中的 2 个（10.0.0.11/12）
变更：13:50 发布 v1.4.2
验证：回滚到 v1.4.1 后 5xx 回落至 0.3%
根因：新版本连接池上限从 20 改为 5
行动：恢复上限 + 增加连接池饱和度告警
```

### 检查清单

```
□ 先描述现象（可量化）
□ 分层排除，不跳步
□ 一次只改一个变量
□ 对照最近变更
□ 有回滚预案
□ 生产操作前先备份
□ 记录时间线与判据
□ 结论进知识库
□ 补上监控缺口（防复发）
□ 复盘行动项有负责人
```
