### 排错失败往往不是"不懂技术"

```
现象：一个接口 500
错误做法：翻代码、改配置、重启、加日志……循环两小时
正确做法：先确认"500 是哪一层返回的"，再进那一层
```

**排错的核心不是知识量，是"缩小范围"的效率。**

### 五层定位法

```
① 客户端     请求发出去了吗？报什么错？
② 网络       能连上吗？端口通吗？DNS 对吗？
③ 服务进程   进程在吗？端口在听吗？
④ 应用逻辑   日志报什么？参数对吗？
⑤ 依赖       数据库/缓存/第三方能通吗？
```

**从哪层开始看现象**：

| 现象 | 先看 |
| --- | --- |
| 浏览器转圈后超时 | ② 网络 / ③ 进程 |
| 立刻返回 502/504 | ③ 进程 / ⑤ 依赖 |
| 返回 500 + 业务错误码 | ④ 应用 |
| 偶发（10% 请求失败） | ⑤ 依赖 / ④ 资源 |
| 全部正常但慢 | ④ 应用 / ⑤ 依赖 |

### 二分缩小范围

**核心动作：找到一个"能区分好坏"的边界**。

```
例：接口慢
  本地 curl 快，外部慢 → 边界在网络（不在应用）
  本地也慢，但 DB 查询快 → 边界在应用逻辑
```

**二分示例（服务不可用）**：

```
① 从本机 curl localhost → 通？     （进程与端口 OK）
② 从同网段另一台 curl IP → 通？    （防火墙 OK）
③ 从公网 curl 域名 → 通？          （LB/DNS OK）
```

每一步都能砍掉一半可能。

### "改一个变量"的验证方式

```
错误：同时改三个配置，然后"好了"
→ 不知道是哪个生效，下次还会犯
→ 可能改了无关的，真正的问题还在
```

**正确做法**：

```
① 记下当前状态（配置、版本、参数）
② 只改一个变量
③ 验证（同一个测试方法）
④ 好 → 确认原因；不好 → 回滚这个变量，再试下一个
```

**回滚很重要**：不回滚的话，变量会累积，最后又变成"不知道哪个生效"。

### 四个常见的错误习惯

**① 先怀疑"最不可能"的地方**

```
"肯定是 DNS 有问题" → 查两小时 DNS → 其实是磁盘满
```

**先查最常见、最容易查的**（磁盘、内存、进程、日志）。

**② 不看日志，先猜**

```
日志里通常已经写了原因（"connection refused"、"no space left"）
```

**看日志的正确顺序**：

```bash
# 1. 时间最近的错误
journalctl -u app --since "10 min ago" -p err

# 2. 应用自己的日志
tail -n 100 /var/log/app/error.log

# 3. 系统层（OOM、磁盘、网络）
dmesg -T | tail -30
```

**③ 只在一个地方看现象**

```
在跳板机 curl 快，就认为"服务没问题"
→ 用户从公网访问可能经过 LB/WAF，那里才是瓶颈
```

**④ 修复了症状，没找根因**

```
"重启一下就好了" → 三天后又挂
→ 必须回答"为什么它会挂"
```

**判断标准**：**如果你说不出"为什么会这样"，那只是暂时压住了。**

### 记录的重要性

**排错时最容易犯的错是"忘了刚才试过什么"**。

**建议边查边记**：

```markdown
## 现象
下单接口 502，10:20 开始

## 已排除
- 10:22 本机 curl localhost 正常
- 10:25 同网段 curl IP 正常
- 10:28 公网 curl 域名 502

## 当前判断
边界在 LB 或 WAF（本机与内网都正常）

## 下一步
- 看 LB 的错误日志
- 检查 LB 到后端的健康检查
```

**这张纸（或这个文档）在故障复盘时价值极高**。

### 一次"看起来复杂"的排错的示范

**现象**：某服务每 2 小时出现一次 30 秒的 502。

**分层**：

```
① 客户端：报 502（网关返回）
② 网络：内网 curl 正常
③ 进程：Pod 在跑，但每 2 小时重启一次
④ 应用：日志显示被 SIGTERM 后优雅退出
⑤ 依赖：无异常
```

**再往下**：为什么每 2 小时被 SIGTERM？

```
查 liveness 探针：initialDelaySeconds 太短 + 启动慢
→ 每 2 小时？不对，那会更频繁
```

**换个角度**：看节点事件。

```
kubectl describe node → 有 "Evicted" 事件
→ 节点内存压力 → kubelet 驱逐 Pod
→ 每 2 小时 = 某批任务的周期（内存峰值）
```

**根因**：同节点上的批处理任务每 2 小时起来一次，把节点内存打满，触发驱逐。

**修复**：给批处理任务设 Memory limit + 把服务与批处理分节点。

**这个案例的关键动作**：

```
① 分层（确定在 ③ 进程层）
② 二分（不是"探针问题"，是"节点驱逐"）
③ 看系统层事件（kubectl describe node）
```

### 一份可复用的排错模板

```markdown
## 1. 现象（可量化）
什么时间、什么操作、什么返回、影响多少用户

## 2. 影响面
全部/部分、哪些地域、哪些用户

## 3. 分层结论
- 客户端：
- 网络：
- 进程：
- 应用：
- 依赖：

## 4. 已排除的假设
（每条附验证方法与结果）

## 5. 根因
（一句话）

## 6. 修复与验证
（怎么改的、怎么确认好了）

## 7. 防止再发
（监控/告警/限制/流程）
```

### 检查清单

```
□ 先分层（客户端/网络/进程/应用/依赖）
□ 每次只改一个变量，改完验证
□ 不看日志不猜原因
□ 先查最常见（磁盘/内存/进程/端口）
□ 不在一个视角下结论（多视角验证）
□ 修复必须能说出"为什么会这样"
□ 边查边记录（现象/已排除/判断/下一步）
□ 最后写"防止再发"
```
