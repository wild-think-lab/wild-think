### 为什么"运动式检查"没用

```
大检查前一周：全员补文档、临时关端口
检查后一个月：一切恢复原样
```

**安全的敌人不是攻击者，是"忘"**。所以要变成月度习惯。

### 每月六件事（各 30–60 分钟）

**① 端口 diff**

```bash
nmap -Pn -p- --min-rate 1000 <公网IP> -oN scan-$(date +%F).txt
diff scan-last.txt scan-$(date +%F).txt
```

有新开端口 → 查是谁、为什么、能不能关。

**② 补丁检查**

```bash
apt list --upgradable 2>/dev/null | head -30
yum updateinfo list security 2>/dev/null | head -30
```

**③ 账号复查**

```bash
lastlog | grep -v 'Never' | head -20         # 长期未登录
awk -F: '($3==0){print $1}' /etc/passwd      # UID 0
```

**④ 日志抽查**

```
随便挑 3 天的认证日志，看有没有：
- 大量失败后成功
- 非常规时间的登录
- 新增账号
```

**⑤ 备份验证**

```
不是"看备份文件在不在"，而是"真的恢复一次"
（小库可以恢复到临时实例；大库至少校验备份完整性）
```

**⑥ 密钥与证书**

```bash
# 证书到期
echo | openssl s_client -connect example.com:443 2>/dev/null | openssl x509 -noout -enddate
# 仓库密钥扫描
gitleaks detect --source . -v
```

### 用四个指标看趋势

| 指标 | 口径 | 目标 |
| --- | --- | --- |
| 高危端口数 | 公网可达的非必要端口 | 0 |
| 未打补丁的高危组件 | 有 CVE 且未修的组件数 | 逐月下降 |
| 平均发现时间 | 从入侵到被发现的时长 | 越短越好 |
| 备份恢复成功率 | 恢复演练通过率 | 100% |

**没有指标的安全工作，无法证明有效**。

### 一次真实整改（3 个月）

**起点**：外部扫描报告列出 17 个问题（其中 5 个高危）。

**第 1 月**：关掉 5 个高危

```
- Redis 未授权（加密码 + bind）
- Docker API 暴露（改 socket）
- 管理后台默认口令（改 + 加 VPN）
- MySQL 公网可达（改 bind）
- 老版本 Nginx（升级）
```

**第 2 月**：补检测与流程

```
- 加 5 条日志检测规则
- 建月度检查表
- 加 secret 扫描到 CI
```

**第 3 月**：验证与固化

```
- 再扫一次：高危 0，中危 3（已排期）
- 做一次恢复演练
- 把检查表写进团队 wiki，指定负责人
```

**关键**：每一步都有"谁负责、什么时候做完"，不是"待办清单"。

### 让非安全岗也参与

```
① 开发：CI 里跑 secret 扫描 + 依赖扫描（他们自己修）
② 运维：端口/账号/补丁归他们
③ 产品：新功能上线前过一遍"是否收集了不必要的个人信息"
```

**安全不是安全部门的事**，是每个改动的一部分。

### 一个可复制的最小体系

```
① 资产清单（一页表）
② 加固基线（一份 checklist）
③ 五条检测规则
④ 月度六件事（30 分钟/次）
⑤ 应急流程（六步，一页纸）
⑥ 备份与恢复演练（每季度）
```

六件东西，加起来不到 20 页文档，但能覆盖 80% 的真实风险。

### 本章要点

```
① 安全的可持续性靠月度习惯，不靠大检查
② 六件事：端口、补丁、账号、日志、备份、密钥
③ 有指标才能证明有效（高危端口数、发现时间、恢复成功率）
④ 整改要有人、有时间，不是待办清单
⑤ 最小体系六件套：清单、基线、规则、月度、应急、演练
```
