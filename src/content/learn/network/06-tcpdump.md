### 抓包解决的是"猜"的问题

服务端日志里没有记录、客户端报超时——到底包有没有到？只有抓包能回答。这也是分清"服务问题"和"网络问题"的唯一硬证据。

### 先装

```bash
sudo apt install -y tcpdump     # Ubuntu
sudo dnf install -y tcpdump     # RHEL 系
```

### 三条命令起步

```bash
sudo tcpdump -i any -n port 80                 # 抓 80 端口，不解析域名
sudo tcpdump -i any -n host 10.0.0.5           # 只抓和某台机器的往来
sudo tcpdump -i any -n port 80 -c 10 -A        # 抓 10 个包后自动停，-A 显示 ASCII 正文
```

参数含义：

| 参数 | 作用 |
| --- | --- |
| `-i any` | 所有网卡（不确定走哪块网卡时用这个） |
| `-n` | 不做域名/端口名解析，输出更快更准 |
| `-c N` | 抓 N 个包后停止，避免忘了 Ctrl+C |
| `-A` | 按 ASCII 打印正文（HTTP 明文能看到） |
| `-w file.pcap` | 存成文件，拿去 Wireshark 细看 |

### 看懂一行输出

```text
10:21:33.123456 IP 10.0.0.9.54321 > 10.0.0.5.80: Flags [S], seq 1234, win 65535, length 0
```

拆开读：

- `IP 10.0.0.9.54321 > 10.0.0.5.80`：从哪台机器的哪个端口，发往哪台机器的哪个端口。
- `Flags [S]`：SYN，握手第一步。
- `[S.]`：SYN+ACK，服务端回应。
- `[.]`：ACK，确认。
- `[P.]`：PSH+ACK，带数据。
- `[F.]`：FIN，开始断开。
- `[R]`：RST，拒绝/重置——这就是 refused 的来源。

### 完整实验：证明包到没到

**服务端**（假设 10.0.0.5）开一个窗口：

```bash
sudo tcpdump -i any -n port 8080
```

**客户端**（另一台机器）发一个请求：

```bash
curl -m 3 http://10.0.0.5:8080/
```

对照三种结果判断：

| 服务端抓到的 | 结论 |
| --- | --- |
| 只有 `[S]` 进来，没有回应 | 端口没监听，或防火墙 DROP（无声丢弃） |
| 有 `[S]` 且回了 `[R]` | 端口没开，但机器可达 → refused |
| 三次握手完整，但请求后没响应 | 服务收到了但处理卡住/挂了 |
| 什么也没抓到 | 包没到这台机器：路由、安全组、抓错了网卡 |

第四种最常见的原因就是抓错网卡——`-i any` 能避免这个坑。

### 抓 HTTPS 能看到什么

只能看到 IP、端口、TLS 握手的证书域名。正文是密文，这是正常的。要看内容只能在客户端解密（如 `SSLKEYLOGFILE`），或者到服务端看应用日志。

### 一个常见误判

`tcpdump` 只抓**经过本机网卡的包**。同一台机器上两个进程用 `127.0.0.1` 通信，有时在 `any` 上也抓不到（走的是 lo 回环，不同内核版本表现不同）。本地测试请显式加 `-i lo`。

### 本章小结

- 抓包是判断"包到没到"的唯一硬证据。
- `-i any -n` 是默认组合，加 `-c` 防止忘停。
- `[S]` 无回应 = 被丢；`[R]` = 端口没开；握手完整无响应 = 应用问题。
- 抓不到先怀疑网卡选错。
