### 面板的四层结构

```
L1 总览：核心业务成功率、可用性、错误预算
L2 服务：每服务的 QPS / 错误率 / P99
L3 资源：CPU / 内存 / 磁盘 / 网络
L4 明细：单实例、单接口、慢查询
```

**"一个大盘塞 60 个图"** → 出问题时没人知道看哪个。

### 面板设计三条规则

```
① 首屏只放 5-8 个关键指标（能判断"好不好"）
② 每个图有明确问题导向（这个图异常时我会做什么）
③ 时间范围与对比（今天 vs 上周同期）
```

### SLI / SLO 怎么写

```
SLI（指标）：成功请求比例 = 2xx+3xx / 总请求
SLO（目标）：99.9% / 30 天滚动
错误预算：0.1% × 请求量 = 允许失败次数
```

**"承诺 100% 可用"** → 无法达成，也没有预算概念。

**用法**：预算用完 → 停止新功能上线，先修稳定性。

### 复盘模板（故障后 48 小时内）

```
1. 时间线（什么时候发现、什么时候恢复，精确到分钟）
2. 影响面（多少用户、多少订单、多少钱）
3. 直接原因 / 根本原因（分开写）
4. 为什么没早发现（监控/告警缺口）
5. 为什么恢复慢（预案/权限/工具缺口）
6. 行动项（负责人 + 截止时间，可验证）
```

**"复盘写成检讨"** → 没人愿意报故障，下次更晚发现。

### 行动项要可验证

```
差：加强监控
好：为 order-api 增加"下单成功率 < 98%"告警，
    负责人 A，截止 12-05，验收：人为注入失败能看到告警
```

### 五个"看板没人看"

**① 只有技术指标，没有业务指标**

```
老板/业务方不关心，技术侧也判断不了影响
```

**② 数据不准**

```
指标口径不一致 → 越看越不信
```

**③ 加载太慢**

```
一个面板 30 秒才出来 → 出故障时不想开
```

**④ 没有基线**

```
不知道"正常"长什么样
```

**⑤ 没有链接到行动**

```
看到异常后不知道找谁、按什么预案
```

### 一个最小的"值班面板"

```
① 核心链路成功率（当前 vs 昨日同期）
② 错误率 top5 接口
③ P99 延迟 top5 接口
④ 资源水位（最高的那台）
⑤ 告警未恢复列表
```

### 检查清单

```
□ 面板分 L1-L4 层
□ 首屏 5-8 个关键指标
□ 有业务指标（不只技术）
□ 指标口径有文档
□ 有 SLI/SLO 与错误预算
□ 面板加载 < 5 秒（缓存/预聚合）
□ 每图有阈值线与基线
□ 故障复盘模板固定
□ 行动项有负责人与验收标准
□ 复盘结论进知识库（可检索）
```
