### 四个黄金信号

```
① 延迟（Latency）：P50 / P95 / P99
② 流量（Traffic）：QPS、并发
③ 错误（Errors）：错误率、5xx 比例
④ 饱和度（Saturation）：CPU、内存、连接池、队列
```

**"只监控 CPU"** → 服务已经 500 了但 CPU 很闲。

### 指标分三层

```
业务层：下单成功率、支付成功率
应用层：请求量、错误率、耗时、线程池
资源层：CPU、内存、磁盘、网络
```

**排障顺序**：业务异常 → 应用指标 → 资源指标。

### 告警分级

```
P0：用户不可用（全站/核心链路）→ 立即电话
P1：部分功能受损 → 15 分钟内响应
P2：容量/趋势风险 → 当天处理
P3：提示性 → 周报
```

**"所有告警都是 P0"** → 一周后没人看。

### 抑制与聚合（防告警风暴）

```
① 同一服务同类告警 5 分钟内只发一次
② 上游故障时抑制下游（依赖抑制）
③ 按服务聚合，而不是按实例逐个发
```

```yaml
# Alertmanager 片段
route:
  group_by: ['service', 'alertname']
  group_wait: 30s
  repeat_interval: 4h
inhibit_rules:
  - source_matchers: ['alertname="ServiceDown"']
    target_matchers: ['severity="warning"']
    equal: ['service']
```

### 告警内容要能直接行动

```
差：CPU 高
好：order-api 在 10.0.0.11 CPU 92%（持续 6 分钟），
    同时 P99 从 180ms 升到 1.2s，查看链接：<dashboard>
```

**"告警没有上下文"** → 每次都要重新排查。

### 阈值怎么定

```
① 先看两周基线（P50/P95）
② 阈值 = 基线 + 合理余量（不是拍脑袋）
③ 有"持续 N 分钟"条件（防抖）
④ 定期复核（业务增长后阈值要调）
```

**"抄别人的阈值"** → 要么天天响，要么永远不响。

### 五个"告警形同虚设"

**① 无接收人/群静音**

```
告警发到没人看的群
```

**② 只告警不恢复**

```
没有 resolved 通知 → 不知道好了没
```

**③ 阈值静态**

```
业务翻倍后阈值早被击穿
```

**④ 告警依赖被监控系统本身**

```
监控挂了，告警也没了（要有外部心跳）
```

**⑤ 没人认领**

```
每条告警要有 owner（服务/团队）
```

### 检查清单

```
□ 四个黄金信号都有
□ 指标分业务/应用/资源三层
□ 告警分级明确（P0-P3）
□ 有抑制与聚合
□ 告警含上下文与面板链接
□ 阈值有基线依据 + 持续时间条件
□ 有 resolved 通知
□ 每条告警有 owner
□ 有外部心跳（监控系统自身存活）
□ 每月复核告警量与误报
```
