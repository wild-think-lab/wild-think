### 先回答三个问题

监控不是"装个 Prometheus"，而是回答三个问题：

```
① 现在是不是坏了？        → 发现
② 坏在哪一段？            → 定位
③ 要不要叫醒人？要不要动手？ → 决策
```

任何一个问题答不出来，监控就是摆设。

### 反面案例：指标很多，事故照样很晚发现

某服务接了 80 个指标：CPU、内存、GC、QPS、线程池、连接数……看起来非常完备。

一次故障：**支付回调接口返回 200，但内部逻辑写了空订单**。所有指标绿，用户投诉 40 分钟后才被发现。

问题在哪：80 个指标全是**内部状态**，没有一个描述"业务是否成功"。

结论：**监控必须从"用户视角的成败"开始设计**，而不是从"机器有什么指标"开始。

### 三层监控

| 层 | 关注 | 典型指标 |
| --- | --- | --- |
| 业务层 | 用户能不能完成目标动作 | 下单成功率、支付成功率、搜索有结果率 |
| 应用层 | 服务处理请求的健康度 | QPS、错误率、延迟分位、队列积压 |
| 系统层 | 资源是否够用 | CPU、内存、磁盘、网络、连接数 |

从上往下设计，**先有业务指标，再有应用指标，最后才是系统指标**。反过来做（先堆系统指标）就会出现"机器很健康但业务已经崩了"。

### 四个黄金信号

Google 的 SRE 提出的四类指标，覆盖绝大多数服务：

```
延迟 Latency   ：成功请求的耗时（区分成功/失败，别把快速失败算成好延迟）
流量 Traffic   ：QPS、并发连接、消息速率
错误 Errors    ：5xx 比例、超时数、业务失败率
饱和度 Saturation：资源使用率（CPU、内存、连接池、磁盘 IO）
```

一个服务只要这四项都有，且都有阈值，就已经比 80% 的团队做得好。

### 监控到什么程度：从 SLO 出发

不要凭感觉设阈值。先定 SLO：

```
可用性 SLO：99.9%（每月允许 43 分钟不可用）
延迟 SLO：P95 < 300ms
```

然后：

- 告警阈值来自 SLO（错误率 > 0.1% 才告警，因为 SLO 是 99.9%）。
- 看板阈值来自 SLO（一眼看出"离违约还有多远"）。
- 错误预算（每月 43 分钟）决定"能不能继续发布"。

没有 SLO 的监控，阈值只能拍脑袋，结果不是太松（漏报）就是太紧（天天响）。

### 三个层次的"发现"手段

1. **指标（Metrics）**：便宜、适合聚合与趋势，但看不到细节。
2. **日志（Logs）**：细节全，但量大、查询慢。
3. **链路（Traces）**：能定位"哪一段慢"，但采样有成本。

三者不是替代关系：

```
指标告诉你"有问题" → 链路告诉你"哪一段" → 日志告诉你"为什么"
```

只上指标，排障时还是抓瞎；只上日志，成本高且难聚合。

### 常见误区

**① 只监控"我能采到的"，不监控"用户关心的"**

机器指标容易采，业务指标要写代码埋点，于是大家都只做前者。

**② 告警等于"发消息"**

告警发到群里没人认领，等于没有告警。每条告警必须有**责任人 + Runbook + 升级路径**。

**③ 追求"全覆盖"**

把所有指标都接进来，结果是看板没人看、告警没人管。**监控的价值与"信噪比"成正比，与数量无关**。

**④ 不做基线**

没有基线就无法判断"这个值是不是异常"。上线第一天就该记录"正常运行长什么样"。

### 这一章要记住的三句话

1. 监控从**用户视角的成败**开始设计，不是从机器指标开始。
2. 先定 SLO，再定阈值；否则阈值永远靠猜。
3. 指标、日志、链路是"发现问题 → 定位段落 → 找到原因"的接力，不是三选一。

### 练习

1. 给你现在负责的一个服务，写出它的四个黄金信号，各一条具体指标。
2. 找出一个"内部指标全绿但业务可能已经失败"的场景，说明该补什么业务指标。
3. 用一句话定义这个服务的 SLO（可用性 + 延迟）。
