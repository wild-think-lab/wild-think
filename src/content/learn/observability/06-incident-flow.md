### 四个阶段

```
① 确认（是不是真故障，影响面多大）
② 收敛（先止血，别查根因）
③ 处置（找到根因并修复）
④ 复盘（把经验变成机制）
```

最常见的错误是**把 ① 和 ③ 混在一起**：一上来就查根因，查了 40 分钟，用户已经在骂了。

### 阶段一：确认（3 分钟内）

自问清单：

```
□ 是全体还是部分（某些接口/某些地区/某些用户）
□ 从什么时候开始（对一下发布时间、告警时间）
□ 用户能感知到什么（打不开 / 慢 / 报错 / 数据错）
□ 影响的是核心链路还是边缘功能
```

**先定影响面，再定优先级**。影响支付的 10% 错误比影响"关于我们"页 100% 错误严重。

工具顺序：拨测（外部视角）→ 看板（内部）→ 日志（细节）。

### 阶段二：收敛（止血优先）

止血手段按"最快见效"排序：

| 手段 | 时间 | 代价 |
| --- | --- | --- |
| 回滚上一版 | 分钟级 | 丢失本次发布的收益 |
| 关闭功能开关 | 秒级 | 该功能不可用 |
| 扩容 | 分钟级 | 成本 |
| 降级（返回缓存/默认值） | 秒级 | 数据可能不完整 |
| 熔断某个依赖 | 秒级 | 相关功能不可用 |

**回滚是最常用的止血手段**：70% 的线上故障由变更引起，回滚后多半立刻恢复。

回滚前要确认：

```
□ 回滚包还在（镜像/制品未被覆盖）
□ 回滚不会引入更严重的问题（如数据库已迁移）
□ 回滚后需要做的补偿（数据修复、缓存清理）
```

**数据库迁移是不可回滚的边界**。有 schema 变更的发布，必须准备"前进式修复"（forward fix），而不是简单回滚。

### 阶段三：处置（找根因）

用"分层收敛"而不是"随机猜测"：

```
① 是我方服务的问题，还是依赖的问题？
   看错误类型：5xx 全量 → 我方或网关；只有依赖调用失败 → 依赖

② 如果是依赖，是哪一个？
   按调用耗时排序，最慢的那个就是嫌疑

③ 如果是资源，是哪一类？
   CPU / 内存 / 磁盘 / 连接池 / 线程池

④ 如果是流量，是突增还是正常量下的容量不足？
   对比昨天同一时间的 QPS
```

每一层都有明确的判据，不要"重启试试"。

### 证据保全

排障过程中容易把现场破坏掉：

```
□ 先保存日志切片（不要等日志轮转掉）
□ 保存当时的指标截图（趋势比单点值有用）
□ 保存连接状态与进程状态（ss、ps、top）
□ 不要立刻删容器/重启（会丢失现场）
```

**重启是最后手段**，因为重启后所有线索都消失，问题可能几小时后再出现。

### 阶段四：复盘

复盘的目标不是"找出谁错了"，而是"系统哪里可以更不容易出错"。

模板：

```markdown
## 时间线
10:12 首次告警 / 10:15 确认 / 10:22 回滚 / 10:30 恢复

## 影响
12 分钟，约 3% 用户下单失败

## 根因
新版本引入的连接池配置错误（maxIdle=1），高并发下排队超时。

## 为什么没早发现
测试环境并发低，连接池从未成为瓶颈；监控只有错误率，没有连接池饱和度。

## 改进（必须有责任人 + 时间）
1. 连接池指标加告警（owner: 张）—— 已完成
2. 预发加并发压测基线（owner: 李）—— 两周内
3. 发布 checklist 增加"连接池参数变更需评审"（owner: 王）—— 一周内
```

关键：

1. **时间线要精确到分钟**，这是"发现晚"还是"处置慢"的唯一依据。
2. **根因要写到"为什么当时这么配置"**，而不是"配置写错了"。
3. **改进必须可验收**（谁、什么时候、怎么算完成），否则复盘等于写作文。

### 三个量化指标

| 指标 | 含义 | 改进方向 |
| --- | --- | --- |
| MTTD（发现时间） | 从故障发生到被告知 | 加拨测、补业务指标 |
| MTTR（恢复时间） | 从被告知到恢复 | 简化回滚、加开关、练 Runbook |
| 变更失败率 | 发布导致故障的比例 | 灰度、预发、自动化检查 |

**MTTD 长通常比 MTTR 长更容易被忽略**：用户投诉了才发现，说明监控没覆盖到用户视角。

### 一条纪律

**每次故障后，至少产出一条"能自动化的改进"**。

可以是：

- 一条新告警。
- 一个自动回滚脚本。
- 一个发布前的检查项。
- 一个 Runbook 的判断表。

只写"下次注意"的复盘，第二次还会犯同样的错。

### 验收

```
□ 能在 3 分钟内说清影响面
□ 止血手段（回滚/开关/降级）都演练过
□ 复盘有精确时间线与可验收的改进项
□ 改进项有责任人与截止时间，并被跟踪
```
