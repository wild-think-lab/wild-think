### 先说结论

```
云原生不是"用容器"或"上 K8s"
它是四个能力的组合：弹性、自愈、标准化交付、可观测
```

**没有这四项，谈云原生只是换了个部署工具**。

### 传统部署的四个痛点

```
① 环境不一致："本地能跑，线上不能"
② 扩容慢：加机器要装环境、配依赖，几小时到几天
③ 恢复慢：进程挂了要人发现、人重启
④ 发布风险高：一次全量更新，出问题影响所有人
```

**这四个痛点，正好对上云原生的四个能力**。

### 能力一：标准化交付（镜像）

```
镜像 = 代码 + 依赖 + 运行时 + 配置（除敏感项）
→ 同一个镜像在开发、测试、生产完全一致
```

**关键认知**：

```
镜像解决的是"环境一致性"，不是"部署效率"
部署效率靠编排与流水线
```

**"镜像里塞了配置"是常见错误**：

```
环境相关的（DB 地址、密钥）应该通过环境变量/配置挂载注入
→ 否则每个环境都要重新构建镜像
```

### 能力二：弹性

```
从"按峰值买机器"变成"按实际用量"
水平扩：加副本（HPA）
垂直扩：加资源（VPA/调 request）
```

**但要认清"弹性的边界"**：

```
① 弹性有延迟（30 秒到几分钟）
② 弹性受下游约束（数据库连接数）
③ 弹性不解决"单点"（无状态才容易扩）
```

**"以为上了 K8s 就能自动扛流量"是最常见的误解**。

### 能力三：自愈

```
① 探针失败 → 重启容器
② 节点挂 → 重新调度
③ 副本不足 → 补齐
```

**自愈的前提是"无状态 + 幂等"**：

```
有状态的服务（如本地存会话）重新调度后会丢数据
→ 状态必须外置（DB/Redis/对象存储）
```

**"自愈"不等于"不出故障"**，它只是"缩短故障时长"。

### 能力四：可观测

```
指标（Metrics）：发生了什么（数值趋势）
日志（Logs）：   为什么发生（细节）
链路（Traces）： 哪一段慢（调用链）
```

**云原生环境"更看不见"**：

```
容器短命、日志分散、Pod 频繁重建
→ 不接可观测，排障会比传统部署更难
```

**"上容器必须先上可观测"** 是这个顺序，反过来会非常痛苦。

### 与传统部署的真实差别

| 维度 | 传统（物理机/虚机） | 云原生（容器编排） |
| --- | --- | --- |
| 环境一致性 | 靠人工对齐 | 靠镜像 |
| 扩容 | 小时级 | 分钟级 |
| 故障恢复 | 人工介入 | 自动 |
| 发布 | 停机/全量 | 滚动/灰度 |
| 排障 | 登机器看日志 | 需要可观测体系 |
| 运维复杂度 | 低（但重复劳动多） | 高（但可标准化） |

**"复杂度并没有消失，只是从'重复劳动'变成'体系设计'"**。

### 三种"不该上云原生"的情况

**① 单机小应用**

```
一个 2C4G 的机器跑得好好的
→ 上 K8s 的收益 < 学习与运维成本
```

**② 没有可观测能力**

```
上容器后出问题"完全看不见"
→ 先补监控与日志，再谈迁移
```

**③ 团队没有持续维护意愿**

```
K8s 集群需要升级、调参、排障
→ 没人维护的集群会比传统部署更不稳定
```

**"为了简历上写 K8s"而上，是最常见的失败原因**。

### 一条务实的路线

```
① 先容器化（镜像 + Compose，单机也能跑）
② 补可观测（指标 + 日志）
③ 再上编排（K8s + 滚动发布）
④ 最后上 GitOps（声明式交付）
```

**每一步都能独立产生价值**，而不是"一步到位"。

### 检查清单

```
□ 能说清云原生的四个能力
□ 镜像只装不变的部分（配置外置）
□ 服务无状态（状态外置）
□ 有可观测（指标/日志/链路）
□ 知道弹性的延迟与下游约束
□ 发布用滚动/灰度（不是全量重启）
□ 评估过"是否真的需要 K8s"
□ 按"容器化 → 可观测 → 编排 → GitOps"推进
```
